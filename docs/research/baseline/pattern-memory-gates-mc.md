## 1. FEATURE LIST

### 1.1 Pattern memory — what it is, what is stored, where

1. **Pattern memory (the derived, read-only synthesis)** — A per-setup view over the trader's own closed journal: similarity-scored historical trades, aggregated win-rate/R stats, warnings, and severity-tagged lessons. **REAL** (it is computed and consumed), but only *part* of it is reachable.
   - Similarity scoring: `services/learning/PatternMemorySynthesisService.ts:130-197` (weighted coin/family/pattern/regime/direction/confidence/recency, capped at 100).
   - Relevant-trade selection (similarity > 20, top 3, 120-day exponential decay): `services/learning/PatternMemorySynthesisService.ts:301-361`.
   - Aggregated stats incl. `sumLossR` / `lossesWithR`: `services/learning/PatternMemorySynthesisService.ts:366-445`.
   - Synthesis bundle: `services/learning/PatternMemorySynthesisService.ts:500-523`.

2. **Pattern memory (the stored ledger — "attributed insights")** — Free-text lessons with a scope (`global` / `coin` / `pattern` / `regime` / `family`), a source provider, quality score and used/helpful counters; now notebook-backed (`distilled/` folder, cap 200) rather than a Preferences key. **REAL** (write + read + feedback loop all work).
   - Store: `services/learning/distilledMemory.ts:202` (`loadDistilledFacts`), `:248` (`mergeDistilledFact`), `:239` (`writeDistilledFact`), cap at `:38` (`DISTILLED_FACT_CAP = 200`).
   - Facade: `services/learning/PatternMemorySynthesisService.ts:706-708` (load), `:719-739` (add), `:747-749` (upsert), `:800-821` (feedback → qualityScore = timesHelpful / (timesHelpful + timesNotHelpful)).
   - Live consumer of the feedback write: `components/dashboards/VersionHistoryDashboard.tsx:101,110`.

3. **How a stored pattern reaches a future turn** — Three real paths, one dead one.
   - **LIVE (1) — Similar closed trades in the retrieval slice:** `services/learning/MemoryRetrievalService.ts:691-707` calls `findRelevantTrades(..., { decayByAge: true, cutoffMs: asOfMs })` and renders the block into the notebook slice that every analyst seat receives. Reached via `hooks/analysisPipeline/memoryContext.ts:143` → `hooks/useAnalysisPipeline.ts:1169-1176` → `enhancedPrompt`.
   - **LIVE (2) — Journal track record + per-model regime weighting:** `hooks/analysisPipeline/memoryContext.ts:156-165` calls `buildSimilarSetupsContext` / `buildRegimeWeightingContext` (`services/learning/SetupMemoryService.ts:131-172` and `:287-310`); `hooks/useAnalysisPipeline.ts:1172` puts the block into the prompt.
   - **LIVE (3) — Pattern-memory penalty in the programmatic gate:** `services/validation/GateKeeperService.ts:146-202` scores the current setup against the journal's losses with the same `calculateSimilarity`, time-decays it, and converts a ≥70 % match into a confidence-cap penalty + a suggested opposite direction. Live because `runProgrammaticGate` is called by `services/trade/proposalGate.ts:215`.
   - **DEAD — `generateSynthesizedPromptInjection`** (`services/learning/PatternMemorySynthesisService.ts:589-669`): the function the flow doc called "the injected sentence" (`docs/app-flow.md:608`; corrected 2026-10-23 — the paragraph now marks it dead at `:613`) has **zero** production callers. Only its own module and the test file reference it.

### 1.2 Pattern detection (what a human would see on the chart)

9. **Classical candle-pattern detector** — **REAL.** 1,245 lines, deterministic, order-N over a 30-bar window: single-candle (doji family, pin bars, marubozu, belt hold), two-candle (engulfing, tweezers, harami, piercing, dark cloud), three-candle (morning/evening star, three soldiers/crows, three inside, FVG), four/five-candle (three-line strike, rising/falling three methods) and market structure (double top/bottom, BOS, CHoCH, SFP, HH/HL/LH/LL). Entry point `services/analysis/CandlePatternDetector.ts:1124-1245`; live at `services/analysis/HybridIntelligenceService.ts:503-508` into the packet that reaches the prompt.
   - Notable correctness: a doji is `'⚪'` and counts toward neither bull nor bear (`:1204-1224`); the incomplete last candle is excluded (`:1146`).

10. **Geometric chart patterns with MEASURED touches** — **REAL, and honest.** `utils/patternDetection.ts:215-400` detects head & shoulders, double top/bottom and triangles; `countTouchesOnLine` (`:68-102`) counts distinct *visits* of price to the line, and `patternStatus` (`:125-126`) only says "confirmed" at ≥ 3 touches. The packet labels a 2-touch shape "ASSUMPTION, not a setup" (`services/analysis/HybridIntelligenceService.ts:961-979`). Live at `HybridIntelligenceService.ts:513-518`.

11. **Snapping a model-named level onto real structure** — **REAL.** `utils/patternDetection.ts:425-453` (`snapPriceToStructure`, 0.3 % tolerance) — a model that says "support at 62150" gets the real swing price if one is within tolerance, and its own number untouched if none is. Live at `services/trade/chartDrawings.ts:342`.

12. **Pattern-family classification (the "lightweight ML" scorer)** — **REAL but advisory.** `services/analysis/PatternClassificationService.ts:61-193` scores four families from RSI/divergence/volume/ADX/MACD and returns the winner + confidence. It is computed and shipped in the packet (`services/analysis/HybridIntelligenceService.ts:609`) — it is a label, not a gate; nothing blocks on it.

13. **Pattern-family *bias* in the gate** — **PARTIAL.** `services/validation/GateKeeperService.ts:90-96, 138-142, 191-196, 217-236, 246-254` compute a per-family bias (A/B/C/Omega). It is returned in `GateOutput.familyBias` and rendered in the card, but `runProgrammaticGate`'s philosophy is stated in the file itself: "ALL families are ALWAYS allowed - no exclusions" (`:74-75`). The bias therefore steers nothing in code; `getGateAnalysis`'s prompt prefix that would have shown it is itself dead (see 1.4).

### 1.3 Monte Carlo

14. **The Monte Carlo simulation itself** — **REAL.** It is a genuine geometric-Brownian-motion simulation with a Markov regime switch, not a formula wearing a simulation's name.
    - Path generator: `services/analysis/MonteCarloService.ts:222-258` — GBM log-return with a per-step regime switch (`switchProb` 0.05) and per-regime vol/drift multipliers (`:208-217`).
    - Path evaluation: `:263-387` — intra-step high/low synthesized from the path's own log-return sigma (`:292-311`), stop checked **before** targets on the same bar (`:321-333`), targets ordered nearest-first via `targetsByDistance` (`:287-290`).
    - Aggregation: `:396-523` — 1,000 sims by default, exclusive TP1/TP2/TP3/SL/TIMEOUT buckets, EV over resolved paths only (`:469-476`), true `avgWinPercent` / `avgLossPercent` from the positive/negative samples (`:478-489`), 5th/95th percentile trade-PnL interval.
    - **Deterministic:** a seeded mulberry32 PRNG (`:114-123`) with an FNV-1a-derived seed from the setup identity (`:145-157`). Same setup → same "Simulated Win Rate" run after run. Pinned by `tests/financialMath.test.ts:157-166`.
    - **Honest about its own inputs:** `monteCarloToMarkdown` (`:718-747`) states the assumptions ("ATR … not fetched; timeframe is a label only; neutral initial drift/regime") and ends with "Statistical estimate from simulated price paths, NOT a forecast".

15. **Ruin risk / Kelly** — **REAL.** `services/analysis/MonteCarloService.ts:581-709` runs 1,000 fixed-fractional equity sequences × 100 trades on the same seeded generator, reporting P(≥25/50/75 % drawdown), mean equity after 100 trades and the Kelly-optimal size. `computeKellyFraction` (`:548-569`) is guarded (no Infinity/NaN, clamped to [0,1], zero-EV ⇒ 0) and is fed the **resolved** win rate so a long-horizon timeout pile-up cannot collapse a real edge to zero.

16. **The web worker** — **REAL and wired.** `services/analysis/monteCarlo.worker.ts:35-58` handles `runSimulation` and `calculateRuinRisk` by calling the *same* exported functions, so worker and main-thread results are byte-identical. The pool is 4 workers with round-robin dispatch, a 10 s timeout, worker ejection on timeout, and a crash handler that rejects all pending requests and drops the pool (`services/analysis/MonteCarloService.ts:783-900`). Both entry points exist: `runSimulationAsync` (`:907-918`), `calculateRuinRiskAsync` (`:927-946`).
    - Note: the worker imports the *service* module, which imports `utils/riskReward` — fine, but it means the "off the main thread" claim carries the service's module graph.

17. **Monte Carlo's effect on the trader** — **PARTIAL / ADVISORY.** The simulation reaches the trader only as **model-facing text**, on demand:
    - Live path: the `run_monte_carlo` desk tool (`services/analysis/DeskToolsService.ts:3177-3206`) — the model calls it, and the markdown digest becomes the tool result the model reads.
    - Second live path: the "What-If" scenario simulator (`services/backtesting/ScenarioSimulatorService.ts:178-224`) — a UI slider that shows the simulated win rate to the trader.
    - **Nothing downstream reads a Monte Carlo result.** The proposal gate (`services/trade/proposalGate.ts`), the programmatic gate (`services/validation/GateKeeperService.ts`) and the confidence clamp (`utils/analysisUtils.ts:1381-1425`) never mention Monte Carlo. A plan whose Monte Carlo win rate is 5 % is logged exactly like one whose simulated win rate is 95 %, provided the other gates pass.
    - The per-analyst Monte Carlo pass is **dead**: `runMonteCarloForSetup` / `runMonteCarloForSetupAsync` (`services/analysis/HybridIntelligenceService.ts:1409-1444`) have no production callers, and the state they would fill (`latestMonteCarloResult`, `perAIMonteCarloResults` in `hooks/useMarketData.ts:20-22`) is declared and passed around but **never set** — `setLatestMonteCarloResult` / `setPerAIMonteCarloResults` appear only as pass-throughs in `App.tsx:515,517,825,826` and `hooks/useAnalysisPipeline.ts:165,167`.

### 1.5 The trade-plan / proposal gate

25. **The proposal gate (`services/trade/proposalGate.ts`)** — **REAL.** This is the one deterministic gate in the product that actually binds a trade plan.
    - `runGateScan` (`:189-252`) never throws: every failure path returns an `unavailable` stamp (`:72-83`) that is deliberately **cap 1, not cap 0** — "0 is a measurement, not an absence" (`:18-22`).
    - `ensureStamp` (`:317-325`) is the ONE call every log path makes; it reuses a fresh stamp (< 120 s, `:48`, `:308-312`) and otherwise runs the scan.
    - `beginGateScan` (`:282-297`) de-dupes one fetch per plan id; `cancelGateScan` (`:301-306`) makes a stopped turn settle as `unavailable` rather than a late evaluated stamp.
    - `gateReceiptLine` (`:328-334`) tells the model "The card will not offer 'Log this trade'; do not ask the user to log it" on a refusal.

26. **The min-edge (net-expectancy) refusal** — **REAL, BLOCKING.** `services/trade/proposalGate.ts:95-115` (`assessMinEdge`) builds the plan through the *same* `buildTradePlan` the card and the journal use (`:100-103`), reads `plan.netEdgeR` from `utils/netRiskReward.ts:283-322`, and refuses when `netEdgeR <= thresholdR` (the trader's own `minEdgeR` setting, `utils/harnessSettings.ts`). The refusal text names the number and the floor: "net expectancy −0.44R at 44 % is at or below your 0.00R floor — after fees" (`:112`).
    - The cost model is real and conservative: 5 bps taker per side, slippage explicitly **not modelled** and typed as the literal `false` (`utils/netRiskReward.ts:46-61`, `:99-104`), with "unknown" returned as `null` + a reason rather than a misleading `0` (`:135-149`).

27. **The plan-shape refusal (inverted levels)** — **REAL, BLOCKING.** `services/trade/proposalGate.ts:152-181` (`assessPlanShape`) refuses a plan whose stop or nearest target sits on the wrong side of the entry, using the canonical `plannedRiskRewardSigned` (`utils/riskReward.ts:163-217`) and the shared ordering gate `utils/levelOrder`. The refusal survives a failed market fetch (`:213`, `:249`) because the arithmetic is plan-local.

28. **The R:R floor and the ATR stop bands** — **REAL, ADVISORY (warn).** `services/trade/proposalGate.ts:171-180` calls the live `validateRiskReward` (`services/validation/AccuracyValidationService.ts:206-298`) and turns its warnings into `gate.warnings` — *not* a refusal. The owner's ruling is recorded in the file: "the app proposes; the trader decides" (`proposalGate.ts:146-151`). The bands are: R:R below the confidence floor (2.0/1.5/1.2/1.0, `ValidationConstants.ts:78-83`), a stop tighter than 1× ATR, a stop wider than 3× ATR, and a stop > 5 % from entry (`AccuracyValidationService.ts:259-284`). With no ATR both ATR bands stand down (`:269`), which is what stopped the old "Infinityx ATR" warning on every plan (`tests/accuracyValidation.test.ts:133-144`).
    - This is the **only** production caller of `validateRiskReward` — the comment at `proposalGate.ts:140-145` says so explicitly: "its only production caller was `TradeValidationGate.ts` — a module with no importer — which is why a plan could be graded against a floor nothing enforced and the trader never saw it."

29. **The code-checked skill ceiling / AVOID trigger** — **REAL, BLOCKING for a fired AVOID trigger (as a cap), advisory otherwise.** `services/trade/proposalGate.ts:258-275` (`buildSkillGate`) calls `services/learning/skillPredicateGate.ts:131` (`evaluateSkillPredicates`); the returned ceiling is folded into the stamp (`:216-218`, `:230-231`) and therefore into the recorded probability. A fired `avoid` trigger names itself in the stamp note (`:271`).

30. **The confirmed-notebook-skill VETO** — **REAL, BLOCKING.** `services/trade/presentTradeTool.ts:113-133` runs `applyNotebookSkillsToAnalysis` (`services/learning/SkillMemoryService.ts:3819`) and, when the skill set says veto, **refuses the `present_trade` call itself** — the plan is never presented, the model gets "present_trade refused: … Do not retry this plan; tell the trader which rule vetoed it", and the refusal is written to the veto ledger (`:117-129`). A *candidate* AVOID only downgrades the tier (`:134-138`).

31. **The confidence cap binding the journal row** — **REAL.** `services/trade/proposedTrade.ts:166-233` (`buildTradePlan`) folds the gate cap and the skill ceiling into the probability through the one shared clamp `utils/analysisUtils.ts:1381-1425` (`clampProbabilityToGate`, which also applies the R:R grade floors 54 % / 69 %), re-tiers the confidence word with the one shared rule `utils/analysisUtils.ts:1457-1468` (`downgradeConfidenceForProbability`), and records every gate word on the row (`proposedTrade.ts:202-207`). An unmeasured scan is recorded **UNCAPPED with the reason** (`:192-196`) — never a fabricated 0 %.

## 3. WEAK SPOTS

Ordered by how much they cost the trader.

1. **The whole 41 KB `TradeValidationGate` is dead code.** `services/validation/TradeValidationGate.ts` has **0 import sites** in the entire production tree. Twelve validation steps, an `isValid` flag, an adjusted confidence, a printable report — none of it runs. The live product keeps exactly one of its checks alive (`validateRiskReward`, re-homed at `services/trade/proposalGate.ts:171`), and `services/trade/proposalGate.ts:140-145` says so in a comment: *"its only production caller was `TradeValidationGate.ts` — a module with no importer — which is why a plan could be graded against a floor nothing enforced and the trader never saw it."* Everything else that gate guarded — MTF confluence, volume, regime, Devil's Advocate, crowding, session risk, entry timing, SL optimisation, scalp/swing rules, the pattern-memory similarity check — is **not enforced anywhere**.

2. **The pattern-memory gate is a test-only artefact.** `generateMandatoryPatternCheck` (`services/learning/PatternMemorySynthesisService.ts:882-976`) computes a correct HALT / REDUCE_SIZE / WARNING / PASS verdict, and `generatePatternMemoryEnforcementContext` (`:982-1081`) turns a HALT into the text "🚫 **DO NOT APPROVE THIS TRADE**" (`:1065-1066`) — but neither function is called from production, and `Message.patternMemoryGate` is never assigned, so the journal's HALT chip (`components/journal/TradeLog.tsx:359-386`) is unreachable. `docs/app-flow.md:610-611` nonetheless told the reader that this is "the pre-trade gate that refuses a setup with no evidence" — corrected 2026-10-23, the paragraph now marks it dead and names `services/trade/proposalGate.ts:152`. **A doc claim that outruns the code is worse than no claim.**

3. **The session guardrails never run.** `services/validation/SessionGuardService.ts:157-268` implements the research's hard numbers (2 % daily loss, 2 trades/day, streak pause at 2, 4 h post-loss cooldown) and fails closed when equity is unset (`:168-186`) — and `assessSession` is called **only from tests**. The trader's own stated breaker is the app's least-firing guard.

4. **The chat/analysis path has no deterministic gate at all.** `hooks/useAnalysisPipeline.ts:1203` reduces the gate injection to `const gateInjection = '';`; the analysis's probability is never capped (`utils/analysisUtils.ts:1381-1425` is called only from the `present_trade` path); `analysis.gateResult` and `analysis.verdictReview` are passthrough schema fields the *model* can populate and the card renders as if they were measurements. A chat turn is therefore graded entirely by the model that produced it.

5. **Calibration is advisory text, not an adjustment.** `services/validation/calibrationPrompts.ts:383-390` tells the model "Use the ADJUSTED confidence level in your final recommendation" and returns `adjustedConfidence`; `hooks/useAnalysisPipeline.ts:1006-1037` reads only the injection string. A 40-point penalty that should read `Avoid` (`services/validation/calibrationPolicy.ts:605-611`) is a paragraph.

6. **Rolling-20 performance does not steer routing.** The functions that would — `calculateDynamicWeights` (`services/backtesting/ModelPerformanceService.ts:531-629`) and `calculateDynamicWeightsEnhanced` (`:1041-1138`, with the explicit "PRIORITY 1: Rolling window performance (last 20 trades) — up to ±25 points") — have no production callers. The live prompt ranks providers by the **all-time** win rate (`:649`) and only mentions the rolling window for its cold-streak count (`:652`). `services/learning/providerFitness.ts` — the module that exists precisely to drop a proven underperformer from the next roster (`:7-9`) — is dead; the `autoAssignLenses` consumer it names does not exist in the repo.

7. **Monte Carlo is real but display-only.** It is a genuine seeded GBM simulation with a correctly wired worker (`services/analysis/monteCarloService.ts:222-258`, `services/analysis/monteCarlo.worker.ts:35-58`), but nothing downstream reads a result. The per-analyst Monte Carlo pass is dead: `runMonteCarloForSetup(Async)` (`services/analysis/HybridIntelligenceService.ts:1409-1444`) has no callers and `setLatestMonteCarloResult` / `setPerAIMonteCarloResults` are never called. The trader sees a simulated win rate in a What-If modal and the model sees a markdown digest — neither changes what gets logged.

8. **Two severity-insight writers, one of them unreachable.** `services/learning/severityInsights.ts:269` (`extractCumulativeBleedInsightForTrade`) is the post-mortem path that was supposed to record "this setup bled 6R" as a durable lesson, and it has no production caller; `services/learning/settlementReflection.ts` writes the post-mortem (`:310`) and never touches the severity store. The severity bucket the gate's mandatory question quotes (`PatternMemorySynthesisService.ts:852-876`) is therefore empty in a running app.

9. **The severity-insight store has no writer that runs, and the generic insight store is display-only.** `addAttributedInsight` / `upsertAttributedInsight` (`PatternMemorySynthesisService.ts:719-749`) are only reached from `severityInsights.ts` (dead) and from the test suite. `recordInsightFeedback` (`:800-821`) is live but writes to a bucket nothing reads back into a decision.

## 4. WHAT IS ALREADY GOOD

Stated plainly, because the point of this baseline is to know what not to break.

1. **The proposal gate is a real, carefully-designed refusal path.** `services/trade/proposalGate.ts:189-252` never throws, distinguishes "measured low" from "could not measure" (`:18-22`), caps at 1 rather than 0 when the fetch fails (`:72-83`), de-dupes one fetch per plan (`:282-297`), and treats a stopped turn as `unavailable` rather than settling a late stamp (`:212`, `:301-306`). The refusal is enforced at the *write* boundary (`App.tsx:1580-1586`), shown on the card (`components/trade/panels/TradeProposalCard.tsx:162-166, 206-209`) and told to the model ("do not ask the user to log it", `proposalGate.ts:329`). **This is the model to copy for every other gate in the app.**

2. **The refusal is fail-closed where it should be and fail-open where it should be.** An unmeasurable plan asks for an explicit confirm and is recorded UNCAPPED with the reason (`App.tsx:1587-1595`, `services/trade/proposedTrade.ts:192-196`) — never a fabricated 0 % cap. An inverted plan is refused **even when the market fetch is down** (`proposalGate.ts:213`), because that arithmetic is plan-local.

3. **The cost model is honest about its own ignorance.** `utils/netRiskReward.ts` types `slippageModeled` as the literal `false` (`:99-104`), returns `null` + a reason instead of a misleading `0` when a cost cannot be computed (`:135-149`), and labels every net figure "net of 10 bps round trip (5 bps/side) · slippage not modeled" (`:214`). The R:R floor and the ATR bands come from one shared place (`services/validation/ValidationConstants.ts:78-83`).

4. **One R:R formula, one clamp, one confidence-band rule.** `utils/riskReward.ts:96-108` (nearest target ÷ stop, order-independent), `utils/analysisUtils.ts:1381-1425` (`clampProbabilityToGate`), `utils/analysisUtils.ts:1457-1468` (`downgradeConfidenceForProbability`). The card, the journal row, the gate and the test suite all read the same helpers — and `tests/proposalGate.test.ts:309-358` pins that the cap lands on the row.

5. **The Monte Carlo is a real simulation with a real worker and a real determinism story.** Seeded mulberry32 + FNV-1a setup identity (`services/analysis/MonteCarloService.ts:114-157`), intra-step high/low synthesis so a TP/SL touch between closes is visible (`:292-311`), the stop checked before the target on the same bar (`:321-333`), EV over resolved paths only (`:469-476`), Kelly fed the resolved subsample with a real average win (`:548-569`, `:603-617`), and a worker that imports the *same* functions so both paths agree (`:907-946`, `services/analysis/monteCarlo.worker.ts:35-58`). `monteCarloToMarkdown` (`:718-747`) states the assumptions and says "NOT a forecast". `tests/financialMath.test.ts:151-190` and `tests/monteCarloRuinRisk.test.ts` pin all of it.

6. **Pattern detection is measured, not asserted.** `utils/patternDetection.ts:68-102` counts *visits* to a line (so twenty consecutive bars on a level are one touch, not twenty), `patternStatus` (`:125-126`) only says "confirmed" at three touches, and the packet labels a two-touch shape "ASSUMPTION, not a setup" (`services/analysis/HybridIntelligenceService.ts:961-979`). A model-named level is snapped onto the real swing or left alone (`utils/patternDetection.ts:425-453`). The candle detector distinguishes a doji from a bearish close (`services/analysis/CandlePatternDetector.ts:1204-1224`).

7. **The journal really does become the model's edge.** `services/learning/SetupMemoryService.ts:131-172` puts the trader's own win rate, average win/loss, expected value and the three most recent comparable outcomes in front of every analyst seat (`hooks/analysisPipeline/memoryContext.ts:156-161`), flags a cold start at N < 5 and tells the model not to raise confidence on it, and `services/learning/MemoryRetrievalService.ts:691-707` surfaces similar closed trades with 120-day age decay and a point-in-time cutoff so a replay cannot see the future.

8. **The notebook skill layer has a genuine hard veto.** `services/trade/presentTradeTool.ts:113-133` refuses the `present_trade` call on a confirmed avoid-skill and records the veto in the ledger, and `services/learning/SkillMemoryService.ts:3943-3959` (`confirmedAvoidForSetup`) stands down under the ε-holdout so the A/B measurement stays honest.

9. **The calibration store is one population, one horizon.** `services/validation/calibrationStore.ts:99-122` rebuilds the confidence buckets from the pruned entry list instead of incrementing (the comment at `:99-108` records exactly the drift that was fixed), and `:267-290` rebuilds every granular dimension the same way — so a coin that was poison a year ago cannot subtract its penalty forever.

10. **Pass mining is a real post-hoc counterfactual with a human gate preserved.** `services/learning/passMining.ts:90-108` resolves skipped trades against the production outcome engine, `:248-299` turns a cluster of ≥ 3 correct passes into an avoid-skill **draft** through the approval inbox, and missed opportunities are a counter-metric only — the module explicitly refuses to teach the system to take more trades.

11. **The rolling window is honestly maintained.** `services/backtesting/ModelPerformanceService.ts:491-497` appends the current trade to the rolling window **before** deriving the recent trend, precisely so a mid-session cold streak is visible; the window is trimmed to 20 per provider (`:886-890`) and rebuilt from the journal at boot (`:1144-1189`).

12. **The tests pin the intended behaviour and are specific.** `tests/proposalGate.test.ts` (322 lines) pins the refusal, the unavailability semantics, the one-fetch-per-plan rule, the stamp freshness, the R:R warn-not-refuse split, the ATR bands standing down with no ATR, and the inverted-plan refusal winning over the edge floor. `tests/patternMemoryGate.test.ts` (219 lines) pins the extended-loss REDUCE_SIZE, the few-but-deep HALT, the single-outlier non-HALT and the surface dedupe. `tests/accuracyValidation.test.ts` pins the direction-aware R:R and the symbol-scoped pattern memory. `tests/financialMath.test.ts` pins the clamp, the leverage double-compounding guard and the Monte Carlo determinism. **The tests are good; the problem is that some of the code they pin is not on any production path.**

## 5. ONE-PARAGRAPH SUMMARY

The app has one real gate — the `present_trade` proposal gate — and it is well built: it refuses inverted plans and plans below the trader's net-expectancy floor, caps the recorded probability through one shared clamp, fails closed on an unmeasurable scan, and shows the refusal on the card and in the toast. Around it sit three large, well-tested, **unwired** validation systems: the 41 KB `TradeValidationGate` (0 importers), the `SessionGuardService` breaker (called only by tests), and the pattern-memory HALT gate (called only by tests — its journal chip can never render, and the flow doc describes it as a live pre-trade refusal). The chat/analysis path has no deterministic gate at all: the gate injection is a hardcoded `''`, the calibration penalty and the provider-accuracy note reach the model only as prose, and the Monte Carlo is a genuine, correctly-workerised simulation whose result nothing downstream reads. Model performance is tracked faithfully but steers nothing in code: the rolling-20 functions that would demote a provider have no callers, and the module written for that job (`providerFitness.ts`) names a consumer that does not exist.
