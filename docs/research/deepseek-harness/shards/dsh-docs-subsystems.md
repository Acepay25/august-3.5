# deepseek-harness :: dsh-docs-subsystems

**Files in shard:** 201 (read: 134, skipped with reason: 67)
**What this shard covers:** The `docs/subsystems/` folder of the DeepSeek Harness — one reference page per subsystem, each written as a *contract page*: a prose section explaining what the subsystem decides and why, a set of `ts type-equiv` fences carrying the load-bearing TypeScript declarations **verbatim from source** (drift-checked by `pnpm run verify-type-equiv`), and a machine-generated **Cordis API** section (`scripts/gen-cordis-catalog.ts`) listing the `ctx.<service>` surface and every event with its dispatch mode (`emit` / `serial` / `waterfall` / `parallel`). Each page exists in English and in a Chinese translation (`*.zh.md`), and each has a generated `*.i18n.yaml` translation-pairing manifest. This shard is therefore a *complete, machine-verified index of the harness's internal vocabulary*: the session event log, the agent loop, the tool registry, the LLM streaming protocol, compaction, approvals, schedules, goals, jobs, subagents, agent teams, skills, persistence, credentials, and the whole Web-client stack.

## 1. Tier-1 — load-bearing source: full entries

The shard contains no `source`-classified files, but a subset of the subsystem pages is genuinely load-bearing design documentation. Those get full entries here. **Every other file in the shard appears exactly once in the tier-2 tables in §2–§4** and is not repeated here.

### `docs/subsystems/core.md`
- **Purpose:** How `packages/core` drives the agent loop — package-by-package loop description, `Agent`/`AgentHandle` ownership and delivery contracts, the two repo-wide type patterns, and the full `agent/*` event vocabulary.
- **Key abstractions:** `Agent` (the public live handle: `id`, `options`, `session`, `inbox`, `status`, `ctx`, `cancel`, `whenIdle`, `runMaintenance`, `send`, `followup`, `steer`, `inject`); `AgentHandle` (owner-only disposer — *the disposer is a capability*); `Inbox` / `InboxTarget` (`'next-turn' | 'next-step'`); `AgentStatus` (`'idle' | 'running'`); `AssistantStreamFrame`; `AgentOptions`; `PreStepDecision`; `RequestErrorAction`; `AgentCancelCause`; `Branded<B>`.
- **Data flow:** `agent-loop` claims a queued prompt from the inbox → opens a turn on the session log → assembles the system-prompt prefix → derives history from the log → streams the model response → dispatches tool calls → appends every model-visible fact back to the log → the next step derives from it (`core.md:9-19`).
- **Non-obvious design decisions:**
  1. The **inbox is two ordered lists**, not one queue — `next-turn` and `next-step` — and steering/injection/follow-up are *fixed-preset aliases* over one unified `send(message, target, wakeup)` (`core.md:322-350`).
  2. `cancel(cause)` takes a **typed cause** that lands in the durable `turn/end` record as `{kind:'aborted', reason}`, so the cancel reason survives the process (`core.md:352-370`).
  3. `whenIdle()` "follows replacement work started before the observed driver retires, but does not identify the settlement of any particular message" — the doc explicitly warns that callers may call a receipt-to-idle interval *a run* only when they own that interval (`core.md:277-283`).
  4. `AgentPresetRegistry` retains a **revision** per preset; a child can `composeFrom()` the exact revision its parent retained, so a preset change cannot mutate a running child mid-flight (`core.md:500-560`).
  5. The **`…Map → derived-union` pattern** is the repo's plugin-extension mechanism: `ContentBlockMap`, `MessageSourceMap`, `FinishReasonMap`, `TurnEndReasonMap`, `SessionEventMap` are all extended by declaration merging with no edit to the owning package (`core.md:364-398`).
- **Edge cases & failure handling:** `register()` returns an *exact-identity* Cordis effect disposer, and the doc insists on it: yielding a wrapper would let the agent unregister and emit `agent/disposed` while its final turn is still draining (`core.md:690-712`). `agent/created` is a **serial** dispatch — a throwing listener fails creation and skips later listeners; listeners must not await `agent.whenIdle()` or their own owner's disposal (`core.md:640-656`). `agent/request-error` is a waterfall where a listener may return `{kind:'retry'}` *without* calling `next()` to own recovery (`core.md:846-864`).
- **Surprising:** `AgentStatus` has only two values — disposal is *not* a third status; `agent/disposed` is an event, not a state (`core.md:264-272`). `running` "describes the driver-wide drain interval and may span consecutive queued turns; it does not prove a turn is still open."

### `docs/subsystems/session.md`
- **Purpose:** The full `SessionEventMap` variant catalog, `TurnEndReason`, `deriveMessages()`, the execution enclosure, and standalone events.
- **Key abstractions:** `SessionEvent` (monotonic `seq`, `time`, discriminated `data`); `SessionEventMap` → `SessionEvent`; `TurnEndReasonMap` → `TurnEndReason`; `deriveMessages()` / `deriveEventMessage()`; `SurfaceEventType`; `SurfaceOp` (`'append' | {op:'replace', startSeq, endSeq}`); `SurfaceIntent`; `EpochHeader`; `RequestContext`; `SessionSurface`.
- **Data flow:** everything model-visible is appended to the log; the LLM history is **derived** from the log by `deriveMessages()` rather than stored separately; surface variants may cite earlier events via `sourceEventSeqs` and carry a `surfaceOp` (a *replace* range) to rewrite the visible surface without deleting history (`session.md:30-190`, `session.md:666-690`).
- **Non-obvious design decisions:**
  1. The log is the **single source of truth** and the message history is a *projection*; `deriveMessages()` is a pure function of the log, cached (pure tail growth is O(new nodes); a replacement rebuilds) and frozen.
  2. `surfaceOp` + `sourceEventSeqs` let one event *rewrite* the visible surface without deleting history — compaction and checkpoints both ride this.
  3. Turn and step boundaries are **durable session events**, not agent emits.
  4. The system prompt is **not** in the request header: it is derived history (surface node 0, a `system/message`), so a prompt change replaces a surface node and leaves `EpochHeader` untouched (`session.md:200-232`).
  5. `ignorable?: true` on an event marks it safely skippable; the default is *required*, "defaulting to required means a forgotten marker over-refuses … rather than silently resuming a gutted session" (`session.md:470-490`).
- **Edge cases & failure handling:** because `SessionEventMap` is merge-extensible, switches over `SessionEvent` must **not** use `assertNever` — a plugin-added variant is a valid unknown value (`session.md:492`). `Session.append` validates JSON-serialisability, the canonical request-header shape, the tool-error consistency rule, and the whole surface contract **at the append site**, "so a bad event fails at the append site rather than later during a backend flush" (`session.md:565-600`).
- **Surprising:** `session/end-seed` exists because "seed history and live work are otherwise byte-identical", which defeats any plugin owning a standalone open/close bracket: an unmatched `compaction/start` reads the same whether the writer crashed mid-compaction or is compacting right now (`session.md:790-830`).

### `docs/subsystems/llm-streaming.md`
- **Purpose:** The `packages/llm` conversation types — `Message`/`ContentBlock`, the assembled model request, the `StreamChunk` wire protocol, `BlockAssembler`, and the `LlmAdapter` provider contract.
- **Key abstractions:** `ContentBlockMap` → `ContentBlock`; `MessageSourceMap` → `MessageSource`; `FinishReasonMap` → `FinishReason`; `ContextForm`; `StreamChunk`; `ReplayEnvelope`; `BlockAssembler`; `LlmAdapter`; `PreparedLlmCall`; `LlmCallConfig`; `LlmFailure`; `TokenUsage`; `LlmResolvedModelInfo`.
- **Data flow:** the assembled request (system prompt + derived history + tools) → the adapter → a stream of `StreamChunk`s → `BlockAssembler` folds them into `ContentBlock`s → the completed block(s) are appended to the session log.
- **Non-obvious design decisions:**
  1. `FinishReason` is a **derived union from a map**, so a provider adds a stop reason by declaration merging; the same mechanism covers content blocks and message sources.
  2. `ContextForm` separates **who produced this** (`kind`) from **what kind of thing it is** (`form`), and the vocabulary is explicitly "SEMANTIC, never visual" — "Colors, icons, ordering, and collapse defaults are the consumer's business and must not enter this union" (`llm-streaming.md:150-190`).
  3. `BlockAssembler` is a **pure** fold, and one keep/drop decision covers content *and* metadata: a `max-tokens` finish drops every tool call, and the same decision prunes the replay envelope's per-block entry at each dropped position, so `blocks()` and `replayState` cannot disagree (`llm-streaming.md:380-420`).
  4. Replay state is adapter-owned but its *split* is shared vocabulary: "when assembly drops a block it drops the entry at the same position, so stored metadata always describes stored content" (`llm-streaming.md:230-250`).
- **Edge cases & failure handling:** every thrown or in-band failure normalizes to one serializable `LlmFailure`; the *same* type carries a thrown transport error and an in-band provider error. An **empty completion is a retryable error, not a silent success** (`EMPTY_RESPONSE`). Context overflow has **one canonical code** (`CONTEXT_WINDOW_EXCEEDED`) so consumers route on the code, never provider text (`llm-streaming.md:290-310`).
- **Surprising:** the adapter contract has **nine MUSTs** the page enumerates, including "one adapter call is one provider attempt" (adapters disable library retries) and "provider stalls are bounded at the transport" with a five-minute default idle timeout (`llm-streaming.md:290-330`).

### `docs/subsystems/tools.md`
- **Purpose:** `ToolDefinition` in full, the typed schema DSL, `ToolExecution`/`ToolResult`, the tool-presentation UI types, and the guarded execution pipeline.
- **Key abstractions:** `ToolDefinition` (schema + `execute` + optional `projectContent`/`finalizeContent`/`presentCall`/`presentResult`); the `defineTool` / `ValueSchemaSpec` / `ParameterSchemaSpec` DSL; `ToolExecution` / `ToolDispatchExecution` / `ToolExecutionResult`; `ToolGuard`; `PreToolDecision` / `PostToolDecision`; `ToolOutputDefinition`; `JsonSchemaNode`.
- **Data flow:** declaration → the registry indexes it per agent scope → `ctx.tools.execute()` materializes the parsed JSON arguments **once** → `tools/pre-execute` (allow/deny/cancel/ask waterfall) → registered **monotonic guards** → `tools/execute` (around-dispatch wrappers) → `projectContent` → `tools/post-execute` (inspect/replace/block) → optional `finalizeContent` → `tools/result` (the immutable authoritative outcome) (`tools.md:180-200`).
- **Non-obvious design decisions:**
  1. `ToolGuard` **deliberately has no allow result**: `undefined` preserves the waterfall decision and a returned reason can only reduce permission, so "listener ordering cannot turn a denial back into permission" (`tools.md:329-340`).
  2. `schemas()` builds the model-facing projection by an **explicit allowlist** — `output`/`execute`/`presentCall`/… "must never leak into a model request" (`tools.md:20-30`).
  3. Tool **arguments cannot be rewritten** by pre-policy: "arguments are already logged and presented", and "history, audit, UI, and execution must agree" (`tools.md:401-420`).
  4. Post-policy may replace content **or** value, never both; a `block` removes the value and becomes an `isError` carrying corrective feedback (`tools.md:422-435`).
  5. `isConcurrencySafe` is **fail-closed**: only an exact `true` opts in; omission, exceptions, non-`true` returns and invalid `defineTool` arguments are all exclusive (`tools.md:95-115`).
- **Edge cases & failure handling:** unknown and throwing tools both become structured errors (`UNKNOWN_TOOL`), so a failed call does not end the turn. Cancellation arriving after entry skips a not-yet-started body with `ABORTED_BEFORE_DISPATCH` or replaces a started success with `ABORTED`; already-started work is still drained (`tools.md:585-600`). The registry **re-fuses the original caller signal** before the body so a wrapper cannot detach caller cancellation (`tools.md:520-540`).
- **Surprising:** the model-facing presentation vocabulary is a **provider-neutral render-intent union** (`generic` / `terminal` / `diff` / `search` / `read` / `web`), each with an explicit fallback for a UI without that card — so "a UI never presents a partial result as complete" (`tools.md:490-520`).

### `docs/subsystems/compaction.md`
- **Purpose:** The compaction seam — how a long transcript is replaced by a summary without breaking the tool-call/result pairing.
- **Key abstractions:** `CompactionResult`; `CompactionTrigger` = `'pressure' | 'context-overflow'`; `ManualCompactionErrorCode`; `CompactionEngine` (`compactIfNeeded` / `compactNow` / `compactRegion`); `PruneResult` / `PrunedEntry`; `compactCheckpointSource()` / `isCompactCheckpointSource()`; `toolPairingBalancedBefore/After`.
- **Data flow:** pressure compaction runs at the `agent/pre-step` waterfall **before request derivation**; the tool-result pruner runs first, then the range is selected and re-measured through `ctx.tokenMeter`; the summary is written as a `user/message` carrying `surfaceOp: {op:'replace', startSeq, endSeq}`; `compaction/start` … `compaction/summary` … `compaction/end` bracket the whole operation in the log (`compaction.md:11-40`).
- **Non-obvious design decisions:**
  1. The summary rides on a **`user/message` with a surfaceOp**, not a new event type — `SurfaceEventType` is deliberately *not* extended, because only message-producing events reach the model (`compaction.md:13-18`).
  2. `shadowedRange` is a **surface-POSITION span, not a numeric seq interval** — after an earlier replace lands a fresh high-seq summary at an older position, `start` can be **greater than** `end`; `shadowedSeqs` is the authoritative set (`compaction.md:60-68`).
  3. The **lock is released last** (`compaction/end` after the replacement lands), so a crash mid-operation becomes a detectable orphaned lock rather than a false "compaction finished" (`compaction.md:19-22`).
  4. Region boundaries preserve tool-call/result *pairing* but not whole turns, so the early closed steps of one oversized turn can compact on their own.
- **Edge cases & failure handling:** `compactNow()` returns `null` without writing when no useful range exists; `changed` closes and persists the failed attempt without a summary replacement; `commit` may follow partial mutation; `persistence` means the in-memory bracket closed but its flush failed; cancellation throws the exact abort reason after required cleanup (`compaction.md:80-95`). A `compaction/summary-error` waterfall lets a listener recover a failed summary request by durably changing the selection — "return true only after making progress" (`compaction.md:430-450`).
- **Surprising:** the compaction seam **owns no pricing API** — the `ctx.tokenMeter` singleton owns estimation and replay, so compaction and measurement cannot drift (`compaction.md:74-78`).

### `docs/subsystems/approval.md`
- **Purpose:** The one-shot user-approval seam — the single place a consequential action is gated.
- **Key abstractions:** `ApprovalRequestId`; `ApprovalOutcome` = `'allowed-once' | 'rejected' | 'cancelled' | 'unavailable'`; `ApprovalPolicy` = `'ask' | 'never'`; `ApprovalRequest`.
- **Data flow:** `ctx.approval.request(req)` → appends `approval/asked` → dispatches the `approval/request` **waterfall** → the first answerer that returns an outcome claims the slot → appends `approval/decided` → resolves with the outcome. Consumers (`dsh-tools`, `dsh-tool-bash`) **fail closed** unless the outcome is exactly `allowed-once` (`approval.md:21-30`).
- **Non-obvious design decisions:**
  1. The request **deliberately omits tool arguments** — the answerer attaches the prompt to the already-streamed tool call via `callId`, so the rendered text and the logged call cannot drift (`approval.md:68-95`).
  2. `never` is enforced *inside the service before waterfall dispatch*, so even an answerer registered later with `prepend` cannot bypass it (`approval.md:100-105`).
  3. A missing, non-owning, throwing, or non-conforming answerer becomes `unavailable`, not `allowed-once` (`approval.md:118-125`).
  4. The audit events are **log-only** and never enter the model transcript; model-visible behaviour is the caller's derived tool result plus a runtime-context snapshot.
- **Edge cases & failure handling:** an idle ask rejects *before* appending anything (the audit pair must be enclosed by the log's commit/replay boundary). A rogue non-vocabulary return value is normalized to `unavailable`. A failure that prevents either audit append from committing still rejects — "returning an unlogged decision would violate the pair" (`approval.md:165-185`).
- **Surprising:** changing the policy appends a new *full snapshot* after retained history and **does not touch the `system/message` nodes** holding the rendered system prompt (`approval.md:56-58`).

### `docs/subsystems/schedule.md`
- **Purpose:** Host-wide reminder records — the harness's long-lived scheduled work (the closest thing in the shard to cron/automation).
- **Key abstractions:** `ScheduleId`; the record union `AfterScheduleRecord | AtScheduleRecord | EveryScheduleRecord | DailyScheduleRecord | WeeklyScheduleRecord | CronScheduleRecord`; `ScheduleView`; `ScheduleCatalogEntry`; `ScheduleDeliveryReceipt` / `ScheduleDeliveryRecord`; `ScheduleDeliveryHistoryResult`; `DeliveryRetentionBounds`; `ScheduleTimingChange`; the legacy `LegacyScheduleRecord` fold vocabulary.
- **Data flow:** the Host owns the record in a `schedule` storage domain (`tasks` table) → a durable transition is appended → the active/ended views are projections → delivery resolves the original Session (including a **cold** Session), restores it, re-samples the clock, and appends the reminder through `followup()` → after a successful Session flush, one task-record put writes the saved receipt.
- **Non-obvious design decisions:**
  1. **Catch-up is explicit and bounded**: "When the Host starts with an overdue Every, Daily, Weekly, or Cron record, it sends only the latest due occurrence… Missed occurrences do not accumulate." (`schedule.md:146-152`).
  2. Every stored record must carry a **`title`** (trimmed, non-empty, ≤120 chars); a record that fails decoding rejects the whole domain open rather than being silently dropped — "the schedule domain declares no backup-and-skip policy" (`schedule.md:13-20`).
  3. Only **canonical UTC** `scheduledAt` is stored, so replay never depends on ambient time-zone state; daily/weekly/cron keep the explicit IANA zone and the *committed* instant (`schedule.md:60-70`, `schedule.md:118-135`).
  4. The **cron dialect is exactly five Vixie fields**; `L`, `W`, `#`, month/day names, macros and six-field expressions are rejected with `invalid_rule` naming the offending field. Canonicalization expands each field into its matched value set and re-encodes it deterministically; the decoder rejects a non-canonical stored expression (`schedule.md:175-215`).
  5. Day-of-month/day-of-week follow Vixie semantics keyed on the field's **star flag**, "independently of the values it matches" (`schedule.md:200-210`).
- **Edge cases & failure handling:** a nonexistent local time is skipped; an ambiguous overlap takes the **earlier** instant once per local date; if that earlier instant has passed, the later duplicate is not eligible. A delivery failure leaves the task stored and warns; "a later management change or Host restart retries it." Delivery never steers or cancels the current turn and does not wait for model completion (`schedule.md:330-345`). Saved receipts are pruned on append to a day window and a record cap; "missing receipts are never reconstructed" (`schedule.md:300-330`).
- **Surprising:** delivery is **not atomic across stores** — "a crash after inbox persistence but before the task put can repeat delivery; the receipt does not close this gap" (`schedule.md:343-345`). And `Schedule` provides "no model-result acknowledgement, execution cancellation, or external notification channel."

### `docs/subsystems/jobs.md`
- **Purpose:** The background-job runtime — how the harness runs long work that is not a turn.
- **Key abstractions:** branded `JobId` (`<kind>-<short-uuid>`); `JobKindMap`; `JobStatus`; `JobSpec` / `JobHandle` / `JobHooks` / `JobOutcome`; `JobOutputSource` / `JobSourceRead`; `JobChunk` / `JobOutputRead` / `JobRead`; `JobView`; `JobEvent` / `JobEventFilter`.
- **Data flow:** a producer calls `start(spec)` → the runtime preflights access, validates and reserves the id → calls `run(job)` synchronously → the producer pushes into a bounded **output ring** (or exposes pull sources the registry pumps) → the model consumes the ring through a registry-kept cursor, observers read it at absolute byte offsets → settlement closes the ring and trims retention (`jobs.md:60-260`).
- **Non-obvious design decisions:**
  1. **Split cursors**: the model's consuming cursor and observers' absolute offsets read the same bytes "and never disturb each other" (`jobs.md:234-240`).
  2. The `log` channel carries producer narration that reaches observers **only**, never the model's consuming read (`jobs.md:230-240`).
  3. Settlement is **first-wins**: one terminal record, released waiters, then one round of contained event delivery "even against a late producer outcome"; the `settled` event reports whether it released a waiter (`awaited`), so a completion reporter can skip settlements a waiting caller already collected (`jobs.md:386-400`).
  4. `producerReported` "does not independently certify resource release" — a teardown-caused failure is reported honestly.
  5. `start` **refuses work while no attached job controller serves the spec's owner**, so a producer cannot start work that owner cannot collect or stop.
- **Edge cases & failure handling:** ring retention is bounded (`retainBytes` default 262144, `settledRetainBytes` default 16384); a reader below the retained window gets a **lossy** read, never an error. A pull source that slides its window reports `lossy` and the spill path. A throwing producer teardown force-fails only the registry record without claiming the work stopped (`jobs.md:395-410`).
- **Surprising:** a **missing `job/settled` remains incomplete** even if the live registry reported termination, and "consumers must not invent a finish timestamp" (`jobs.md:40-55`). Turn completion does not imply that every owned job stopped.

### `docs/subsystems/goal.md`
- **Purpose:** Persisted goal identity, lifecycle snapshots, activation, change records, and round attribution.
- **Key abstractions:** `GoalId`; `GoalRef` (id + `revision`); `GoalPhase` = `'active' | 'paused' | 'blocked' | 'complete'`; `GoalBlockReason`; `GoalSnapshot`; `GoalView`; `GoalActivationChanged`; `GoalSnapshotChangeMeta` / `GoalClearChangeMeta`; `GoalMessageSource`; `CreateGoalRequest` / `EditGoalRequest`; `GoalChanged`.
- **Data flow:** a goal is persisted with a lifecycle snapshot → every mutation is a durable `goal/change` event whose payload is either a **complete post-mutation snapshot** or a clear tombstone → the strict fold derives lifecycle state only from those events → a continuation consumer attributes each admitted user-message turn with a positive sequential round number and the current revision (`goal.md:40-130`).
- **Non-obvious design decisions:**
  1. **Durable phase and process-local activation are separate axes**: `GoalPhase` answers what happened to the objective; `activation` answers whether a continuation consumer may start another round, and is "never persisted" (`goal.md:30-40`, `goal.md:60-75`).
  2. **Compare-and-set on revision**: every accepted durable mutation increments `revision`; `edit`/`pause`/`resume`/`complete`/`block`/`clear` all require the expected current revision (`goal.md:200-280`).
  3. **Round budget is durable**: `maxGoalRounds` is part of the snapshot, and "only these admitted `user/message` events advance `roundsStarted`"; replay rejects non-positive rounds, gaps, stale revisions, stopped phases and cap overflow (`goal.md:50-56`, `goal.md:118-135`).
  4. `disarm()` removes *process-local continuation authority* "without changing durable goal phase or revision", so unloading a driver does not rewrite the goal (`goal.md:170-180`).
- **Edge cases & failure handling:** "A completed goal may be replaced; every other current phase must be cleared or resumed instead." The clear operation retains a **tombstone** whose revision is one past the cleared snapshot. The service "resolves creation defaults, reads strict replay from the optionally registered `goal` projection" and "its first dependent access fails if the projection registry or key is absent" (`goal.md:160-175`).
- **Surprising:** `GoalBlockReason` splits a **stable machine-routable code** from a free-form human/model explanation — the blocked reason is a first-class durable artifact, not a string in a log line (`goal.md:42-50`).

### `docs/subsystems/feedback.md`
- **Purpose:** Lifecycle-bound per-message feedback records, optimistic versions, sidecar persistence, and the Host Remote contract.
- **Key abstractions:** `MessageFeedbackVersion` (a branded CAS token); `MessageFeedbackRating`; `MessageFeedbackItem`; `MessageFeedbackPut` / `MessageFeedbackDelete`; the `MessageFeedbackFailure` code union (`session-not-found`, `target-not-found`, `version-conflict`, `note-blank`, `note-too-large`); `FeedbackCategory` (seven durable ids); `FeedbackRecord`; `SessionFeedbackRecordRequest`.
- **Data flow:** feedback is folded from canonical `feedback/message-put` / `feedback/message-delete` events whose payload `sessionId` matches the owning Session → the current item set is a fold, not a store → the Host Remote exposes `list` / `put` / `delete` (`feedback.md:1-10`, `feedback.md:230-290`).
- **Non-obvious design decisions:**
  1. **Strict optimistic concurrency**: "every request for an existing item must match its current `ifVersion`, including a no-op (a put repeating the stored rating, note, and category)"; a conflict returns the **authoritative current item**, so a caller reconciles from the reply instead of refetching (`feedback.md:279-285`).
  2. A **matching no-op appends no event** — the log stays minimal (`feedback.md:285`).
  3. Feedback is **log-only and never enters model context**; it is also not an LLM request — "recording feedback does not trigger an LLM request or a separate `dsh_feedback` upload" (`feedback.md:1-5`, `feedback.md:300-320`).
  4. The `category` vocabulary is **durable log vocabulary**, fixed at seven ids (`feedback.md:150-165`).
- **Edge cases & failure handling:** deleting an absent item **succeeds** (idempotent). A per-Session queue serializes reads and mutations; cold mutations hold a persistence write handle across read, comparison, append and flush. "Persistence failures propagate rather than reporting success." Fork seeds can contain parent feedback events, but their payload retains the parent `sessionId`, so they do not become current feedback for the child (`feedback.md:275-300`).
- **Surprising:** the doc keeps an explicit **"Boundaries and limitations"** list — the queue is process-local, there is no item-count or aggregate-byte cap, the Host records no authenticated actor, the trajectory view renders no feedback entry although its nodes carry the same `messageId`, and the dialog does not pre-check `maxNoteBytes` (`feedback.md:355-380`).

### `docs/subsystems/persistence.md`
- **Purpose:** The durability seam — `SessionPersistence`, the JSONL provider, the `session/flush` checkpoint, crash recovery, and `SessionHeader`.
- **Key abstractions:** `SessionHandle` (`read`/`append`/`flush`/`close`); `SessionHandleReadResult`; `SessionHeader`; `SessionLocation`; `SessionPersistenceRevision`; `SessionPersistenceSnapshot`; `CreateSessionOptions`; `RestoredSessionOptions` / `SessionSeedEventState`; `SessionPreparation`.
- **Data flow:** `session/event` (a *synchronous* notification) is routed by session id into the active write handle's bounded **write-behind** window → the first pending event starts a fixed batching window → expiry starts one durable `append` → `session/flush` cancels the wait and drains through quiescence → a crash leaves a torn physical tail that the write path truncates before its first new append (`persistence.md:60-115`).
- **Non-obvious design decisions:**
  1. **The handle is the single door** for log access and the cross-process write lease; a mutation on a read handle is a runtime `SessionReadOnlyError` rather than a typed split, and a second `open(id,'write')` rejects while an owner is active (`persistence.md:20-40`).
  2. `append` is **best-effort**; only a resolved `flush` promises durability — "on resolution every acknowledged append is durable and the session is materialized for other processes" (`persistence.md:65-100`).
  3. **Crash recovery preserves the interrupted turn**: persistence does *not* truncate or repair it — "a single turn can be huge in a long-horizon task… and those events were durably appended before the crash". Repair is the *reader's* job (`agent-loop` computes `interruptedTurnClosers` and appends them) (`persistence.md:108-125`).
  4. The shipped provider stores each log as **checksummed concatenated Zstandard frames** by default, or raw lines by configuration, with per-batch `fsync` appends and torn-tail truncation (`persistence.md:300-312`).
  5. `SessionPersistenceRevision` is a cheap **opaque change token**; "equal revisions may be treated as an unchanged log; unequal revisions promise nothing", and write-ownership churn never changes one (`persistence.md:245-275`).
- **Edge cases & failure handling:** a backend **refuses** a log it cannot faithfully interpret with `SessionFormatUnsupportedError`, distinct from corruption because "nothing is damaged"; a future highest generation refuses even when an older readable generation remains. Read-only observers (session-query) balance an interrupted cold log with the same closers **in memory only**, writing nothing back (`persistence.md:170-200`, `persistence.md:120-130`).
- **Surprising:** `SessionLocation` is "not a consumer-facing query" — it survives **only** as refusal diagnostics so a user can find the raw log a build refused to interpret (`persistence.md:100-115`).

### `docs/subsystems/skills.md`
- **Purpose:** The skill service — discovery priority, `SkillSummary`/`SkillDefinition`, the session-prefix catalog, and model-facing `skill` loading.
- **Key abstractions:** `SkillProvider` / `SkillProviderObservation` / `SkillProviderControl`; `SkillSource`; `SkillInvocationPolicy`; `SkillSummary`; `SkillCandidate`; `SkillDefinition`; `SkillResourceBase`; `SkillCatalogSnapshot`; `SkillRegistration`; `SkillLookupOptions` / `SkillViewOptions`.
- **Data flow:** providers register **synchronously** during `apply()`; remote discovery is awaited inside `list()` → the registry merges the global layer with the viewing scope's chain (nearest layer wins a duplicate name outright; rank decides duplicates only *within* one layer) → a sorted invocation-neutral catalog is published → the consumer injects a durable `<system-reminder>` catalog and the model loads a skill on demand (`skills.md:1-70`).
- **Non-obvious design decisions:**
  1. **Discovery priority is an explicit numbered table** — `project-dsh` (100) < `project-agents` (200) < `custom` (300) < `user-dsh` (400) < `user-agents` (500) < `bundled` (600) (`skills.md:66-76`).
  2. The registry is **host + per-scope layered**: "provider names are unique per layer rather than process-wide", and discovery caches are keyed by the resolved scope chain so re-parenting a scope is visible without a registry mutation (`skills.md:26-36`).
  3. **Invocation policy is two independent booleans** (`modelInvocable`, `userInvocable`); both false keeps the skill available only through trusted `ctx.skills.get()` callers. The frontmatter keys are exactly `disable-model-invocation` and `user-invocable` (`skills.md:95-140`).
  4. `SkillCatalogSnapshot.complete` distinguishes **authoritative absence** from transient provider failure; incomplete snapshots are **not cached**, so each consumer keeps its last-good catalog (`skills.md:145-165`).
  5. The model-facing catalog contains **only** sorted name and normalized XML-escaped description — "it omits bodies, paths, sources, providers, and routing hints"; the catalog is a digest-compared **replacement**, not an append (`skills.md:195-215`).
- **Edge cases & failure handling:** "Full definitions are not cached by the registry" — each `get()` rereads the current body, and a definition whose name no longer matches its candidate is rejected and invalidates the exact provider for rediscovery. The model tool "rejects it before loading unless `isModelInvocable` permits access, then rereads the complete definition … and rechecks the policy before returning content" (`skills.md:170-195`).
- **Surprising:** the model-facing catalog is a **durable user-role message** that is *replaced* when the digest changes and "deleting every skill appends an explicit empty replacement" — and "these catalog messages are session history, not World State" (`skills.md:200-220`).

### `docs/subsystems/agent-team.md`
- **Purpose:** Agent Teams — an implicit Lead identity, named continuable teammates, direct peer inbox delivery, and a shared task DAG.
- **Key abstractions:** `TeamId` (the root `SessionId` under a distinct brand); `TeamTaskId` (`task-<n>`); `TeamMemberSnapshot`; `TeamTaskSnapshot`; `TeamMessageSnapshot`; `TeamMessageSource`; `TeamMemberProjection`; `TeamTaskView`; `TeamProjection`.
- **Data flow:** the Lead spawns named teammates (each a real Session) → peers `sendMessage()` into each other's inbox → every task mutation appends a **complete snapshot** with `revision + 1` → the Lead Session publishes `SessionProjectionMap.agentTeam` for the browser (`agent-team.md:20-110`).
- **Non-obvious design decisions:**
  1. **Every task event stores a complete snapshot**, and `revision` is the compare-and-set value — no delta log to replay (`agent-team.md:58`).
  2. `blockedBy` edges must name non-deleted tasks and keep the graph acyclic; `writeScopes` are **normalized advisory path prefixes, not locks** — the harness refuses to pretend it has file locking (`agent-team.md:58-60`).
  3. Roster `running`/`inactive` status is **derived separately** and never rewrites the durable lifecycle record (`provisioning` → `active` | `failed`).
  4. Team has **no new-message outbox or resend deduplication** — a send returns inbox acceptance or rejects.
- **Edge cases & failure handling:** `failure` in the projection "names the first rejected persisted Team record; members and tasks then stay at the last valid state" — a corrupt record degrades the view rather than the roster. Deleted tasks are retained as tombstones. Events inherited by an ordinary fork retain the ancestor `TeamId` and never enter the new root's state (`agent-team.md:96-110`).
- **Surprising:** teammate **names are immutable labels**, and `interrupt()` "without clearing its pending inbox" — the pending message survives the interrupt (`agent-team.md:196-210`).

### `docs/subsystems/subagent.md`
- **Purpose:** The subagent seam — how a model starts a *named* child agent, and the **start-time-vs-runtime capability split**.
- **Key abstractions:** `SubagentCapabilities` (`agentOptions`, `agentPreset`, `outputSchema`, `depthLimit`); `SubagentActivationSpec`; `SubagentActivation`; `SubagentStartRequest` / `ResolvedSubagentStartRequest`; `ContinuableCreateRequest` / `ContinuableCreateSpec`; `AgentMessageSource`; `SubagentSettledMessageSource`; `SubagentInterruptAuthority`; `SubagentResult` / `SubagentStopReasonMap`; `SubagentRun`; `SubagentProvider`; `SubagentDescendantListEntry`.
- **Data flow:** a caller resolves a named provider → the manager validates every requested **start-time capability** → `prepareContinuable` selects local Agent creation, `start` selects one external execution → the activation owns a result promise and a `dispose()` → the settlement notice returns to the parent (`subagent.md:1-120`).
- **Non-obvious design decisions:**
  1. The **start-time capability flags** are the contract: "The manager checks every requested option before preparing a local child or starting an external execution" (`subagent.md:9`, `subagent.md:20-40`).
  2. `ContinuableCreateSpec` is **DATA, never a capability** — it carries no Agent, handle, prompt delivery, result, disposal or resume operation, "because the continuation manager owns the child's whole lifecycle after preparation" (`subagent.md:120-145`).
  3. `SubagentSettledMessageSource` is deliberately a **different kind** from `AgentMessageSource`: "an Agent message is content the sender chose, while this message is the manager stating what became of the child, and a transcript that merged them would credit the child with words it never wrote" (`subagent.md:170-190`).
  4. `maxDepth` is an **absolute delegation-depth cap** persisted in the Session header, "so a recursion budget survives restart and resume" (`subagent.md:110-120`, `persistence.md:150-175`).
- **Edge cases & failure handling:** a `SubagentRun.result` **does not reject on a child-level failure** — a model/transport failure resolves with `stopReason: 'error'` so the consumer maps it to an `isError` tool result; it rejects only on an infrastructure fault the seam cannot represent (`subagent.md:230-250`). A cleanup failure does not replace a captured result: "the activation result and parent notice retain it, while dispose rejects".
- **Surprising:** `inheritsParentContext` is **descriptive, not service-validated**: "It says nothing about tool registration, injected services, or authority inheritance" (`subagent.md:270-285`).

### `docs/subsystems/storage.md`
- **Purpose:** The storage subsystem — the `StorageBackend` contract, `StorageForms`, `DomainSpec`/`Domain`, and the `domain/changed` event.
- **Key abstractions:** `StorageBackend` / `KvFacet` / `KvUnit`; `StorageForms`; `DomainSpec` / `Domain` / `KvTable`; `DomainChangedBase` / `DomainChanged`; `DomainFacility`.
- **Data flow:** a domain is declared once by its owning package as a `DomainSpec` (zod schemas, so `z.infer` keeps consumer types un-duplicated) → `ctx.storageDomain.open(spec)` resolves the backend route, opens the unit and validates every stored record → writes queue on one per-domain chain, reach backend durability first, then mutate memory, then emit `domain/changed` (`storage.md:60-140`).
- **Non-obvious design decisions:**
  1. **The hub performs no IO itself**: backends own media, data forms own semantics, and "product packages never touch backends directly". Which backend serves which consumer is the *domain layer's* route table, never a hub-global choice (`storage.md:10-30`).
  2. `DomainSpec.invalidRecords: 'backup-and-skip'` is a **declared, per-domain** policy: "the default, the whole open rejects with `invalid-record` — right for authoritative data" (`storage.md:85-100`).
  3. A domain's `layout` may be `single` (one document) or `per-record` (one document per record, "for units whose records are large, sparse, or individually disposable — the projection cache") (`storage.md:70-85`).
  4. `update(key, fn)` is an **atomic read-modify-write at its chain slot** (`storage.md:120-130`).
- **Edge cases & failure handling:** "a rejected backend write leaves memory untouched, so reads never diverge from the medium". Returned records are the stored objects themselves, not copies — "replace via `put`/`update`, never mutate in place". A `domain/changed` listener that throws is **contained with a logged warning** rather than rejecting the already-durable write (`storage.md:126-140`).
- **Surprising:** the change event is **in-process only**; cross-process change push is a recorded limitation (`storage.md:140`).

### `docs/subsystems/token-meter.md`
- **Purpose:** Immutable scalar and positional replay measurements with consumed-log revisions.
- **Key abstractions:** `TokenMeasurement` (`logRevision`, `baseline`, `surfaceDeltaTokens`, `totalTokens`, `surfaceTokens`, `nodes`); `TokenSurfaceNode` (`seq`, `tokens`, `heuristicTokens`).
- **Data flow:** the durable log tail is replayed → the effective envelope's routed provider/model selects the request-image pricing → provider usage is reused only when the latest successful call's canonical request envelope matches and its total is no lower than that call's route-priced anchor; otherwise the complete envelope and surface are repriced → a detached, deeply immutable snapshot is returned (`token-meter.md:1-40`).
- **Non-obvious design decisions:**
  1. **Two prices per node**: `tokens` is the route-priced price (the route's declared image visual price when it has one), and `heuristicTokens` is a fixed route-independent heuristic. "The shadow-price protocol prices replacements with this value so the O(1) projection fold stays in agreement with its own appends" (`token-meter.md:30-50`).
  2. `logRevision` is "the number of durable events consumed for every field in the measurement", so a measurement is comparable against a log position (`token-meter.md:5`).
  3. `surfaceDeltaTokens` is **signed** and preserves growth *and* shrinkage relative to a matching anchor, repricing both sides under the same route.
- **Edge cases & failure handling:** "Surface order is authoritative; replacement nodes can have higher durable seqs than later positional nodes" — so the snapshot's `nodes` array is positional, not seq-ordered (`token-meter.md:52`). "The snapshot is immutable and does not grow when the underlying replay fold advances."
- **Surprising:** `totalTokens` (request-and-response pressure) and `surfaceTokens` (surface-only route-priced total) are **different numbers**, and the doc is careful to say which is which.

### `docs/subsystems/client-resources.md`
- **Purpose:** The `dsh-resource://<type>/…` address model — one provider per protocol, the `useResource` global hook, the four states, and hold-and-release.
- **Key abstractions:** `ResourceProtocolMap`; `ResourceProvider` (`open(address, {signal})` → `AsyncIterable<RemoteResult>`); `useResource<P>(address)`; `ctx.resources.register` / `.pin` / `.source`.
- **Data flow:** a component calls `useResource(address)` → the first holder opens the provider's stream (the current state first, then one frame per change) → later holders share it and read the latest value at once → the last release aborts the stream, discards the value and returns the snapshot to `loading`/`none` (`client-resources.md:1-80`).
- **Non-obvious design decisions:**
  1. **One scheme, many hosts**: "one scheme serves every protocol, so adding a protocol adds a host, never a scheme". The model reads only the scheme and the host (`client-resources.md:20-40`).
  2. **A protocol has exactly one provider**; a second registration throws. Registering while addresses are already held opens their streams at once (`client-resources.md:60-70`).
  3. The four states are `none` / `loading` / `live` / `failed`, and in `failed` the model **keeps the last value beside the failure**, so a body can show stale content with a notice rather than a blank (`client-resources.md:55-70`).
  4. The address string is the **content identity** — `DSH-RESOURCE://File/session/s1/a` is "a distinct record" because addresses compare as strings, and `openResource` accepts only the canonical lower-case spelling (`client-resources.md:30-45`).
- **Edge cases & failure handling:** a throw inside the provider's stream is a programming error and is **not caught**. A misspelled protocol or a malformed address reads as `none` with no other diagnostic. A provider that ignores `signal` keeps running until its next frame (`client-resources.md:80-95`).
- **Surprising:** "Nothing in the model produces user-visible text" — the model is a data channel; the consumer presents `failed` itself (`client-resources.md:70-75`).

### `docs/subsystems/session-projection.md`
- **Purpose:** The projection seam — `SessionProjectionMap`, the pure `ProjectionDefinition` unit, `ProjectionSnapshot`'s consistent cut, and the change feed.
- **Key abstractions:** `ProjectionDefinition` (`stateSchema`, `init`, `apply`, optional `wire`, `stateVersion`); `ProjectionSnapshot` (`asOfSeq`, `values`); `ProjectionChangeListener`; `ProjectionCheckpoint`.
- **Data flow:** the registry subscribes to `session/event` **once** → every committed event passes every registered unit's `apply` (an "eager drive") → a changed state reference computes the next client view → the change feed fires only when the raw result changes by `Object.is` → `snapshot()` reads a watermark cache, materializing cells lazily over the in-memory log (`session-projection.md:1-110`).
- **Non-obvious design decisions:**
  1. A unit's functions **MUST be synchronous** — "an async unit would tear the carriers' consistency cut" — and `state` **MUST be plain JSON** (the persisted-cache precondition) (`session-projection.md:30-45`).
  2. `apply` **MUST return the same state reference** when the event is not the unit's; an unchanged reference (`Object.is`) produces zero downstream work (`session-projection.md:45-60`).
  3. `stateVersion` is a **persisted-cache invalidation version**: bump it whenever the serialized state fields or the fold semantics change, "so persisted `(sessionId, key, ver, seq, val)` rows from an older unit are discarded instead of being forward-applied into garbage" (`session-projection.md:60-70`).
  4. `restoreFloor` uses a **one-below anchor** that is "load-bearing": the tail then proves how far the stored log still extends, so a crash-repair truncation that shrank the log below a row's watermark is detected instead of served as current (`session-projection.md:290-320`).
- **Edge cases & failure handling:** "The framework drives, the domain computes": domains hold no subscriptions and clients never fold domain events. A duplicate key with a different `stateVersion` throws, while same-version registrants share one unit and are counted. A discarded row with `baseSeq > 0` **throws** (the caller re-reads from seq 0) (`session-projection.md:100-130`, `session-projection.md:320-350`).
- **Surprising:** the Agent Teams projection (§ `agent-team.md`) is a *consumer* of this seam, not a special case — a team roster is just a projection over the log.

## 5. Ideas worth stealing

1. **Fail-closed approval with a closed outcome vocabulary and a mandatory audit pair.** `ApprovalOutcome` is `'allowed-once' | 'rejected' | 'cancelled' | 'unavailable'` and every non-grant denies; a missing/throwing/non-conforming answerer becomes `unavailable` rather than opening the gate; the `approval/asked` + `approval/decided` pair is appended *before* the outcome is returned, so "returning an unlogged decision would violate the pair" (`docs/subsystems/approval.md:21-30`, `docs/subsystems/approval.md:165-185`). *CONVERGENT-shaped and directly stealable for August Trading's approval/plan-review paths.* **UNIQUE to this repo's shape, but the mechanism is portable.**
2. **Monotonic guards: a denial can be tightened but never loosened by listener order.** `ToolGuard` returns `string | undefined` and has **no allow result**, so "listener ordering cannot turn a denial back into permission" (`docs/subsystems/tools.md:329-340`). August Trading's risk/validation gate could adopt the same shape to make rule precedence order-independent. **UNIQUE here; highly portable.**
3. **Compare-and-set revisions on every durable mutation, with the whole snapshot stored.** Team tasks store a *complete* snapshot per event and a `revision` that is the CAS value (`docs/subsystems/agent-team.md:58`); goals do the same (`docs/subsystems/goal.md:44-56`); message feedback uses an opaque `ifVersion` token and returns the authoritative current item on conflict (`docs/subsystems/feedback.md:279-285`); schedule edits compare the *complete observed record* and answer `schedule_conflict` rather than overwriting (`docs/subsystems/schedule.md:275-285`). August Trading's trade journal and skill state could use one shared CAS-revision helper. **CONVERGENT within this repo — strong signal.**
4. **Catch-up is bounded: a missed run delivers the *latest* due occurrence and missed occurrences do not accumulate.** (`docs/subsystems/schedule.md:146-152`). This is exactly the breaker/catch-up rule August Trading's automation needs, stated as one sentence. **UNIQUE here but the rule itself is the steal.**
5. **The log is the single source of truth; the UI history is a *projection* with a surface-op algebra.** `deriveMessages()` is a pure, cached, frozen function of the append-only event log, and a message may *replace* a range of surface nodes via `surfaceOp: {op:'replace', startSeq, endSeq}` without deleting history (`docs/subsystems/session.md:30-190`, `docs/subsystems/session.md:666-690`). A trade journal could adopt the same "append-only events + a replace op" shape so a corrected trade is a new event, not an edit. **CONVERGENT and very transferable.**
6. **Two independent prices per node: a route-priced price and a fixed heuristic price.** `TokenSurfaceNode` carries both `tokens` (route-priced) and `heuristicTokens` (fixed), and the shadow-price protocol uses the heuristic so the O(1) projection fold "stays in agreement with its own appends" (`docs/subsystems/token-meter.md:30-50`). August Trading's context-budget/pruning code could price each stored artifact the same way. **UNIQUE here.**
7. **Everything is a `…Map → derived-union` extended by declaration merging.** `ContentBlockMap`, `MessageSourceMap`, `FinishReasonMap`, `TurnEndReasonMap`, `SessionEventMap` — a plugin adds a variant with **no edit to the owning package** (`docs/subsystems/core.md:364-398`). August Trading could adopt this for its tool-result kinds and provider error codes. **CONVERGENT (pi and hermes-agent do the same kind of map-union extension).**
8. **Branded ids everywhere, so a `SessionId` cannot be passed where a `ToolCallId` is expected.** `Branded<B>` + `brandString<T>()` (`docs/subsystems/core.md:399-405`). Cheap, high-value, and August Trading already has a `MessageId`/`TradeId` vocabulary that could be branded. **CONVERGENT.**
9. **A cap that refuses to lie about what it enforces.** `SandboxEnforcement` is `'full' | 'partial'` and the doc insists a consumer needing the absolute promise "must not treat it as `full`" (`docs/subsystems/sandbox.md:60-75`); the same honesty appears in the job ring (`lossy`, never an error), the feedback API (`earlierRecordsUnavailable`), the projection cache (`asOfSeq` is the *lowest* watermark) and the session query (`SESSION_QUERY_STALE_CURSOR`). August Trading's automation could adopt an explicit "partial/unknown" state instead of silently reporting success. **UNIQUE in this repo's wording, CONVERGENT in spirit.**
10. **Split cursors over one durable stream: a consuming cursor for the model and absolute-offset cursors for observers.** The job ring, the subprocess output reader and the shell process all implement this (`docs/subsystems/jobs.md:234-240`, `docs/subsystems/subprocess.md:230-260`) — "independent readers never consume one another's output". August Trading's live trade feed could use the same split. **CONVERGENT within this repo.**
11. **The tool-result spill: keep the full text on disk, give the model a locator and a retrieval hint.** `SpillRef` = opaque locator + exact byte count + `retrievalHint`; the policy replaces an over-budget result with head/tail plus the locator, and a save failure **keeps the inline result** rather than turning a successful call into an error (`docs/subsystems/spill.md:11-25`, `docs/subsystems/spill.md:90-100`). Directly applicable to August Trading's large market-data payloads. **CONVERGENT-shaped.**
12. **A persisted "what changed" feed that is a notification, not a transaction participant.** `domain/changed` is emitted *strictly after* the backend acknowledged durability, carries the **new** value (never the old), and a throwing listener is contained so it cannot reject an already-durable write (`docs/subsystems/storage.md:132-145`). August Trading's UI could consume a trade-journal change feed with the same post-commit ordering guarantee. **UNIQUE here.**
13. **A per-session "current value" projection with a `stateVersion` that invalidates persisted rows.** Bump `stateVersion` when the fold semantics change, so stale cached rows are discarded "instead of being forward-applied into garbage" (`docs/subsystems/session-projection.md:60-70`). **UNIQUE here.**
14. **A redact waterfall that ships no rules of its own.** `session-telemetry/record` transforms the outbound copy; with no listener mounted records reach the backend exactly as captured, so "exported data is exactly as clean as the rules a deployment mounts" — and a throwing listener withholds that one record fail-closed, never reaching the agent loop (`docs/subsystems/session-telemetry.md:142-160`). A clean privacy seam for August Trading's telemetry. **UNIQUE here.**
15. **A "not built" section in every design doc.** `sidebar-right.md` enumerates what was deliberately left out (no layout persistence, no `find`, no undo); `conversation.md` ends with eight **verification obligations**; `web.md` enumerates unsupported MCP-adjacent features. *Minimalism as a documented artifact.* **CONVERGENT (hermes-agent's design notes do the same).**
16. **The bilingual pairing is machine-checked by hashing each heading section's prose.** Each `*.i18n.yaml` records an EN and ZH hash per heading section, so "after editing either side, bring the other along and re-record". The *idea* — a per-section digest that proves the two locales have not drifted — is transferable to any two-surface documentation. **UNIQUE here.**

## 6. Trading-specific findings

- **Long-lived monitoring & scheduled work:** `docs/subsystems/schedule.md` is the whole answer. Durable reminder records live in a storage domain **independent of Session activation**; the Host reads persisted tasks at startup and sets its timer to the earliest active target; delivery resolves the original Session **including a cold Session**, restores it, re-samples the clock, and excludes members no longer due after a rollback; recurring tasks due in the same scan share **one** follow-up; a failure to resolve/enqueue/confirm leaves the task stored and warns so a later change or a restart retries it (`schedule.md:330-345`). The catch-up rule is explicit and bounded — "it sends only the latest due occurrence… Missed occurrences do not accumulate" (`schedule.md:146-152`). The idempotency boundary is stated honestly: "a crash after inbox persistence but before the task put can repeat delivery; the receipt does not close this gap" (`schedule.md:343-345`), and the saved-receipt ledger with a day window + record cap is what makes a repeat *visible* rather than silent (`schedule.md:300-330`). **No separate "automation" surface** — a reminder enters the ordinary conversation.
- **Human-in-the-loop approval:** two seams. `approval.md` is the *machine* gate (one-shot, fail-closed, audit pair, per-session `ask`/`never` policy, `never` enforced before the waterfall so no late answerer can bypass it). `user-questions.md` is the *human* gate (structured questions with stable ids, a `plan-review` intent that changes presentation only, a **timed** variant whose timeout returns `{pending:true, callId}` — explicitly "not an empty answer, a refusal, a confirmation, or permission" — and late replies folded into the projection so the transcript can show what the user finally chose). `permission-presets.md` bundles sandbox + approval into one named selector with a **derived** `custom` state. `plan.md` adds a third: plan mode is *soft guidance* enforced by nothing, and the `exit_plan_mode` review arc is what actually gates it.
- **Post-mortem / reflection loops:** **not in this shard as a loop** — but the *primitives* are all here and are precisely what a reflection loop needs: durable `goal/change` snapshots with compare-and-set revisions and a **durable round cap** (`goal.md:44-56`, `goal.md:118-135`); per-message feedback with optimistic versions and a seven-id category taxonomy (`feedback.md:150-165`, `feedback.md:279-285`); `session-title` snapshots that cite the exact source-message seqs a title was derived from (`session-title.md:35-50`); and the `session-telemetry` ledger that mirrors the log one-to-one with a dedupe key `(session.id, session.format_version, event.seq)`. What is *absent* is the retention/retirement half — nothing in this shard stops a rule from accumulating, so August Trading must design that itself.
- **Multi-agent:** this repo has **no debate engine**. Three distinct multi-agent shapes instead: **subagents** (a named provider registry with start-time capability flags and a delegation-depth cap; a child cannot gain a capability it was not started with — `subagent.md:20-40`, `subagent.md:110-120`); **Agent Teams** (named peers with a shared task DAG, CAS revisions, and advisory write scopes that are explicitly *not* locks — `agent-team.md:58-60`); and **workflows** (a model-written script that starts children, where a `parallel()`/`pipeline()` **re-throws** fatal misuse instead of mapping it to `null` — `workflow.md:75-90`). The verdict implied by the whole shard: *value comes from delegation and durable task state, not from two opinions and a reconciliation step.* That is a direct answer to "where does debate add value over one agent" — here, nowhere.
- **Structured logs the model can query:** the durable log is **JSONL** (checksummed Zstandard frames by default) with one row per event, `seq` contiguous from 0 (`persistence.md:300-312`). On top of it, `session-query.md` provides a **live-preferred logical corpus**: bounded exact-event reads, lineage traces with a closed completeness discriminant, provider-independent filters, and cursor-paginated full-text search with snippets — with a separate SQLite provider owning only the full-text index lifecycle (`session-query.md:1-5`). `storage.md` provides a second tier: typed KV *domains* with zod-validated records, per-domain invalid-record policy, and a `domain/changed` feed (`storage.md:60-145`). So: **a plain append-only file is the source of truth; a derived index makes it queryable; both are file-based.** No heavy database is required for the log itself.
- **Staying simple as features accumulate:** the shard's central discipline is the **capability seam** — an abstract service (`ctx.X`), one or more providers, and consumers. `compaction.md`, `lsp.md`, `web.md`, `ptc-runtime.md`, `filesystem.md`, `sandbox.md`, `storage.md`, `office-to-pdf.md`, `persistence.md` all open with the same paragraph: "one optional capability, not part of the agent-loop spine". A capability can be absent, and the rest of the harness still works. Second lever: **the merge-extensible map** — a new content block, a new finish reason, a new turn-end reason, a new event type is added by declaration merging, never by editing the owning package. Third lever: **the "Not built" lists**. Fourth: the docs themselves are *generated and drift-checked* — `verify-type-equiv` proves the type blocks are source-equivalent, and `verify-cordis-catalog` proves the API sections are fresh (`README.md:60-62`).

## 7. Non-obvious decisions and gotchas

- **A "surface" is a separate projection from the log.** `surfaceOp` describes how an event *joins the ordered visible surface*; `sourceEventSeqs` names the earlier events it derives from. The compiler **requires** `surfaceOp` on every message-producing event and **forbids** it on every log-only event (`session.md:240-300`). A reader who assumes "append = append" will misread compaction and checkpointing.
- **`shadowedRange` is a positional span, not a numeric interval.** After an earlier replace, `start` can be **greater** than `end`; the authoritative set is `shadowedSeqs` (`compaction.md:60-68`). Numeric reasoning about compaction is a bug.
- **The compaction lock is released last.** `compaction/start` … `compaction/end` bracket the whole operation so a crash leaves a *detectable orphaned lock* rather than a false "finished" (`compaction.md:19-22`). But the markers are "lock time points, not an exclusive container" — an unrelated idle injection can appear between them (`compaction.md:19-24`).
- **`session/end-seed` exists only to disambiguate seed history from live work.** Only the `Session` constructor and `buildForkSeed` may create it; a plugin appending one "would silently classify every live bracket before it as seed history" (`session.md:790-830`).
- **A `switch` over `SessionEvent` must NOT use `assertNever`.** `SessionEventMap` is merge-extensible, so a plugin-added variant is a legitimate unknown value (`session.md:492`). Every *other* closed union in the harness does use `assertNever` (`StreamChunk`, `LspQueryResult`, `WebFetchBody`, `FinishReason`) — the exception is deliberate and easy to trip over.
- **`agent/created` is a *serial* dispatch**: a throwing listener fails creation and **skips later listeners**; a returned-promise rejection is logged but cannot retroactively veto the synchronous boundary (`core.md:640-656`).
- **The exact disposer identity is load-bearing.** `ctx.agents.register()` must be yielded *by identity* into a composite effect; "yielding a wrapper would leave it disposing as a concurrent sibling on owner unload, unregistering the agent (and emitting `agent/disposed`) while its final turn is still draining" (`core.md:690-712`). The same rule appears for `ctx.sessions.enter()`.
- **Approval is enforced *before* the waterfall, not inside it.** `never` is checked inside the service, so an answerer registered later with `prepend` cannot bypass it (`approval.md:100-105`).
- **An approval request omits the tool arguments on purpose.** The answerer attaches to the already-streamed call via `callId` "instead of rendering a second copy that could drift" (`approval.md:68-80`).
- **`fs/observed` listeners MUST be synchronous.** The tool does not guard the emit, so a throwing listener "can replace a read error or surface as the tool's `isError` result after a mutation already succeeded" (`filesystem.md:95-115`).
- **`tools/pre-execute` cannot rewrite arguments** — "arguments are already logged and presented" (`tools.md:401-420`). A hook that wants to rewrite must be a `tools/execute` wrapper, which may only change the signal.
- **A wrapper cannot detach caller cancellation.** The registry "re-fuses the original caller signal before the body" (`tools.md:520-540`).
- **The fs seam deliberately has NO timeout.** "A local syscall is best-effort-abortable at most — a timeout could not force an in-progress `fsync`/`rename` to stop, so a `timeoutMs` here would be a deadline the seam cannot enforce" (`filesystem.md:200-215`). This is the repo's "explicit > implicit" rule applied where an implicit default would lie.
- **The shell's timeout and abort are mutually exclusive by first cause.** "one fused deadline drives both the timeout and the caller's cancellation, so a timeout and an abort racing before process close report the single first-abort cause, not both" (`shell.md:130-160`).
- **`SubprocessOutcome` carries no cause classification.** "Deliberately carries NO timeout or cancellation classification (the caller reads the signal it owns to classify causes)" (`subprocess.md:280-300`).
- **The schedule's cron dialect is strict five-field Vixie.** `L`, `W`, `#`, `JAN`/`MON`, `@daily` macros and six-field expressions are all rejected. Canonicalization expands each field to its value set and re-encodes it, so two differently-spelled equivalent expressions are a **no-op** (`updated:false`) rather than a rewrite (`schedule.md:175-215`, `schedule.md:300-315`).
- **A schedule record must carry a `title`; a bad one rejects the whole domain open.** "the schedule domain declares no backup-and-skip policy, so one such stored task rejects the whole domain open instead of being dropped" (`schedule.md:13-20`). This is the opposite of the storage domain's default and is a deliberate contrast.
- **A job's `settled` event says whether it released a waiter (`awaited`).** A completion reporter must "report only the unawaited ones" (`jobs.md:400-415`). Without this, every completion is reported twice.
- **A missing `job/settled` stays incomplete.** "consumers must not invent a finish timestamp" (`jobs.md:45-55`).
- **Web fetch: a non-2xx response is a *result*, not an error** (`web.md:100-120`); and the provider's `available()` "must not make network calls" — it is an input to selection, not a health check (`web.md:150-165`).
- **The web provider selection refuses to guess.** Multiple usable providers with no configured id is `WEB_PROVIDER_AMBIGUOUS`, "not first-wins" (`web.md:150-165`).
- **`domain/changed` carries the NEW value, never the old.** "a diffing consumer keeps its own previous snapshot" (`storage.md:132-140`).
- **Storage reads are synchronous from authoritative in-memory state, and a rejected backend write leaves memory untouched** — "so reads never diverge from the medium" (`storage.md:120-130`).
- **The right Sidebar's "Not built" list is a feature.** No layout persistence (a reload starts every session collapsed), no `find` (callers use `revealIfOpened` and let the surface de-duplicate), no undo (`sidebar-right.md:145-165`).
- **The Conversation `exclusive: true` claim is evaluated against every match before any is accepted**, "so the outcome is independent of registration order" — but "Two claims on one target, or a claim from a Definition without a target, throw during dispatch" (`conversation.md:250-262`).
- **`webhook.md` is the counter-example in this shard:** it deliberately keeps **no** queue, retry, deduplication, execution status or crash replay, so "repeated delivery may create repeated Sessions" (`webhook.md:19-30`). The page links the decision record that explains why. Knowing which parts of a system are *intentionally* stateless is as valuable as knowing how they work.

## 8. Weak spots

- **The documentation is enormous and heavily duplicated by construction.** The same Cordis API section is regenerated into every page, and every page repeats the "capability seam / Service Definition / Provider / Consumer" paragraph and the "Cordis API … generated by `scripts/gen-cordis-catalog.ts`" boilerplate. The 67 pages total ~2.3 MB, of which a large fraction is generated text. A reader who only needs the *decisions* still has to filter it.
- **The event vocabulary is a single flat namespace with heavy overloading.** `SessionEventMap` mixes turn boundaries, surface messages, request headers, tool calls and plugin-owned records in one map, and the rules about which combination is legal (surface versus log-only, `sourceEventSeqs` forbidden on `assistant/message`, `surfaceOp` mandatory on surface events) are enforced by *TypeScript conditional types over a mapped union* — clever, but very hard to hold in your head when a new event type is added.
- **Some pages are candidly over-specified for their audience.** `ptc-runtime.md`, `ssh.md` and `office-to-pdf.md` carry details (e.g. the exact portable identifier subset, the `RESERVED_BINDING_GLOBALS` list) that only the implementer needs; the *decision* is one sentence each. The `claude-code-mods.md` page is a compatibility matrix of ~150 rows that is accurate but has no natural owner — it will rot with every upstream Claude Code release.
- **Two seams are honest about being deliberately weak, which is good, but two are not.** The webhook runtime has no delivery state at all (fine, documented) — but the **schedule's** delivery is not atomic across two stores and the doc says the receipt "does not close this gap" (`schedule.md:343-345`). A scheduler that can double-deliver after a crash between the inbox write and the task-row write is a real reliability hole, stated honestly but not fixed.
- **The `Session.append` validation surface is enormous.** One method validates JSON-serialisability, the canonical request-header shape, the tool-error consistency rule, the canonical surface contract, positional replacement validity and complete shadowed-node coverage, in "one iterative pass … so a stateful getter cannot supply one value to validation and another to storage" (`session.md:565-600`). That is a remarkable amount of policy in one place, and it is the most likely place for a subtle bug.
- **The bilingual duplication doubles the maintenance surface.** 67 English pages × 2 + 67 hash manifests means every English edit requires a Chinese edit *plus* a hash re-record. The machinery (`verify-translation-pairing`) makes the drift *detectable* but not *absent*; the zh files even carry a few extra lines over their English counterparts (core +12, llm-streaming +6, session +4), which is small but shows the two sides are not mechanically derived.
