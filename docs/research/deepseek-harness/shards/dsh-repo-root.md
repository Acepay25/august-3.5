# deepseek-harness :: dsh-repo-root

**Files in shard:** 92 (read: 91, skipped with reason: 1)
**What this shard covers:** the repository *root* of DeepSeek Harness (`dsh`) — everything that is not inside a capability package: the pnpm workspace manifest and root `package.json` with its ~250 scripts, the TypeScript project graph (`tsconfig.*`), the Vitest lane matrix, oxlint/jscpd/lefthook/GitLab-CI gates, the bilingual EN/ZH documentation set and its generated pairing-hash ledger, and three small but load-bearing source groups — the Electron **desktop-host** process (the Node-mode host that boots the Web profile inside Electron, owns the update-admission lock, the quit inspection, the Windows console-signal bridge, and the ASAR→unpacked Office-engine resolver), and the two **exclusive-registration capability packages** (`dsh-browser-use`, `dsh-computer-use`) that show how the harness says "only one provider may hold this slot". This shard is therefore mostly *policy and scaffolding*: it is where the repo's rules about the agent loop, tool design, memory, sessions and human approval are actually written down, and where the test lanes that are supposed to prove those rules are configured.

## 1. File-by-file

### Tier 1 — load-bearing source: full entry

### `apps/desktop-host/src/cli.ts`
- **Purpose:** Run the ordinary `dsh` CLI using the *immutable runtime shipped inside the Desktop installation*, with Desktop's own bundled pnpm and reserved-profile plugin access.
- **Key abstractions:** `runDesktopCli(runtimeDir, supportDir)` — the single exported entry; the module also self-executes when `import.meta.main` is true.
- **Data flow:** `runtimeDir` → `installOfficeEngineResolution(runtimeDir)` → `runCli({ manageDesktopProfile: true, packageManager: { command: process.execPath, args: ['--expose-internals', <bundled pnpm.mjs>], env: { ELECTRON_RUN_AS_NODE: '1', DSH_DESKTOP_NODE_EXECUTABLE, PATH } } })`. The CLI's *plugin* lifetimes own the process lifetime — `runDesktopCli` resolves when the selected command completes.
- **Non-obvious design decisions:** the bundled package manager is launched by re-executing **Electron's own binary with `ELECTRON_RUN_AS_NODE=1`** (`apps/desktop-host/src/cli.ts:19-27`), not a system Node. That is how the Desktop shell ships one runtime for the UI *and* the CLI instead of two. `--expose-internals` is passed so the pnpm ESM loader can reach Node internals.
- **Edge cases & failure handling:** on Windows the console handler is installed *before* the CLI starts (`cli.ts:29-33`), because a `Ctrl-C` before the JS listeners exist is swallowed by the OS. `runtimeArchivePath(runtimeDir) ?? runtimeDir` (`:35`) tolerates both a prepared directory and an ASAR-contained tree.
- **Surprising:** the `import.meta.main` block re-derives `runtimeDir` as `resolve(import.meta.dirname, '../../../..')` — a hard-coded depth from the bundled `lib/cli.js` back to the runtime root. The CLI therefore only works when Electron placed it at that exact depth.

### `apps/desktop-host/src/index.ts`
- **Purpose:** Launch the Desktop *profile* through the Web application and report its URL back to the Electron shell over IPC.
- **Key abstractions:** `main()`; the `control` object holding the two late-bound installers (`installDesktopUpdateTaskControl`, `installDesktopQuitInspection`); the `send()` promise wrapper around `process.send`; the `stop()` idempotent shutdown promise.
- **Data flow:** `process.argv[2]` (runtimeDir) + `process.argv[3]` (projectDir) → `loadProfileDirectory('dsh', projectDir, installAnchor)` → `runProfile({ environment: loadLayeredEnv('dsh'), profile: 'desktop', args: ['--no-open','--host','127.0.0.1','--port','0'] })` → `await application` → install controls → `ctx.plugin(desktopOffice, {...})` → `installPlatformSessionPublisher(ctx, …)` → `ctx.connection.authenticatedUrl(...)` → `process.send({ type: 'ready', url, injections })`.
- **Non-obvious design decisions:** the host binds to **port 0** and asks the connection layer for an *authenticated* URL (`index.ts:41, 103`) — the browser never sees an unauthenticated local port. The Office plugin is mounted **after** `await application` (`:96-100`) so a boot failure is reported by `main`, not swallowed by the shutdown path. The shutdown handler explicitly separates *startup failure* from *shutdown*: "Startup failure is reported by main; shutdown only owns a tree that booted" (`index.ts:53-55`).
- **Edge cases & failure handling:** every IPC message is shape-checked before use — `typeof message !== 'object'`, `'type' in message`, `Number.isSafeInteger(message.requestId)`, and `['inspect','lock','unlock'].includes(action)` (`index.ts:78-80`); anything else is dropped silently. If the host is already stopping, the quit/update inspectors *throw* rather than report "idle" (`:66, 80`), and the catch sends `activeTasks: true` so the shell treats the state as interruptible work and asks before quitting (`:70-74`).
- **Surprising:** the fatal diagnostic is sent over IPC, not stderr: "The shell receives the complete inspected error here, not through stderr: stderr bytes and this IPC message race, and the shell reports the first failure it sees." (`index.ts:111-115`). The diagnostic is capped at 64 KiB (`MAX_FATAL_DIAGNOSTIC_CHARS`, `:108`) and `inspect(error, { depth: 4, maxArrayLength: 50 })` bounds the object graph.

### `apps/desktop-host/src/office-engine.ts`
- **Purpose:** Resolve packaged Office engine manifests from their complete, *unpacked* resource directories, because a native child process cannot execute a file that lives inside an Electron ASAR archive.
- **Key abstractions:** `runtimeArchivePath(runtimeDir)` and `installOfficeEngineResolution(runtimeDir): ModuleHooks | undefined`.
- **Data flow:** `registerHooks({ resolve(specifier, context, nextResolve) { … } })` — a **Node module-resolution hook** that rewrites any resolution of `@deepseek-ai/libreoffice-kit-<platform>-…` from the archived path to the `app.asar.unpacked` sibling, using `realpathSync` on both sides and preserving the tail of the path.
- **Non-obvious design decisions:** the hook is **thread-local** — "Hooks apply only to this thread; worker threads must install their own resolver" (`:22`). It also **fails closed**: if the canonical real path of a matching request is not under the runtime's `libreoffice-kit-` source root but *is* under the archive, it throws "desktop Office engine resolved outside the runtime package directory" (`:41-44`) rather than silently loading the wrong copy. An engine that resolves to a path *outside* the archive entirely is left alone (`:45-46`) — third-party engines are not hijacked.
- **Edge cases & failure handling:** `runtimeArchivePath` returns `undefined` for a prepared (non-ASAR) directory, and `installOfficeEngineResolution` then returns `undefined` — the whole mechanism is a no-op outside a packaged app (`:24`). `realpathSync` is used to defeat symlink aliases (the test at `tests/office-engine.spec.ts` covers a directory-alias case).
- **Surprising:** `office.ts` computes the *unpacked* Office package root independently, by resolving `@deepseek-ai/libreoffice-kit/package.json` through `import.meta.resolve` and re-rooting it under `${archive}.unpacked` — two different mechanisms for the same "find the real file" problem, one for ESM `import.meta.resolve` and one for `require()`.

### `apps/desktop-host/src/office.ts`
- **Purpose:** Enable offline Office authoring and LibreOffice Kit operations inside the Desktop profile.
- **Key abstractions:** `name = 'desktop-office'`; `Config { source, root, runtimeDir }`; `apply(ctx, config)`.
- **Data flow:** `ctx.plugin(workspaceDependencies, config)` → compute the real (unpacked) package root of `@deepseek-ai/libreoffice-kit` → `ctx.plugin(officeSkills, { assetRoot: <source>/../office-skills, node: <source>/dependencies/node/bin/node[.exe], cli: <packageRoot>/lib/cli.js })`.
- **Non-obvious design decisions:** the bundled **Node binary is addressed by platform-specific filename** (`process.platform === 'win32' ? 'node.exe' : 'node'`, `:32`) — the skill payload must not guess. The Office *assets* live at `dirname(config.source)/office-skills`, i.e. a *sibling* of the payload directory, not inside it.
- **Edge cases & failure handling:** the config doc says "Missing sibling `office-skills` resources fail Host startup" (`Config.source`, `:23`) — a missing payload is a loud failure, not a degraded mode.
- **Surprising:** this file is a *function plugin* (`name`/`Config`/`apply` exports, no default export) — the exact shape `packages/AGENTS.md` mandates, and the exact shape the ACP postmortem says a default export destroys.

### `apps/desktop-host/src/platform-session.ts`
- **Purpose:** Keep Electron's private Platform credentials bound to the currently-active DeepSeek account provider, without ever forwarding credentials to the renderer.
- **Key abstractions:** `installPlatformSessionPublisher(ctx, publish)`; internally an `AbortController` named `lifetime` and an async `updates` loop over `account.watch(signal, true)`.
- **Data flow:** `ctx.inject(['deepseekAccount'], accountCtx => …)` → `accountCtx.effect(() => { … return async () => { lifetime.abort(); publish(null); await updates } })` → for each watch tick, `account.getPlatformSession()` → `publish(session)` → over IPC to the Electron main process only.
- **Non-obvious design decisions:** the effect's disposer **publishes `null` before awaiting the update loop** (`:30-32`) so the credential is cleared the instant the provider unloads, not when the pending read finishes. The watch is asked for `includeIdentityChanges = true` (`account.watch(lifetime.signal, true)`), so an account-identity change re-publishes the session.
- **Edge cases & failure handling:** there are **two** abort checks around the credential read (`:21, 26`) with an eslint-disable explaining why: "Disposal can abort during the credential read." The `finally` block publishes `null` only if not aborted (the disposer already did). A failing watch logs a warning and still clears the session.
- **Surprising:** this is the *only* place credentials cross a boundary, and it deliberately never sends them to the renderer — the publish callback's doc says "never forwards credentials to the renderer" (`:9`).

### `apps/desktop-host/src/quit-inspection.ts`
- **Purpose:** Answer "what would quitting the Host right now affect?" — separating *interruptible work* from *armed scheduled reminders*.
- **Key abstractions:** `interface DesktopQuitInspection { activeTasks: boolean; scheduledTasks: boolean }`; `installDesktopQuitInspection(ctx): () => Promise<DesktopQuitInspection>`.
- **Data flow:** `ctx.get('agents')` + `ctx.get('jobs')` → `hasDesktopActiveTasks(liveAgents, jobs)` → for each live agent, `ctx.waterfall('workspace/session-activity', { sessionId: agent.id }, () => Promise.resolve([]))` → `activity.some(entry => entry.kind === 'schedule')`.
- **Non-obvious design decisions:** the two booleans are **separate** because they imply different user prompts ("a run is in progress" vs "a reminder is armed"). The `waterfall` call supplies a **default `() => Promise.resolve([])`**, so the inspector works even when no activity provider is mounted. It **stops at the first** session that has an armed schedule (`:36`).
- **Edge cases & failure handling:** unavailable task services throw "task services are unavailable" — the test pins this explicitly: "does not classify unavailable task services as idle" (`tests/quit-inspection.spec.ts`). After context disposal the inspector throws "desktop quit: Host is stopping" rather than returning a false "nothing is running" (`:26-27`).
- **Surprising:** the doc-comment states the precise semantics of the count: "reminders in sessions that were never loaded during this run cannot fire and are not counted" (`:20-22`). That is a *reachability* argument, not a liveness argument — an armed-timer inventory restricted to reachable sessions.

### `apps/desktop-host/src/update-tasks.ts`
- **Purpose:** The **admission lock** — the pattern this shard is most worth stealing. It lets the Desktop shell decide whether it may install an update (restart the host) without interrupting live work.
- **Key abstractions:** `hasDesktopActiveTasks(liveAgents, jobs): boolean` (exported, and reused by the quit inspector); `installDesktopUpdateTaskControl(ctx): (action: 'inspect' | 'lock' | 'unlock') => Promise<boolean>`.
- **Data flow:** a `ctx.on('connection/request', …)` middleware intercepts every inbound HTTP request. While `locked` is true it answers `503` and returns (`:34-38`). Otherwise it registers the request in `pendingRequests` (a `Set<Promise<void>>` of `Promise.withResolvers()`), awaits `next()`, and removes itself in a `finally` (`:39-44`). `action: 'lock'` sets `locked = true`, bumps `lockGeneration`, awaits `Promise.all(pendingRequests)` — the **drain** — then re-checks `hasDesktopActiveTasks` and returns it.
- **Non-obvious design decisions:** the comment "Read requests are not tasks; admitted writes must finish before the final work check" (`:51-52`) explains why the drain exists at all. The **`lockGeneration` counter** (`:30, 47, 53, 58`) makes a superseded lock fail loudly: if someone calls `unlock` while a `lock` is still draining, the draining lock throws "desktop update: admission lock was superseded" instead of proceeding on a stale view. The drain waits for the *admitted requests*, and only then re-reads the roster — so the answer reflects the world *after* the drain, not before.
- **Edge cases & failure handling:** `stopped` is set by `ctx.effect(() => () => { stopped = true })` (`:32`) so every call after disposal throws "desktop update: Host is stopping". The eslint-disable at `:56` records that disposal can run *while* admitted requests drain.
- **Surprising:** the lock is implemented at the **HTTP connection layer**, not at the agent layer. A request refused with 503 is the first line of defence; the agent/job roster is only the second.

### `apps/desktop-host/src/windows-cli-signals.ts`
- **Purpose:** Deliver Windows console interrupts (`Ctrl-C`, `Ctrl-Break`) to Node's CLI listeners when Node is running inside Electron's `ELECTRON_RUN_AS_NODE` mode.
- **Key abstractions:** `installWindowsCliSignals(): Promise<void>`; dynamically imports `koffi` and calls `SetConsoleCtrlHandler`.
- **Data flow:** `koffi.load('kernel32.dll')` → `koffi.proto('int __stdcall DshCliConsoleHandler(uint32_t event)')` → `koffi.register(cb, koffi.pointer(type))` → `kernel.func('int __stdcall SetConsoleCtrlHandler(...)')` → `install(handler, 1)`.
- **Non-obvious design decisions:** the callback **re-emits Node's own signals** (`process.emit('SIGINT')`, `process.emit('SIGBREAK')`) rather than implementing cancellation, so every existing `process.on('SIGINT')` listener in the app works unchanged. Event `0` → SIGINT, event `1` → SIGBREAK; anything else returns 0 to keep native handling.
- **Edge cases & failure handling:** if `SetConsoleCtrlHandler` returns 0 the handler is **unregistered** (`koffi.unregister(handler)`) before throwing "desktop CLI: cannot register the Windows console handler" — no leaked native callback.
- **Surprising:** "Koffi queues callbacks from the console thread onto the JavaScript thread" (`:5-6`) — the FFI bridge is what makes this possible at all, and the doc says the registration "lasts until process exit" (`:7`).

### `packages/browser-use/browser-use/src/index.ts`
- **Purpose:** The **exclusive named registration** service for the browser-use capability: exactly one provider may hold the slot.
- **Key abstractions:** `class BrowserUseRegistry extends Service` (Cordis `Service`, key `browserUse`); `providerName` getter; `register(name): () => Promise<void>`.
- **Data flow:** a provider plugin calls `ctx.browserUse.register(BrowserUseProviderName('playwright-mcp'))` → the service throws if a registration exists → otherwise `ctx.effect(() => { this.registration = name; return () => { this.registration = undefined } }, 'browserUse.register()')` and returns that effect's disposer.
- **Non-obvious design decisions:** a **second registration fails even when it repeats the current name** (`:36-38`), and the error message **names the incumbent** ("browser use provider \"playwright-mcp\" is already registered"). The registration is held by a Cordis *effect*, so unloading the provider plugin releases it automatically — and "a repeated disposer cannot remove a later registration" (`packages/browser-use/browser-use/README.md`, "Understand the implementation"), because the effect disposer only clears if it is still the current owner.
- **Edge cases & failure handling:** `providerName` reports the name "including while its resources are closing" — the slot is freed only after the provider has stopped admitting tool calls and awaited its own work, so no window exists where a new provider holds the slot while the old one is still running.
- **Surprising:** the whole file is ~45 lines and contains **no browser object, no operation interface, no resource lifecycle, no provider selector** — the README states this explicitly. The package is a *name slot*, nothing else.

### `packages/computer-use/computer-use/src/index.ts`
- **Purpose:** Identical-by-construction twin of the browser-use registry, for desktop providers.
- **Key abstractions:** `class ComputerUseRegistry extends Service` (key `computerUse`); `providerName`; `register(name): () => Promise<void>`.
- **Data flow / decisions / edge cases:** byte-for-byte the same shape as the browser-use registry with the names swapped — the exclusivity rule, the "already registered" error naming the incumbent, the effect-owned slot, and the disposer semantics are all identical (`:35-46`).
- **Surprising:** the two packages are **duplicated rather than shared**. The `.jscpd.json` config (`minTokens: 60, minLines: 6`) does not flag them because the duplicated block is below the token threshold — the duplication gate is tuned *below* the size of the smallest intentionally-duplicated unit. The shared shape is instead expressed by the `Branded<>` brand function pattern.

### `packages/browser-use/browser-use/src/brand.ts`
- **Purpose:** Brand a provider-owned name so a `string` cannot be passed where a provider name is required.
- **Key abstractions:** `type BrowserUseProviderName = Branded<'BrowserUseProviderName'>`; `function BrowserUseProviderName(name: string): BrowserUseProviderName`.
- **Data flow:** a pure type-level cast; no runtime validation.
- **Non-obvious design decisions:** the brand function deliberately **does not validate** — "Brand a provider-owned name without changing or validating it" (`:9`). The registry's exclusivity, not the brand, is the enforcement point.
- **Edge cases & failure handling:** none, by design — the doc says the name is "chosen by the provider implementation". The trade-off is stated plainly in `AGENTS.md:144`: "Opaque cross-boundary ids are branded (`Branded<B>` from `dsh-brand`), never bare `string`."
- **Surprising:** the brand lives in a **separate export path** (`./brand` subpath) so a consumer can import the type without pulling the Service class — and so the brand module has zero runtime dependencies beyond the type.

### `packages/computer-use/computer-use/src/brand.ts`
- **Purpose:** The computer-use twin of the browser-use brand module.
- **Key abstractions:** `type ComputerUseProviderName = Branded<'ComputerUseProviderName'>`; `ComputerUseProviderName(name: string)`.
- **Data flow / decisions / edge cases:** identical to the browser-use brand; same "brand without validating" contract.
- **Surprising:** both brand modules are **independent copies** — 17 lines each, differing only in the brand string. The naming convention (`BrandName` type + `BrandName()` function with the same name) is the repo's idiom for "opaque id".

### `packages/tsdown.worker.ts`
- **Purpose:** Emit the fixed startup banner for Node Worker bundles, so a Worker can resolve the parent's profile before any business code runs.
- **Key abstractions:** `profileWorkerBanner(format: 'cjs' | 'esm'): string`.
- **Data flow:** returns `"use strict";\nrequire("@deepseek-ai/dsh-app-boot/worker/profile-resolution-bootstrap");` for CJS and the `import` form for ESM.
- **Non-obvious design decisions:** the comment explains the exact constraint it works around: "ESM static dependencies must resolve without the profile resolver" (`:4`). The bootstrap must therefore be loaded as the **first statement** of the bundle, before the Worker's own static imports — hence a text banner rather than an import.
- **Edge cases & failure handling:** the banner is format-specific; the CJS form must precede any `require` to be a valid program prologue.
- **Surprising:** this one file is the entire "worker profile resolution" strategy — the whole behaviour is "put this exact string at the top of the bundle".

### `tsdown.config.ts`
- **Purpose:** The workspace bundler configuration: one `tsdown` invocation that compiles the TypeScript-emitted `lib/types` of every workspace package into runtime bundles.
- **Key abstractions:** `isBuildFaceClient(env?.DSH_BUILD_FACE)` — the single place that decides "host" vs "client" face and **throws** on any other value (`:12-15`); the default export `defineConfig(({ env }) => …)`.
- **Data flow:** `globSync(['vendor/*/package.json', 'packages/*/*/package.json'])` → `workspacePackageGlobs(...)` → workspace build with `entry: client ? '' : ['lib/types/{index,startup}.js']`, `format: ['esm']`, `platform: 'node'`, `target: 'es2024'`, `codeSplitting` default, `dts: false`, `clean: false`; on the host face the `typertPlugin({ mode: 'workspace', faces: WORKSPACE_TYPERT_FACES })` runs a **type-graph generator** as a bundler plugin.
- **Non-obvious design decisions:** `clean: false` and `dts: false` — the bundler never removes or re-emits declarations, because `tsc -b` owns `lib/types` and the two tools must not fight over the same directory. The **client face selects a different package set** (`client ? [] : ['apps/desktop-host']`) and generates *browser* artifacts, so the same repo builds two genuinely different products from one source tree.
- **Edge cases & failure handling:** an unknown `DSH_BUILD_FACE` fails loudly with the received value in the message (`:14`).
- **Surprising:** the comment at `:20-24` says "tsdown builds workspace members concurrently without ordering them" — the build therefore cannot rely on inter-package build order, which is why every package is a TypeScript *project reference* and every import resolves through `paths`.

### `vitest.shared.ts`
- **Purpose:** The two things every Vitest lane needs: a Node flag that stops process-wide Web Storage from shadowing jsdom's, and a Vite plugin that transpiles standard TypeScript decorators before Vite's parser sees them.
- **Key abstractions:** `vitestExecArgv` (computed at module load); `standardDecoratorPlugin()` returning a Vite plugin with `enforce: 'pre'`.
- **Data flow:** `process.allowedNodeEnvironmentFlags.has('--webstorage')` → `['--no-webstorage']`; the plugin's `transform(code, id)` filters `/\.[cm]?tsx?$/` and a decorator-syntax regex, then `ts.transpileModule(...)` with `target: ES2024`, `module: ESNext`, `jsx: ReactJSX` for `.tsx`.
- **Non-obvious design decisions:** the transpiled output is post-processed to insert `/* v8 ignore next -- compiler-synthetic decorator accessors have no source behavior */` **before every `__esDecorate(` call** (`:36-39`) — the compiler emits accessor boilerplate that has no source-level behaviour, and it would otherwise pollute the 100% per-file coverage gate. The sourceMappingURL is stripped and the map returned separately.
- **Edge cases & failure handling:** the plugin is a no-op for non-TS files and for files with no decorator syntax, so the vast majority of the repo pays only a regex test.
- **Surprising:** the `--no-webstorage` flag exists because Node 22+ ships a process-global Web Storage that would **shadow jsdom's** and make storage-dependent tests silently pass against the wrong implementation.

### `vitest.config.ts`
- **Purpose:** The main unit-test configuration and the **coverage gate** for the whole repository.
- **Key abstractions:** `pathsPlugin()` (the shared `vite-tsconfig-paths` facade); `windowsUnsupportedPackages` / `windowsUnsupportedTests` / `nonLinuxWebWorkerTests` / `platformUnsupportedTests`; `windowsOnlyCoverageExclusions`; `windowsRunnerCoverageExclusions`; `pwshCoverageExclusions`; `testIncludes`; `processBoundTests`; `claudeCodeTestingAliases`; `coverageExemptHeavySuites`.
- **Data flow:** the config resolves the `tsconfig.base.json` `paths` map for *all* test files ("tsconfig.base.json has no include, which vite-tsconfig-paths treats as match-all"), then defines **two Vitest projects**: `thread-safe` (everything except `processBoundTests`) and `process-bound` (the eight process-global suites), both with `pool: 'forks'`.
- **Non-obvious design decisions:** (1) **Everything forks.** The comment says "Node 24 has aborted in the CJS lexer … from worker threads on macOS, Linux, and Windows. Forked workers avoid that shared thread path." (2) The coverage gate is **per-file 100%** on statements/branches/functions/lines, with `perFile: true` "so a well-covered big file can't subsidize a bare one". (3) The platform exclusions are computed at **config load time** from `process.platform`, so the gate is different on Windows than on Linux — and each exclusion carries a comment explaining why (POSIX-only shell suites, `ssh` needs Unix sockets, the WebWorker suites compare against a fixed Linux platform). (4) The `pwshCoverageExclusions` are decided by *actually running* `pwsh -Command '$true'` (`spawnSync(resolvePwshPath(), …)`), so the exemption is active exactly when the suites skip.
- **Edge cases & failure handling:** `COVERAGE_EXEMPT_ENV` and `COVERAGE_PARTITION_MODE_ENV` are validated: "A set-but-not-'1' value is a misconfiguration, not a silent no-op" (`:151-154`, `:166-169`). The coverage list of exemptions is very long and each entry is individually justified in comments (the webworker runtime, the inspector bridges, the client UI debt).
- **Surprising:** `claudeCodeTestingAliases` maps `claude-code/testing` and `claude-code` to **test-support shims inside the repo** (`packages/experimental/claude-code-mods/tests/support/…`), so the example mods' tests import upstream module names unchanged.

### `vitest.e2e.config.ts`
- **Purpose:** The real-API end-to-end lane — the only lane that spends tokens.
- **Key abstractions:** `positiveIntFromEnv(name, fallback)`; `DEFAULT_E2E_MAX_WORKERS = 4`.
- **Data flow:** `process.loadEnvFile(new URL('.env', import.meta.url).pathname)` (Node ≥ 21.7) inside a `try/catch` that tolerates a missing `.env`; `DSH_E2E_MAX_WORKERS` → `fileParallelism` + `maxWorkers`.
- **Non-obvious design decisions:** `retry: 2` is justified as "retries for transient flakes (the shared internal key hits concurrency quotas)" — the harness knows its own quota and encodes it. The worker count is a **bounded pool**, not unbounded parallelism, with the escape hatch documented: "`DSH_E2E_MAX_WORKERS=1` restores serial execution". `include` covers `packages/*/*/tests/**/*.e2e.ts`, `apps/cli/tests/**/*.e2e.ts`, `apps/desktop/tests/**/*.e2e.ts` and explicitly **excludes** the expected-output and browser-client suites that belong to other lanes.
- **Edge cases & failure handling:** `positiveIntFromEnv` **throws** on a non-integer or `< 1` value rather than falling back — a typo'd env var fails the run instead of silently changing parallelism.
- **Surprising:** the config explains why bare workspace names must resolve through the `tsconfig.base.json` `paths` facade and not through package `exports`: "dropping /client subpath imports onto package exports would load browser dist bundles into node" (`:34-38`).

### `vitest.snapshot.config.ts`
- **Purpose:** The **keyless recorded-session replay** lane — the harness's core regression mechanism.
- **Key abstractions:** `DEFAULT_SNAPSHOT_MAX_CONCURRENCY = 5`; `snapshotMaxConcurrency`; `snapshotMaxWorkers`; the `DSH_SNAPSHOT` mode switch (`replay` | `record` | `refresh`).
- **Data flow:** in `record` mode only, `.env` is loaded (and a non-ENOENT failure is **re-thrown** rather than swallowed: "Surface any other failure rather than silently recording with wrong env"). The `include` list is the session-snapshot corpus plus `snapshots/**/*.snapshot.ts`, plus `apps/web/tests/**/*.snapshot.ts` only when `DSH_EXAMPLE_MODE === 'lib'`.
- **Non-obvious design decisions:** the parallelism rule encodes a real concurrency-safety argument: **replay** may run in parallel because "Replay never writes committed outputs and every scenario owns its mutable runtime state (the subprocess suites use a unique temp dir and fixture set per scenario)", while **record and refresh stay serial** because "concurrent writers would corrupt expected outputs" (`:36-42`). This is a genuinely useful general rule: *a test lane that writes shared golden files must be serial; a lane that only reads them may be parallel.*
- **Edge cases & failure handling:** `fileParallelism` is `(DSH_SNAPSHOT || 'replay') === 'replay' && (workers ?? concurrency) > 1` — so a mis-set `DSH_SNAPSHOT` value silently falls back to *not* parallel, which is the safe direction.
- **Surprising:** `refresh` is a **third** mode distinct from `record`: it replays committed scripts and *updates current expected outputs* without touching the recorded fixtures. Three modes — record (needs a key), replay (keyless), refresh (keyless, writes) — is a clean separation of "capture", "verify", "refresh".

## 2. Ideas worth stealing

1. **An admission lock that drains in-flight work before acting, then re-checks.** `apps/desktop-host/src/update-tasks.ts:33-60` — new requests are refused with `503` while locked; already-admitted requests are awaited to completion (`await Promise.all(pendingRequests)`); only *then* is the work roster re-read, so the answer reflects the world after the drain. A `lockGeneration` counter makes a superseded lock fail loudly instead of acting on a stale view (`update-tasks.ts:58`). **Why it transfers:** August Trading's backup/restore/wipe and provider-migration paths all mutate state that in-flight analysis turns also touch. `UNIQUE` — none of the other two reference repos is read in this shard; treat this as strong prior art for the pattern itself, and confirm convergence when the `pi` and `hermes-agent` shards land.
2. **A separate "is it safe to stop?" inspector that distinguishes two kinds of pending work.** `apps/desktop-host/src/quit-inspection.ts:29-38` returns `{ activeTasks, scheduledTasks }` — running work and *armed reminders* are counted separately, because they mean different things to the user. It also refuses after disposal rather than reporting "idle" (`quit-inspection.ts:26-27`), and the test explicitly pins "does not classify unavailable task services as idle". **Why it transfers:** August Trading's TP/SL watcher and scheduled automations are exactly this second kind of pending work; a trade can be "quiet" yet still have an armed TP/SL timer that a restart would silently drop. `UNIQUE`.
3. **One exclusive slot per capability, with the incumbent named in the error.** `packages/browser-use/browser-use/src/index.ts:35-44` — the second registration throws `browser use provider "playwright-mcp" is already registered`, and the slot is owned by a Cordis *effect* so unloading the provider frees it, while "a repeated disposer cannot remove a later registration". **Why it transfers:** August has several places where exactly one owner should hold a resource (the auto-capture source, the approval mode, the chart's active session). A one-line registry with a named incumbent is far clearer than a boolean flag. `UNIQUE`.
4. **"Model-visible ⟺ logged": anything that reaches a model request must be reconstructable from the session log.** `AGENTS.md:137`. **Why it transfers:** this is the single rule August Trading most needs — every number that reaches the analysis prompt (R:R, ATR stop band, the plan's edge) must be reconstructable from the trade journal row, or the journal is not an audit trail. `UNIQUE` to this repo's phrasing, but it is the same invariant `pi`'s replay corpus implements; expect `CONVERGENT`.
5. **Enforce a decision in the operation that makes it — and test denial through the executor.** `packages/AGENTS.md:16`. "Schema omission, prompt filtering, facades, wrappers, and listener order are not enforcement when direct or alternate callers can bypass them." **Why it transfers:** August's R:R floor and ATR stop-band gate live in `services/validation/`, but if any other call site can call the analysis path directly, the gate is a suggestion. `UNIQUE`.
6. **Publish state only at its commit point.** `packages/AGENTS.md:17` — emit each notification and update derived state only after the operation succeeds; derive caches, prompts, UI echoes, replay and query views from one authoritative source. **Why it transfers:** August has several derived views of one trade (the chat row, the journal card, the outcome engine's verdict, the CSV export). One authoritative source + commit-point publication is the fix for "the row and the card disagree". `UNIQUE`.
7. **Apply bounds to the complete result, not to a part of it.** `packages/AGENTS.md:18` — enforce byte/token/item/time limits where the complete emitted or retained value (including wrappers and metadata) is known; test tiny and exact limits, oversized single chunks, and multibyte byte limits. **Why it transfers:** August's context-window budgeting (`utils/contextWindow.ts`, `compactForWire()`) must bound the *assembled* request, not the history array — and the multibyte case is the one that bites with emoji in a trade note. `UNIQUE`.
8. **A coverage gate of per-file 100%, with every exemption individually justified in a comment.** `vitest.config.ts` (`thresholds: { perFile: true, statements: 100, branches: 100, functions: 100, lines: 100 }`) plus a long, individually-commented exclusion list; a custom reporter prints exact `path:line:col` for every uncovered branch. **Why it transfers:** August's AGENTS.md already insists that a test proves a rendered row, not a component return value — the same instinct, one level down. `UNIQUE`.
9. **A recorded-session replay lane with three modes: record (needs a key), replay (keyless), refresh (keyless, writes).** `vitest.snapshot.config.ts` — and the concurrency rule that encodes *why*: replay may run in parallel (it never writes committed outputs and every scenario owns a unique temp dir), record and refresh stay serial (concurrent writers would corrupt expected outputs). **Why it transfers:** August could record a real provider exchange and replay it in CI without an API key, and the "writers stay serial, readers may parallel" rule is directly reusable. `UNIQUE`.
10. **Test lanes named by cost and risk, with the escape hatch documented.** `vitest.e2e.config.ts` (`retry: 2` for "the shared internal key hits concurrency quotas", `DSH_E2E_MAX_WORKERS=1` restores serial), `vitest.web.perf.config.ts` (manual, outside CI, `--expose-gc`), `vitest.web-stress.config.ts` (opt-in by filename). **Why it transfers:** August's `render-probe` already plays this role; the naming convention (`*.perf.ts`, `*.stress.ts`, `*.expected.e2e.ts`, `*.client.spec.ts` vs `*.host.spec.ts`) makes the lanes mutually exclusive *by filename*, so no lane can accidentally absorb another's files. `UNIQUE`.
11. **Bilingual documentation drift detection by content hash.** The `*.i18n.yaml` ledger stores a hash per heading section for the English and the Chinese block; `verify-translation-pairing` fails when one side changes alone. **Why it transfers:** a one-hour-to-build mechanic that prevents the classic "the zh README quietly rotted" problem, and it doubles as a "did this doc actually change?" gate. `UNIQUE`.
12. **Deny-by-default install scripts and a release-age window, both with a reasoned exemption list.** `pnpm-workspace.yaml` (`allowBuilds`, `minimumReleaseAgeExclude`). **Why it transfers:** August Trading ships an Electron/Capacitor app; encoding "which dependencies may run install scripts" as explicit reviewed config is a supply-chain control a trading app needs. `UNIQUE`.
13. **The two compiler faces are separated by *filename suffix*, not by per-file config.** `tsconfig.host.json` excludes `*.client.*`; `tsconfig.client.json` excludes `*.host.*`. **Why it transfers:** August's `AGENTS.md` already notes that `electron/*.cjs` escapes `tsc` — the same trick (suffix-based face selection) could give the Electron main/preload their own program without a 400-file include list. `UNIQUE`.
14. **Trust TypeScript at typed same-process boundaries; validate at the seven dangerous ones.** `AGENTS.md:145` — parser/config, queued, model/tool JSON, durable/file, worker, process, and wire. **Why it transfers:** August's zod-at-the-boundary rule is the same idea but is currently applied somewhat unevenly; the enumerated list of exactly seven boundary kinds would let August say precisely where validation is required and where it is noise. `UNIQUE`.

## 3. Trading-specific findings

- **Long-lived monitoring & scheduled work — the host-side view only.** This shard does not contain the scheduler, but it shows the *contract* the scheduler must satisfy: scheduled reminders are surfaced as `workspace/session-activity` entries of `kind: 'schedule'` carrying an `id` and a `label` (`apps/desktop-host/src/quit-inspection.ts:35-36`; the fixture at `apps/desktop-host/tests/quit-inspection.spec.ts` uses `{ kind: 'schedule', items: [{ id: 'reminder-1', label: 'stand-up' }] }`). Two rules transfer: (a) **only armed timers count** — "reminders in sessions that were never loaded during this run cannot fire and are not counted" (`quit-inspection.ts:20-22`); (b) **a stopped process must report its pending work before exit**, never silently drop it. The scheduler implementation itself lives in `packages/schedule/schedule` — *not in this shard*.
- **Human-in-the-loop approval — the gating mechanics are here, the approval UX is not.** What this shard shows is how a *destructive* action is gated rather than how a model request is: `installDesktopUpdateTaskControl(ctx)` exposes exactly three verbs — `inspect`, `lock`, `unlock` (`apps/desktop-host/src/index.ts:78-80`) — and the shell must ask before quitting when the inspector reports active work (`apps/desktop-host/src/index.ts:70-74`). The approval *seams* live in `packages/interaction/` (`user-approval`, `user-questions`, `permission-presets`, `tool-ask-user`) and `packages/credentials/authorization` — *not in this shard*.
- **Post-mortem / reflection loops — only the seams are visible.** The root tsconfig references show the machinery exists as separate packages: `packages/goal/goal` + `goal-round-driver` (same-session goal persistence and lifecycle), `packages/session/session-turn-outline`, `packages/feedback/message-feedback` + `command-feedback`, and `packages/plan/plan-mode` ("Plan collaboration state with a direct entry command and **reviewed exit**" — `packages/README.md`). The "reviewed exit" wording is the anti-bad-rule-accumulation mechanism August would need for its skill/rule store. *Implementations are not in this shard.*
- **Multi-agent — the shape is visible, the debate question is not.** `packages/subagent/` splits into `subagent` (the contract), `tool-subagent` + `tool-subagent-control` (the model-facing delegation tools), and four concrete providers: `subagent-acp`, `subagent-claude-code`, `subagent-codex`, `subagent-dsh-sdk`. There is also `packages/experimental/agent-team` + `agent-team-profile` + `tool-agent-team`, and the Web client has an `ui-agent-team` panel. **There is no debate engine** anywhere in this shard — the design leans on *delegation with a control surface*, not on multi-agent debate. August's multi-provider "debate" service (removed from its codebase per its own AGENTS.md) may have been over-engineered relative to this repo's stance.
- **Structured logs the model can query — the storage choices are declared in one place.** The root project graph names them: `packages/session/session-persistence-jsonl` (**JSONL**, with a POSIX `flock`-based write lease in `lease.ts`), `packages/session/session-query-sqlite` (**SQLite full-text search** — the package table says "logical corpus, bounded reads, lineage, semantic filtering, SQLite full-text search"), `packages/session-query/session-log-export`, `packages/session/session-projection` + `session-projection-cache`, `packages/session/session-stats`, `packages/storage/storage-json` + `storage-sqlite` + `storage-domain`, and `packages/session/session-log-deepseek`. The pattern — **JSONL as the durable write-ahead log, SQLite as the query index** — is exactly August's "trade log the model can query" problem, solved without a heavy database at write time.
- **Staying simple as features accumulate — the mechanisms are explicit and named.** (a) **The capability-seam rule**: every capability is Definition/Provider/Consumer, and "it is complete, never one role" (`AGENTS.md:139`; `packages/AGENTS.md:12`). (b) **The package-group map**: 50 groups, one README each, every package in exactly one group. (c) **The experimental group**: "Capabilities under evaluation; status and support policy" — `packages/experimental/README.md#status` — and "experimental status is independent of publication, installation and optional delivery" (`packages/README.md`). (d) **One product group per concern, business rules in their own package** ("a business branch belongs to an independent package and attaches through a registration surface", `packages/AGENTS.md:14`). (e) **A package must have product use or an explicit classification** (`scripts/product-package-policy.ts`) — so a feature cannot exist without a reason on the record.

## 4. Non-obvious decisions and gotchas

- **`ctx.effect()` is the only registration mechanism, and the effect name is a string.** `packages/browser-use/browser-use/src/index.ts:39-44` passes `'browserUse.register()'` as the effect's label. Every contribution in the harness is an effect, so unloading a plugin releases its contribution automatically; this is why "a repeated disposer cannot remove a later registration" and why the registry's `providerName` still reports the name "while its resources are closing".
- **The `paths` map in `tsconfig.base.json` is a *facade*, not a build artifact.** It has no `include`, so `vite-tsconfig-paths` treats it as match-all and applies the map to **every** test file in every lane. Adding `include`/`files` to it would "leak into every extending package project and narrow the facade's match-all scope" (`tsconfig.base.json:2-4`). The map is regenerated by `scripts/gen-tsconfig-paths.ts` and gated by `verify-tsconfig-paths`.
- **A solution tsconfig with `files: []` is a deliberate design, not an oversight.** `tsconfig.json` says: "NEVER flatten this solution into a single ts.Program (scripts seed tsconfig.host.json or tsconfig.client.json)" — because the Host and Client sides both merge the Cordis `Context` under the same keys with different services, and one program cannot see both.
- **The desktop host binds to port 0 and hands Electron an *authenticated* URL.** `apps/desktop-host/src/index.ts:41, 103` — the browser never sees a bare local port.
- **The fatal diagnostic travels over IPC, not stderr, and is bounded.** `apps/desktop-host/src/index.ts:108-117` — "stderr bytes and this IPC message race, and the shell reports the first failure it sees"; the payload is `inspect(error, { depth: 4, maxArrayLength: 50 })` truncated to 64 KiB.
- **`hasDesktopActiveTasks` is shared by two features.** The update-restart check and the quit inspection use the *same* function (`apps/desktop-host/src/update-tasks.ts:16`, imported at `quit-inspection.ts:6`) — the doc explicitly says the inspector counts "Work the shared update-restart check also counts". One definition of "interrupting work" for the whole app.
- **`process-bound` vs `thread-safe` is a *test-design* distinction, not a flakiness workaround.** Eight suites are process-bound because they touch process-global state, process APIs, or timing-sensitive process I/O; they get their own Vitest project so the rest of the inventory can stay in one project and still fork.
- **Coverage exclusions are computed, not listed.** The pwsh exemption is decided by *running* `pwsh -Command '$true'` at config load (`vitest.config.ts:130-140`), so the exemption is active exactly when the suites self-skip. The other exclusions are platform-conditional at config load, which means **the coverage gate differs per platform** and a Windows run genuinely measures less.
- **The `__esDecorate(` compiler artefact is annotated with `v8 ignore` before transpile output is accepted.** `vitest.shared.ts:36-39` — without it, compiler-generated accessor boilerplate would count against the 100% per-file gate.
- **The Office engine resolver fails closed but leaves third-party engines alone.** `apps/desktop-host/src/office-engine.ts:35-46` — a matching request that resolves *inside the archive but outside the runtime package directory* throws; a matching request that resolves *outside the archive entirely* is left untouched. Both halves of that rule are deliberate and both are pinned by tests.
- **The desktop-host's `import.meta.dirname` depth assumption.** `apps/desktop-host/src/cli.ts:34` resolves the runtime as `resolve(import.meta.dirname, '../../../..')` — the CLI only works when the bundler placed `lib/cli.js` at exactly that depth.
- **The `.i18n.yaml` ledger hashes *per heading section*, so renaming a heading breaks the record.** The hashes are keyed by the heading's slug path (`/safety/no-warranty-or-liability`); a heading rename is a ledger edit, not just a prose edit.
- **The lockfile is the supply-chain authority, not the notices file.** `THIRD_PARTY_NOTICES.md` says so explicitly: "The complete npm transitive closure … is recorded with exact pinned versions in `pnpm-lock.yaml` — inspect it with `pnpm licenses list`."

## 5. Weak spots

- **The root `package.json` is ~250 scripts, most of them single-purpose `verify-*`/`gen-*` gates.** Roughly 60 `verify-*` and ~20 `gen-*`/`verify-*` pairs each own a bespoke script under `scripts/`. Every one is a maintenance liability and a place for a rule to be enforced in two places and drift. The `check:ci:*` matrix (`run-gates.ts ci-primary`, `ci-linux-primary`, `ci-static`, `ci-coverage`, `ci-unit`, `ci-bench`, `ci-snapshot`, `ci-artifacts`, `ci-consumers`, `ci-windows-*`) is the only thing keeping this from being unmaintainable — but it means the *gate list itself* is now a configuration surface that needs its own gates.
- **The "100% per-file coverage" claim is undermined by a very long exemption list.** `vitest.config.ts` contains ~100 exclusion globs (the whole `packages/client/ui-*/src/client/*` tree, the inspector bridges, the webworker runtime, the Typert generator, self-modification). Each is individually justified, but the aggregate means the headline number describes a much smaller surface than the repository. The `TODO(gui): cover and remove` comments are the honest bookkeeping, but a reader of the badge alone would be misled.
- **The coverage gate is platform-dependent, so "covered" means different things per OS.** `vitest.config.ts` computes exclusions from `process.platform` at config load. A Linux CI run and a Windows CI run enforce different per-file bars, and a file can be fully covered on one platform and exempt on the other with no single artifact saying so.
- **The i18n pairing ledger is brittle.** Hashing per heading section means any heading rename, any added code fence, or any whitespace change on one side requires re-recording the *other* side's hash too. It detects drift but couples two files that are supposed to be independent translations.
- **The desktop-host duplicates the browser-use / computer-use registries and the brand modules verbatim.** Four files, two pairs, near-identical. The duplication gate's `minTokens: 60` is tuned so it does not fire, and the package group is only two packages, so no shared seam was worth extracting yet — but the pattern does not scale past a handful of capabilities.
- **`tsconfig.base.json` is a 563-line file whose entire middle is generated.** The hand-written part is ~30 lines of compiler options; the rest is a machine-written `paths` map. A reader (or a human editing it) can easily break the resolution graph, which every Vitest lane depends on. The `gen-tsconfig-paths`/`verify-tsconfig-paths` pair is the only guard.
- **Some rules in `AGENTS.md` are unenforceable by machine and therefore depend entirely on review** — "ban `prove` + `nance`", "keep comments local", "prefer symmetry for parallel values", "no metaphors". They are stated with the same authority as the machine-checked ones, so a reader cannot tell which rules will actually be caught.
