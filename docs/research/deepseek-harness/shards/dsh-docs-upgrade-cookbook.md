# deepseek-harness :: dsh-docs-upgrade-cookbook

**Files in shard:** 244 (read: 164, skipped with reason: 80)
**What this shard covers:** This shard is DeepSeek Harness's *documentation corpus* — the handbook, not the code. It holds four bodies of prose: (1) the **cookbook** (`docs/cookbook/`) — how to add a package, a tool, an LLM adapter, a Remote API endpoint, a settings card, a Session log format version, a vendored package, a plugin preview, and how to run code review and stacked-PR review; (2) the **Cordis** plugin-framework reference and hands-on tutorial (`docs/cordis-api/`, `docs/cordis-tutorial/`) — the Context/Event/Fiber/Registry/Service API and a seven-chapter runnable tutorial; (3) the **defensive-patterns** rules (`docs/defensive-patterns/`) — 30+ hard-won "rule + the defect it prevents" statements across package surface, remote/API, client components, conversation/Session, and general bug classes; (4) the **i18n**, **postmortem** and **upgrade-guide** corpora — the bilingual-pairing contract, four incident write-ups, and 42 per-release migration guides. Every English `.md` has a Simplified-Chinese mirror (`.zh.md`) and a generated per-section hash record (`.i18n.yaml`). There is no source code in this shard, but the rules it states are the most prescriptive part of the whole repository, and they are the load-bearing material for a trading app: turn boundaries, tool contracts, projection-as-single-read-path, retention/GC, evidence requirements, and the failure taxonomies.

### Tier 2 — English source documents (84 files, read in full)

#### `docs/cookbook/adding-a-package.md`
- **Purpose:** The file-by-file checklist for creating a new `@deepseek-ai/dsh-<name>` workspace package, validated against the bash and adapter packages as templates.
- **Key abstractions:** A **role-naming table** (Controller / Store / Directory / Presenter / Registry / Runtime / Resolver / Binder / Engine / Policy / Executor / Gateway / Provider / Backend / Handle / Config / Service) with an explicit "use it when / do not use it when" column for each — a naming standard that is unusually precise for a repo. Singular vs. plural `ctx` key agreement is mandatory. "Name the stable current responsibility" — never the first implementation, a possible future expansion, or the Cordis base class.
- **Data flow:** New package → `package.json` invariants (enforced by `pnpm run constraints` / `scripts/check-workspace-constraints.ts`) → root `tsconfig.base.json` / `tsconfig.host.json` references → package README → optional `locale/en.json` display metadata → verification.
- **Non-obvious design decisions:** The **Model Experience** README template (`docs/cookbook/adding-a-package.md:105`) — every package README must document what the *model* sees, its token effect, and its KV-Cache effect, with three ordered H4 fields, plus a mandatory **"Known Limitations and Deferred Work"** section (or a whitelist entry in `scripts/verify-package-readme-limitations.ts`). A package with no context effect uses one audited sentence (`None, as ` / `Indirectly, through `) and is then done — it may not expand into a description of another package's work. `SDK` is reserved for the JSON-RPC client/server protocol; the harness itself "is an agent harness, not an SDK project."
- **Edge cases & failure handling:** `exports` map is restricted to a standard key set; subpath plugins never read a `package.json`. Plugin display metadata falls back *independently* per field (locale title → package name → complete Cordis plugin name). Malformed JSON or invalid fields produce a per-plugin diagnostic while retaining valid text, without attempting the export.
- **Surprising:** The "change face equal to the review face" idea repeated in every file — a change carries only the lines its stated behavior change needs.

#### `docs/cookbook/adding-a-plugin-preview.md`
- **Purpose:** Governs the internal `BUNDLE_PREVIEWS` map in Plugin Manager — the illustrations for built-in bundles.
- **Key abstractions:** A fixed **640×300 (32:15) SVG** contract, en+zh pair, self-contained (no fonts, remote resources, scripts, `text`, or `foreignObject`), combined size ≤ 1 MiB, rendered via `<img>` so SVG is treated as an image and never inlined HTML.
- **Data flow:** SVG pair under `packages/client/ui-plugin-manager/src/client/assets/` → imported into `PluginManagerPage.tsx` → one entry in `BUNDLE_PREVIEWS` → the page renders one `<img>` at ≤320 px height with the page supplying border and 16 px corners.
- **Non-obvious design decisions:** **Omission reserves no space** — "no image is required, and omission reserves no space." Third-party plugins have *no* preview interface at all; the map is internal and closed. A brand asset may be embedded as a base64 data URL (the one raster exception), but validation checks the data-URL envelope, not decoded pixels.
- **Edge cases & failure handling:** Decode failure shows a localized notice without blocking controls; lists and component rows keep their small icons. Visual quality and bilingual meaning-equivalence still require human review even when the format gate is green.

#### `docs/cookbook/adding-a-remote-api.md`
- **Purpose:** The five steps to add or change a `ctx.remote` endpoint.
- **Key abstractions:** One error class, `RemoteError`, plus a `<domain>/<reason>` code table merged into `RemoteErrorDetailsMap` by declaration merging. `RemoteResult<T>` on the client (an `ok`/`error` discriminated union, **not** a thrown exception).
- **Data flow:** Host-side `TypertRemoteService` subclass → `@Remote` decorator on the *business* method → `remoteExport*` adapter only when the shape must change → `build:lib` regenerates the client declarations and codecs → client calls `ctx.remote.<namespace>.<method>()` and branches on `if (!result.ok)`.
- **Non-obvious design decisions:** **Four placement rules for a failure code** (one producer declares it next to the throw; several producers declare it in the lowest domain package both depend on; carrier codes `gateway/bad-request` / `gateway/cancelled` / `gateway/internal` are declared in protocol and never copied; a local failure that never crosses the wire stays out of the code table) — `docs/cookbook/adding-a-remote-api.md:51`. The result type is *not* an exception: "A Remote call does not reject, and an assembly mistake should crash." A defensive `catch` is written only to separate a Remote failure from a local defect, using `isRemoteFailure`.
- **Edge cases & failure handling:** The caller aborting a unary call yields `gateway/cancelled` on the error branch rather than a throw. `ctx.remote.$host.home` is `undefined` until the first ready frame and must be refreshed on `connection/reset`. Lookup objects (`Agent`, `Session`) may only occupy top-level parameter positions; `signal: AbortSignal` is always the final parameter.
- **Surprising:** `build:lib` is mandatory once a signature, code table, namespace, or export name changed, because that is what hands the client its codecs — a body-only change needs no regeneration.

#### `docs/cookbook/adding-a-session-format-version.md`
- **Purpose:** How to introduce the next Session log format version without rewriting released data.
- **Key abstractions:** A **per-artifact `Stage` interface** (`transformEvent`, `transformRun`, `finish`) rather than a whole-artifact array-to-array migrator; adjacent N→N+1 migration *edges* as library packages; a generated migration catalog with a declared chain.
- **Data flow:** `SESSION_FORMAT_VERSION` constant → `gen-session-format-catalog` (which rejects gaps, duplicate edges, unknown metadata members) → per-edge `createStage` → strict restore through `sessionFormatCatalog.createRestore(header, { recovery: 'strict', validation: 'current' })` → published successor beside an unchanged source.
- **Non-obvious design decisions:** **"Bump the format only when an effective discriminator cannot prevent unsafe interpretation"** — `docs/cookbook/adding-a-session-format-version.md:23`. A structural change to headers, event envelopes, or semantics goes to a reader-compatibility *review*, not an automatic bump. Each integer therefore identifies a *family* of supported representations, not one fixed schema; same-version logs bypass adjacent migrations and can mix historical and newer record variants after resume. A released codec may never be broadened to admit a current feature; the N→N+1 converter may take fixes after N+1 ships if the output stays compatible.
- **Edge cases & failure handling:** "Never substitute zero for an unknown cut" — `headerInheritedEventCount` is exposed only when known before EOF. The inherited cut is a *logical* event count, not a physical row count. Alpha converters may explicitly refuse historical cases and publish no partial successor. "Use native writer output as the conversion oracle" — replay the same inputs through old and target writers and compare.
- **Surprising:** The **V4 corpus migration** (`docs/cookbook/adding-a-session-format-version.md:122`): a bounded queue, `--jobs N`, per-Session outcomes, one sequential retry only for the source-change error, JSON + `summary.json` + `migration.log` reports, nonzero exit on any failure. And the frozen V3 event vocabulary check (`verify-v3-event-vocabulary --source-ref`), which pins the last V3 writer commit so later V4 additions cannot leak into the frozen set.

#### `docs/cookbook/adding-a-settings-card.md`
- **Purpose:** Declaring live configuration fields in a plugin Config schema and exposing them through a product-owned settings card.
- **Key abstractions:** `Volatile<T>` references (read via `.get()`, updated without remounting the plugin); `role('secret')` to keep a value out of form responses; `.check()` for cross-field validation that runs on the Host *before* persistence and is omitted from serialized form schemas.
- **Data flow:** Custom plugin pages receive `form.state` and `form.mutate(operations, expectedRevision)` — `docs/cookbook/adding-a-settings-card.md:42` — the Host validates the full Config and applies edits through ConfigEditor and volatile HMR.
- **Non-obvious design decisions:** **Revision-based optimistic concurrency** on form mutation (`expectedRevision`). Slot contributions to another plugin's page return `null` for a subject they have nothing for. The browser half attaches to the Loader row whose specifier is the *bare package name* — a subpath-mounted row never carries a half, so a bundle split across several rows keeps its half on the root row and every page it registers disappears when that row is switched off.
- **Edge cases & failure handling:** Reject an invalid value and verify that neither the file nor the live value changed.

#### `docs/cookbook/adding-a-tool.md`
- **Purpose:** The reference for the contracts a model-facing tool must satisfy — the single most transferable document in this shard for a trading app.
- **Key abstractions:** `defineTool({ name, description, parameters, output: { schema, render }, execute })`; `ParameterSchemaSpec` / `ValueSchemaSpec`; `exec` carrying immutable identity (`callId`, `name`, `arguments`, `agent`, `token`, `signal`, optional `parent`); `output.presentationMeta(args, value)` for replayable card data; `presentCall` / `presentResult` returning a `card`-tagged render intent (`generic` / `terminal` / `diff` / `read` / `search` / `web`).
- **Data flow:** Model emits `arguments` → registry materializes them as detached lossless JSON, **freezes before policy starts**, assigns an opaque `exec.token` → pre-execute policy → execute → canonical JSON value → snapshot/validate/freeze → `output.render` for the model, `presentationMeta` for the durable card → `tools/result` observers.
- **Non-obvious design decisions:** **"Throwing or returning an invalid value means `isError`"** — `docs/cookbook/adding-a-tool.md:46` — so a *successful* domain outcome must be represented in the canonical value even when the renderer explains a non-ideal state (a non-zero process exit). The registry catches throws and contains schema, renderer, metadata-projector, and lossless-JSON failures *before observers run*. Presenters must be **pure functions of `args` (+ the result)** — no I/O, no session state, no clock/random — because they run on live streaming *and* on session-log replay; `defineTool` soft-validates the display path so malformed logged arguments return `undefined` rather than throwing. UI-only formatting (fences, diffs, relativized paths) never enters the canonical value.
- **Edge cases & failure handling:** `ctx.tools.guard()` for a monotonic final deny that later listeners cannot undo; `tools/execute` for deadline/retry/metrics; `tools/post-execute` for replacement; `tools/result` for observation of the immutable outcome. Background work goes through `ctx.jobs.start({ kind, label, owner: exec.agent, run })`; once the id is published, ownership moves to the *task* signal, not `exec.signal` — later outer cancellation stops waiting but does not kill published work. A pre-aborted call is a failure because no task exists whose id could satisfy the successful output schema.
- **Surprising:** In PTC mode every visible tool is reachable as `await tools.<name>(args)` with **exact argument and return types derived from the same schemas**, and a failed call rejects with the real `ToolCallError` from which a program can inspect only `name`, `toolName`, and `message` — never internal codes.

#### `docs/cookbook/adding-a-vendored-package.md`
- **Purpose:** Adding an upstream Cordis package as pinned source under `vendor/` rather than as an npm dependency.
- **Key abstractions:** The `vendor/<dir>/` layout, `tsconfig.json` strictness relaxations, and the project-reference graph as the isolation boundary.
- **Data flow:** Copy upstream `src/` verbatim → rescope the name → register in `tsconfig.base.json` `paths` and `tsconfig.host.json` `references` → add a `vendor/README.md` manifest row (dir, npm name, version, upstream repo, commit SHA) → `scripts/check-vendor-manifest.sh` pre-commit guard.

Vendoring one package often means vendoring its dependency tree. The manifest guard fails the commit if source is staged without the manifest row, so the manifest is part of the change, not a follow-up.
- **Edge cases & failure handling:** Local relative imports in vendored TS use explicit `.ts` specifiers — a repo-local build difference from upstream.

#### `docs/cookbook/adding-an-llm-adapter.md`
- **Purpose:** Connecting a new model provider — the protocol contract two reference implementations were verified against.
- **Key abstractions:** `LlmAdapter` subclass, `ctx.llm.registerAdapter([...], adapter)`, `StreamChunk`, `LlmError` with a stable code, `resolveModel()` capability seam, `finish.replayState`.
- **Data flow:** `options.provider` selects the adapter, `options.model` is the provider model id → the adapter streams `StreamChunk`s → `usage` then `finish` → `LlmRuntime` normalizes failures into terminal finish chunks.
- **Non-obvious design decisions:** **"Emit `usage` BEFORE `finish`; emit NOTHING after `finish`"** — `docs/cookbook/adding-an-llm-adapter.md:27` — with the robust method being to buffer finish/usage until the provider's end-of-stream marker, because some providers send trailing usage-only chunks. Tool-call `arguments` stay **raw JSON strings end-to-end** (re-stringify at `block-end` if the provider hands back parsed objects). Block `index`es are allocated in first-seen stream order and reused for every delta of the same block.
- **Edge cases & failure handling:** **Exactly two sanctioned error paths** — throw from `stream()` (transport/protocol) or end the stream with `finish {kind: 'error' | 'aborted'}` (provider in-band failure) — `docs/cookbook/adding-an-llm-adapter.md:30`; a `GenerateOptions` field the provider cannot honor throws `LlmError(..., 'UNSUPPORTED_OPTION')` rather than being silently dropped. `finish.replayState` carries native metadata, passed only when the historical and target provider routes are owned by the *exact same adapter instance* — never inferred from provider/model names.
- **Surprising:** Reasoning efforts are *ordered opaque ids* mapped to provider requests by the adapter; an id need not equal its wire spelling, and an adapter-defined `off` must be preserved.

#### `docs/cookbook/extension-cookbook.md`
- **Purpose:** Reference patterns for harness extensions plus **the feature → mechanism map** — a table mapping every product feature to the extension point that implements it.
- **Key abstractions:** Tool plugin, hook plugin (the `tools/pre-execute` permission gate), UI plugin, external protocol driver; the `ctx.tools.guard()` / `tools/execute` / `tools/post-execute` / `tools/result` selection rule.
- **Data flow:** A protocol driver adapts a wire peer to `ctx.agents`; a low-level prompt request returns its **durable enqueue receipt** and does *not* acquire a result by correlating `MessageId` with `turn/end`; whole-agent status is published separately; teardown goes through `AgentHandle.dispose()` so disposal reaches quiescence.
- **Non-obvious design decisions:** The map's claim is that "the microkernel claim made checkable" — **no row modifies the loop** — `docs/cookbook/extension-cookbook.md:98`. `system-prompt/assemble` is an *expert cooperative whole-assembly transform* whose returned assembly is authoritative, so listener authors own preserving active PTC mode and structured-output contributions. `ctx.tools.restrict()` is preferred over ad-hoc tool filtering because it keeps presentation, lookup, and execution aligned.
- **Edge cases & failure handling:** Scheduled work is a plugin registering model-callable scheduling tools; a due timer delivers through `followup(…, {source: {kind: 'schedule'}})` — `docs/cookbook/extension-cookbook.md:127`. Every registration is a `ctx.effect`, which is why vendored HMR "just works".

#### `docs/cookbook/maintaining-dsh-code-review.md`
- **Purpose:** The operator contract for the periodic maintenance of the `dsh-code-review` skill by a single designated operator running a private tool.
- **Key abstractions:** Two independently configured reviewer adapters; a promotion manifest; three operator decisions (discard / batch / promote).
- **Data flow:** Daily run with a **two-UTC-day overlap** (weekly recovery uses seven days) → select merged PRs whose merge commit is reachable from `origin/master` → collect pre-merge human review feedback with commit anchors → compare feedback-time and final landed patches → adapters classify authorship and adoption → primary adapter drafts a revised `SKILL.md` → **both adapters review the same diff; blocking findings loop until both approve** → `doc-sync` + `lint` against the candidate → artifacts under `~/dsh-code-review-outputs/`.
- **Non-obvious design decisions:** The tool refuses to run when the two reviewer commands resolve to byte-identical executables, and a batch whose adapter response fails schema or id validation is **failed closed at the batch level** (every item marked unclear) rather than dropped. PRs whose merge commit is unreachable (squashed parents) or beyond a 250-commit cap go to `skipped-pulls.json` and are skipped, not fatal. It deliberately does *not* acquire PR conversation comments because current GitHub state cannot give a force-push-safe feedback-time baseline.
- **Edge cases & failure handling:** **"No candidate" is the common case and sends no notification**, to avoid alert fatigue — `docs/cookbook/maintaining-dsh-code-review.md:50`; days without a skill update are the workflow behaving correctly. The operator reads the diff on its own merits and does not defer to "the reviewers approved". A total-provider outage never collapses into "no candidate".
- **Surprising:** The manifest links each proposed rule back to the source human feedback URL and the landed commit range — the *evidence* is the artefact, not the diff. The single-maintainer bus factor is called out as needing a documented handoff decision.

#### `docs/cookbook/responding-to-pr-review-on-a-stack.md`
- **Purpose:** Review-fix placement and propagation across a dependent stack of PRs (`A ← B ← C …`).
- **Key abstractions:** One worktree per PR branch; GitHub's `PullRequest.stack` / `stackEntry.position` as the authoritative stack evidence; merge-forward vs. native cascading rebase.
- **Data flow:** A comment on `B` pointing at code `B` introduced → fix lands on `B` → `B` is propagated into `C` → each fix remains a distinct commit → the official stack procedure lands them.
- **Non-obvious design decisions:** **"A fix lands on the PR that INTRODUCED the issue, then flows up-stack"** — originating it downstream leaves `B` shipping the unfixed code and hides the fix from `B`'s reviewer. A regression guard must be proven to **fail on the unfixed code** (introduce it, watch red, revert) — "a guard that passes both ways guards nothing." A rewritten push must be lease-protected and abort rather than overwrite a concurrently advanced remote head; raw `--force` is forbidden.
- **Edge cases & failure handling:** After any rewritten push, re-read unresolved threads, approvals, mergeability, and checks — a force-pushed OID or a stale inline anchor is not current evidence. A sub-agent that reframes a problem as already handled is a signal to dig in personally.

#### `docs/cookbook/reviewing-persistence-type-changes.md`
- **Purpose:** The procedure for changing a declared Session persistence type, with a bilingual compatibility explanation and one command to classify and record it.
- **Key abstractions:** Per-root before/after digests; a `formatVersion` for normalization rules; `--decision same-version` vs `--decision version-bump`.
- **Data flow:** `verify-persistence-changes --json` (read-only preview) → a local prose JSON with `en`/`zh` × `summary`/`compatibility`/`verification` → `persistence-changes --record` / `--update` → generated record pair, after-schemas, catalogs, machine inventory, pairing records → `doc-sync`.
- **Non-obvious design decisions:** **A structural difference can remain same-version with evidence of safe interpretation or refusal; it does not automatically require a higher writer version** — `docs/cookbook/reviewing-persistence-type-changes.md:51`. An *actual* header-version increase can infer `version-bump`, but a flagged change with an unchanged header and no explicit decision fails with `decision-required`. The update command refuses the initial baseline, records another record depends on, and finalized checkpoint records. "Routine changes never create another baseline."
- **Edge cases & failure handling:** `--silent` is required when consuming JSON because pnpm otherwise appends lifecycle text to stdout. A stale generated inventory fails verification. Storage compaction does not change root fingerprints and needs no acknowledgement.

#### `docs/cordis-api/context.md`
- **Purpose:** Generated API reference for the Cordis `Context` — the root and child dependency container.
- **Key abstractions:** `extend(meta?)` (prototypal child, parent unmutated), `isolate(name, label?)` (independent service scope; the same label joins two scopes), `intercept(name, config)` (service-specific config merged ancestor-first), the service store (`get`/`set`/`provide`/`accessor`/`mixin`).
- **Data flow:** Normal property reads go through the service resolver; `provide` returns a disposer that unregisters the service and wakes dependents; `mixin` exposes selected service members directly on `ctx` as accessors that forward and bind methods.
- **Non-obvious design decisions:** `Context.is(value)` works **across realms and across multiple copies of cordis** because the brand is keyed by a global symbol rather than `instanceof`. `ctx.get(name, strict = true)` returns `undefined` for a service whose providing fiber is not currently active — that is the "strict" default.
- **Edge cases & failure handling:** `set` on an unprovided name throws; `provide` throws if the name is already provided in scope or declared as an accessor.

#### `docs/cordis-api/events.md`
- **Purpose:** Generated reference for the event-dispatch API mixed into every context.
- **Key abstractions:** Five dispatch modes — `emit` (sync broadcast, returns ignored), `parallel` (all concurrent, awaited together), `serial` (in order, first bail wins), `bail` (synchronous serial), `waterfall` (around-middleware with a `next` continuation).
- **Data flow:** `ctx.on(name, listener, options)` returns a disposer; listeners are **owned by the current fiber**, so they vanish with it. `EventOptions` has `prepend` and `global` (receive regardless of context filter checks).
- **Non-obvious design decisions:** The dispatch mode is **part of the event's contract** — "Which one an event uses is part of its contract — it decides whether listeners can return values, run concurrently, or short-circuit each other." The `DispatchMode` union is exported as a named type (`docs/cordis-api/events.md:189`).
- **Edge cases & failure handling:** `bail`/`serial` treat the first non-`null`/non-`false`/non-`undefined` return as the bail value.

#### `docs/cordis-api/fiber.md`
- **Purpose:** Generated reference for the Fiber — one loaded plugin instance's lifecycle, config, and effects.
- **Key abstractions:** `ctx.effect(execute, label?)`; `Effect` (a disposer, a promise of one, or a possibly-async iterable of them); `EffectMeta` diagnostics tree; `CordisError` with the stable code `INACTIVE_EFFECT`; `ValidationError`.
- **Data flow:** `execute` runs immediately; its disposers are collected and run **in reverse order** either when the returned disposer is called or when the fiber unloads, whichever comes first; calling the disposer twice is a no-op. `fiber.update(config, noSave?)` runs the `internal/update` waterfall first so hooks and HMR can veto or replace the restart.
- **Non-obvious design decisions:** `fiber.inertia` is the in-flight load/unload transition, so a caller can await the current transition rather than assuming it finished. `fiber.await()` rethrows startup errors, so a config-validation failure is never swallowed into "pending".
- **Edge cases & failure handling:** `ctx.effect` on an already-disposed fiber throws `CordisError('INACTIVE_EFFECT')`; an invalid effect shape throws `TypeError`.

#### `docs/cordis-api/inherited.md`
- **Purpose:** The terse summary of the *vendored* Cordis API every harness plugin inherits — the framework tier beneath the harness tier.
- **Key abstractions:** The `ctx` member list (`on`/`once`, the five dispatch methods, `plugin`/`inject`, `effect`, `get`/`set`/`provide`/`accessor`/`mixin`, `extend`/`isolate`/`intercept`, `root`/`fiber`/`registry`/`reflect`/`events`/`logger`, `timer` + its four helpers, `loader`); the inherited event list (`internal/plugin`, `internal/status`, `internal/service`, the `internal/update`/`internal/config`/`internal/get`/`internal/set`/`internal/listener`/`internal/dispatch` waterfalls, `exit`, and the `loader/*` events).

#### `docs/cordis-api/registry.md`
- **Purpose:** Generated reference for plugin loading and dependency injection.
- **Key abstractions:** `ctx.inject(deps, callback)` and `ctx.plugin(plugin, ...args)`; three plugin shapes (Function, Constructor, Object); `Plugin.Runtime` (the mutable record shared by all fibers of one callback, holding a `DisposableList<Fiber>`); `Inject.resolve` normalizing array/object/class-inherited declarations.
- **Data flow:** `ctx.plugin` validates config against the plugin's `Config` schema, then returns a `Fiber & PromiseLike<Fiber>` — awaiting it settles once loading finished, **rejecting on config or startup errors**.
- **Non-obvious design decisions:** `inject` is shorthand for `ctx.plugin({ inject, apply: callback })`, and the callback is unloaded and re-run whenever a required service changes. The `Runtime` record's `callback` is the **registry identity key** — every fiber of one plugin shares it.
- **Edge cases & failure handling:** `Plugin.Base` carries `name`, `Config`, `inject`, `provide`, and `intercept` — `intercept` names services whose intercept config the plugin *declares it consumes*.

#### `docs/cordis-api/service.md`
- **Purpose:** Generated reference for the `Service` base class.
- **Key abstractions:** `super(ctx, name)` registers the instance as `ctx.<name>` and removes it automatically with the owning fiber; seven symbol-keyed extension points (`init`, `check`, `config`, `invoke`, `extend`, `tracker`, `resolveConfig`).
- **Data flow:** The service registers immediately at construction and is removed with the fiber — no explicit unregister.
- **Non-obvious design decisions:** The extension points are all **symbol-keyed statics** rather than overridable methods, so a subclass opts in by declaring the symbol rather than by overriding a method (and the harness can detect which capabilities a service has).
- **Edge cases & failure handling:** `Service.check` is the availability predicate passed to `ctx.provide()`; `Service.config` is a phantom intercept-config type parameter.

#### `docs/cordis-tutorial/01-first-plugin.md`
- **Purpose:** The smallest possible plugin and the loader that mounts it.
- **Key abstractions:** A function plugin exporting `apply(ctx)` (plus an optional `name`); the three accepted plugin shapes.
- **Data flow:** `cordis.yml` entry → Loader resolves `./hello.ts` → mounts it as a child plugin → Cordis calls `apply(ctx)`.
- **Non-obvious design decisions:** **"Entries start concurrently, so list position guarantees nothing about which plugin loads first; ordering comes from service dependencies (`inject`), not from position in the file."** A plugin that fails to load is a *loud* failure, not a skipped entry.
- **Edge cases & failure handling:** A config entry whose module cannot be **resolved** (typo'd path or package name) is reported through the Cordis logger service instead of crashing the process, and at boot that report can be lost before a console exporter is watching — "If a freshly added entry seems to do nothing, check the spelling first."

#### `docs/cordis-tutorial/02-lifecycle-and-effects.md`
- **Purpose:** Effects, the fiber state machine, and disposal ordering.
- **Key abstractions:** `ctx.effect(() => { …; return disposer })`; the fiber states `PENDING → LOADING → ACTIVE → UNLOADING → DISPOSED` with `↘ FAILED`.
- **Data flow:** The effect body runs during load; the disposer it returns runs during unload. `fiber.dispose()` resolves after all cleanup — including async disposers — and recursively unloads child plugins.
- **Non-obvious design decisions:** **"Disposers start in reverse registration order, but multiple async disposers run concurrently"** — so teardown steps that must run in sequence go in one disposer and are awaited there. A PENDING fiber does not keep Node's event loop alive, so a composition with nothing else running exits 0 *silently*.
- **Edge cases & failure handling:** Registrations made through Cordis APIs (`ctx.on`, `ctx.plugin`, service registrations, `ctx.tools.register`) are effects already; only foreign resources need manual wrapping.

#### `docs/cordis-tutorial/03-services.md`
- **Purpose:** Providing a service and consuming it with `inject`.
- **Key abstractions:** `Service` subclass + `super(ctx, 'greeter')` for runtime; `declare module '@deepseek-ai/cordis' { interface Context { greeter: GreeterService } }` for compile time; `ctx.get('greeter')` for optional dependencies.
- **Data flow:** A consumer declaring `inject = ['greeter']` is held PENDING until the service exists, so inside `apply` `ctx.greeter` is guaranteed ready. If the service disappears while the app runs, **every dependent plugin is unloaded too**, and loads again when the service returns.
- **Non-obvious design decisions:** The dependency relation is **tracked after load**, not just a boot check — combined with effects, this prevents a running consumer from retaining a reference to an unavailable service. Service names live in **one flat namespace per application**, so a plugin must namespace its own.
- **Edge cases & failure handling:** Removing the provider leaves the consumer PENDING — no crash, no partial run, and a silent exit 0.

#### `docs/cordis-tutorial/04-events.md`
- **Purpose:** Declaring, emitting, and listening to typed events; the five dispatch modes; the waterfall.
- **Key abstractions:** `interface Events { 'stats/report'(name: string, count: number): void }` declaration merging; the `namespace/action` event-name convention; the `next` continuation in a waterfall.
- **Data flow:** `ctx.emit` → typed listeners → a listener that only observes must call `next()`, otherwise it silently swallows the default behavior for everyone downstream.
- **Non-obvious design decisions:** **"A waterfall listener that only observes or annotates must call `next()`; returning without it is a deliberate short-circuit"** — forgetting it is a standing rule of the repository. The harness uses waterfalls for decisions cooperating plugins may wrap or answer: `agent/request` (replace the model-call config) and `approval/request` (a policy answers instead of the user).
- **Edge cases & failure handling:** Because `ctx.on()` is an effect, the listener disappears with the plugin — no manual `removeListener` bookkeeping.

#### `docs/cordis-tutorial/05-config.md`
- **Purpose:** Validated configuration from `cordis.yml`, and the volatile-field mechanism.
- **Key abstractions:** `export const Config: Schema<Config> = Schema.object({...})` — the *same name* is both the TypeScript interface and the runtime schema; `.volatile()`; `!!js` for computed values.
- **Data flow:** The Loader compares raw config while ignoring schema-declared volatile fields; a volatile-only change is parsed through the plugin's `internal/config` hook and validated; when every ordinary effective value still matches, the Loader commits new values into the running references and emits **one instance-local `loader/volatile-update`** with the changed paths as arrays of keys, bypassing the target plugin's `internal/update`.
- **Non-obvious design decisions:** The Loader compares raw config while ignoring schema-declared volatile fields; a volatile-only change is parsed through the plugin's `internal/config` hook and validated; when every ordinary effective value still matches, the Loader commits new values into the running references and emits one instance-local `loader/volatile-update` with the changed paths as arrays of keys, bypassing the target plugin's `internal/update`. Volatile references hold **detached, recursively frozen snapshots** of plain data; functions, class instances, and cycles are rejected. Volatile fields must be declared at fixed object paths — independent references inside arrays, dictionaries, union/intersect branches, lazy schemas, transforms, or another volatile value are rejected.
- **Edge cases & failure handling:** Invalid config fails the load with a precise `ValidationError` and the fiber goes to FAILED; the plugin never starts half-configured. An invalid volatile candidate is logged and leaves the running references unchanged until the next activation. Equal values do not notify.

#### `docs/cordis-tutorial/06-composition-and-hmr.md`
- **Purpose:** Treating `cordis.yml` as the application, hot module replacement, and diagnosing a plugin that never loads.

- **Data flow:** The loader diffs entries by `id` and mounts/unmounts/reconfigures only what changed. An entry *without* an `id` gets a generated id on every read, so after any config-file edit it counts as removed-plus-added and remounts even if its own lines did not change.

#### `docs/defensive-patterns/README.md`
- **Purpose:** The index and the five habits that the whole directory applies to each artifact class.
- **Key abstractions:** **Make correctness explicit** (named call points, explicit lifecycles, explicit conditions and types) rather than compensating afterwards with timing; **keep one source of truth** (one read path, one home, one owner); **extend through the registered seam** (a new capability registers; an existing carrier stops taking new logic instead of growing a branch inside it); **keep the change face equal to the review face**; **require evidence** (a claim is falsifiable and recomputable, not kept in sync by hand).
- **Data flow:** A routing table maps "what you are changing" to "which page to read", and `dsh-code-review` reads this directory when judging a pull request; Development routes through the same table from `AGENTS.md`.
- **Non-obvious design decisions:** Every rule is stated as **the rule plus the defect it prevents** — a "bug-class" framing rather than a style guide.

#### `docs/defensive-patterns/general.md`
- **Purpose:** Fifteen bug-class rules for lifecycle, concurrency, subprocess, and teardown code — the most directly stealable page in this shard.
- **Key abstractions:** The rules, each with a "judged condition", a boundary, and a correct/wrong example: orthogonal outcome reporting; public contracts on both sides; async ≠ sync; timing does not carry correctness; optional inputs state both behaviors; one value states one fact; no new `active`/`current` singleton; shared state has one owner; a business capability owns itself; changes carry performance evidence; migrations preserve behavior; dispose reaches quiescence; contain callback exceptions; never hand untrusted output the ambient environment or predictable paths; unlink link-shaped paths.
- **Data flow:** Each rule is a gate for review, not a runtime mechanism: "the shape of the report" is judged, "the mechanism that produced it" is a separate decision.
- **Non-obvious design decisions:** **"A result can be several things at once — a process can time out AND exit 0 because it trapped the signal"** — `docs/defensive-patterns/general.md:7` — so each independent fact (`timedOut`, `signal`, `exitCode`) must be readable *without entering another condition's branch*. **Never treat `agent/status` or `whenIdle()` as the result of one follow-up** — `docs/defensive-patterns/general.md:19` — several queued follow-ups, steering, and injected work may share one `running` interval. **Accumulating `?.` is the signal** that a determination about whether a field should exist has been replaced by a fallback — `docs/defensive-patterns/general.md:48`. **Unknown / empty / absent are three different facts** with three representations — `docs/defensive-patterns/general.md:71`. **A module-level cache, singleton, global `WeakMap`, or `globalThis.__X__` bypass hides the owner** and outlives every teardown — `docs/defensive-patterns/general.md:104`.
- **Edge cases & failure handling:** The performance rule names three metrics (runtime, peak memory, steady-state memory) measured in **one environment on one input**, at the granularity of the changed path — and warns that comparing old vs. new with the same measurement hook on both sides **dilutes the difference until it disappears**. A CI benchmark gate is "an alert, not a pass". A migration must keep error codes, diagnostics, data-flow order, and UI timing equal item by item; a defect found during a migration is its own change. Spawned commands get a **scrubbed env** (drop `*KEY*`/`*SECRET*`/`*TOKEN*`/`*PASSWORD*`); temp/spill files use a private 0700 dir, random names, and exclusive owner-only opens (`'wx'`, `0o600`) to prevent symlink races. Link-shaped paths are removed with `lstatSync().isSymbolicLink()` then `unlinkSync`, because Windows `rmSync(link)` throws `ERR_FS_EISDIR` on a junction and recursive deletion may descend through it into the target.

#### `docs/defensive-patterns/conversation-and-session.md`
- **Purpose:** Rules for reading a Session, holding one, computing conversation nodes, and rendering them.
- **Key abstractions:** **Projection** as the only read-and-compute path (`ProjectionDefinition` with `key`, `stateVersion`, `init`, `apply`, `wire`); `SessionReference` with `retain`/`release`; `ConversationNodeDefinition` with `publication: () => 'none' | 'animation-frame' | 'immediate'`.
- **Data flow:** A unit folds host-side State and declares the client-visible View; the registry drives the unit and publishes changes; a client reads the published value at its render position.
- **Non-obvious design decisions:** **"Two answers to the same question — one pulled, one pushed — drift apart, so a render can show a value the Session log no longer supports"** — `docs/defensive-patterns/conversation-and-session.md:7`. The "small Session may be read in full" exception was **removed and is not reconsidered**: a cache miss leaves an *explicit state* for the caller instead of silently switching onto the slow path — `docs/defensive-patterns/conversation-and-session.md:50`. Retention uses the single predicate `refCount == 0 && inflight == 0` and **never enumerates which Sessions may be reclaimed from business state**, because that list would have to be maintained by every feature that adds a state — `docs/defensive-patterns/conversation-and-session.md:85`. On the high-frequency path, `immediate` publication and a full recomputation per chunk are forbidden; a chunk computes the increment on the affected subtree, not the event window — `docs/defensive-patterns/conversation-and-session.md:128`. `stateVersion` starts at 1 and is bumped whenever the serialized state fields or fold semantics change, *compatible or not*; registering one key twice with different `stateVersion` values throws instead of merging.
- **Edge cases & failure handling:** The node build/grouping engine, the node list and seat components, the Markdown pipeline, and the user-message model each carry **no business rule**: the business declares its kind and registers its renderer, and the engine consumes the placement enum as data. A business difference travels in the message payload (its own merge-extensible `source` kind) rather than as a field on the shared `UserMessage`.

#### `docs/defensive-patterns/client-components.md`
- **Purpose:** Rules for client components, their state, and their effects.
- **Key abstractions:** The **inject face** of a Slot registration (plain data, action callbacks, and the reserved `hooks` compartment bound as `use<Name>` hooks); `renderSlot`; `useResource<Protocol>(address)`; a declared store with a `persist` key; `ConversationNodeDataMap` kind registration.
- **Data flow:** The registration's `inject` factory closes over `ctx`; the parent's render site passes owner data through `renderSlot`; the component reads one field through its bound hook and writes through a narrow action set.
- **Non-obvious design decisions:** **"It never reads one large global state at the top of the tree to hand values down"** — `docs/defensive-patterns/client-components.md:7` — because keeping every live value on the inject face is what makes an unchanged prop keep its identity and lets a component subscribe only to the sub-state it reads; otherwise any unrelated field change re-renders the whole subtree, which is "how a long session under streaming events loses frames while the user scrolls or types". **Props carry data and callbacks, not React nodes** — `docs/defensive-patterns/client-components.md:55` — a node-valued prop hides a second composition path the Slot contract does not describe. **A slot registration is a stable function component** declared at module scope — `docs/defensive-patterns/client-components.md:95` — because a component created during render is a new *type* each pass and React remounts the subtree, resetting expanded rows, focus, and scroll position. **Components never receive a Cordis context** — `docs/defensive-patterns/client-components.md:135` — a bare observable reaches a component only after Injection wraps it in a hook whose subscription the renderer releases. Resource consumers go through `useResource` so there is one cache and one invalidation policy per protocol — `docs/defensive-patterns/client-components.md:188`.
- **Edge cases & failure handling:** **State changes must not remount a control or replace its DOM node** — `docs/defensive-patterns/client-components.md:273` — so focus, selection, and an in-progress draft survive; initial state is established by the first flow, not filled in later by an effect. `useLayoutEffect` is not a default, and swapping it for `useEffect` is not a fix — `docs/defensive-patterns/client-components.md:310`. Effects never push render-derived data to a parent — `docs/defensive-patterns/client-components.md:348` — because a push costs a second render and leaves the parent without the value on its first frame. A `key` must name a real identity; `key={index}` over a mutable list is forbidden — `docs/defensive-patterns/client-components.md:417`.
- **Surprising:** A table of **per-shared-layer isolation levels** (`docs/defensive-patterns/client-components.md:450`): a new control starts in the feature package and is promoted into the shared catalog only when a second consumer needs it; a shared-layer change carries the owning domain expert's confirmation and regresses every consumer.

#### `docs/defensive-patterns/remote-and-api.md`
- **Purpose:** Rules for the `packages/api` layer and the remote methods it exposes.
- **Key abstractions:** A **new remote business capability is a new service** (its own package or object) with `@Remote` on its concrete methods; `TypertClientRemote['session']` as the only source of client-facing types; `@Remote({ resources })` / `@RemoteScope(key, { resources })` for access control; `this.ctx.invocation.peer.principal` and `principalOf(this.ctx.invocation)`.
- **Data flow:** The decorator marks the method → the generator produces the client map and codecs → the Gateway resolves lookup arguments, enforces resources, and validates the result.
- **Non-obvious design decisions:** **Split by business boundary, not by caller count** — a capability with a single caller today still gets its own service, and an endpoint that changes owners *moves* to the new owner instead of joining the object it is leaving — `docs/defensive-patterns/remote-and-api.md:7`. The `@Remote` decorator carries **five disciplines** checked separately — `docs/defensive-patterns/remote-and-api.md:47` — mark the concrete method (a body that only delegates means the annotation is on the wrong method); take client-facing types from inference, never a hand-written second set; keep the wire payload JSON with **no output-side decode** (the generated codec and Gateway already validate); treat existing names as additive (a rename is its own change with its own review); and name **every** resource the method touches, because access control never checks a resource it omits. The caller is read only from the invocation, never from arguments.
- **Edge cases & failure handling:** A method returning several resources filters each item through `this.ctx.remoteAccess.allows(resource)`. `packages/api` carries generic orchestration only — `docs/defensive-patterns/remote-and-api.md:83` — and the page publishes the package census (`session-controller` 34 `src` files, gateway 11, …) as the impact evidence. A business branch in the shared layer needs an independent-package review answering why the logic cannot live in the owning package.

#### `docs/defensive-patterns/package-surface.md`
- **Purpose:** What a package exports, how it is built, and how it declares dependencies.
- **Key abstractions:** The **Loader four** (`name`, `inject`, `Config`, `apply`) for a function plugin vs. a default-exported service class; the standard `exports` key set (`.`, `./package.json`, `./src/*`, `./client`, `./types`, `./typert`, `./remote`, `./locale/*.json`, `./cordis.patch.yml`); `workspace:*` for `dsh-*` and `workspace:~` for other internal packages; `engines.dsh`.

- **Non-obvious design decisions:** **The four and the default export are mutually exclusive** — a default export beside the four makes the Loader discard the function plugin's namespace (this is the exact bug of post-mortem 0001). **A package's export map uses only the standard key set**, and a key used by a handful of packages without a documented owner "is not a precedent" — `docs/defensive-patterns/package-surface.md:75`. #### `docs/i18n/README.md`
- **Purpose:** The bilingual documentation pairing contract, the gate, the scope, and the exclusions.
- **Key abstractions:** A **pair is three sibling files** — `foo.md`, `foo.zh.md`, and a consistency record `foo.i18n.yaml` — with no locale directories and no interleaved bilingual files. The record holds **one entry per heading section** that still contains language-specific content, keyed by the section's English heading-slug path (`/` before the first heading, `~2`, `~3` for repeats), each holding a hash of the English and of the Chinese blocks in that section.
- **Data flow:** Edit one side → patch the counterpart minimally against the edited side's diff (never re-translate whole files) → `pnpm run verify-translation-pairing --write <pair>` re-records the entries → **that yaml diff is the reviewable act of confirming consistency**, which is why `--write` requires naming the pairs you confirmed.
- **Non-obvious design decisions:** **Blob hashes, not commit hashes or timestamps** — content identity is the only signal that means what the gate claims, and the recorded hash recovers the exact last-confirmed text of either side (`git cat-file -p <hash>`) so a drifted pair is updated by diffing, not re-translating. Each side's hash covers every top-level block of the section **except fenced code blocks and generated regions** (the two kinds the gate already requires to be identical), and content that merely happens to be identical is still hashed. Because edits to different sections change separate record lines, Git's default text merge composes them; a record conflicts only when both branches changed hashed content in the same section.
- **Edge cases & failure handling:** **"A green gate means the pair was confirmed consistent at these exact contents, not that the confirmation was sound"** — `docs/i18n/README.md:44` — it cannot judge whether the two sides say the same thing; that is the reviewer's half. Generated English sources omit the language switcher so they stay byte-identical to generator output. Exclusions are explicit and manifest-listed only (`cordis-api/inherited.md`, agent instructions, the two bilingual-by-construction i18n files, the machine-consumed translation prompt, the internal review policy, and the frozen archived notes).

#### `docs/i18n/translation-rules.md`
- **Purpose:** How to translate between the two sides of a pair.
- **Key abstractions:** RFC 2119 rule levels (MUST / MUST NOT / SHOULD / MAY) binding humans and agents equally; the **structural signature** the gate compares (heading depths, fenced code blocks, table row and column counts, list kinds, ordered-list starts, item counts, link locale, semantic targets with exact query/fragment suffixes).
- **Data flow:** Load `terminology.md` → translate the changed content in one terminology-guided pass → run the gate and the rest of `doc-sync` → human review owns list and table order, noncanonical numbering, inline code, emphasis, meaning, terminology, and tone.
- **Non-obvious design decisions:** **Both languages carry equal authority** — a Chinese-first document is as legitimate as an English-first one; neither side outranks the other, and if the pair disagrees on substance, *fix the side that is wrong* and bring the other along. Fenced code blocks are **byte-identical including comments**, and inline code spans are verbatim — never translated or reformatted. When a relative document link targets the active bilingual corpus, the English side uses `.md` and the Chinese side `.zh.md`; a missing counterpart is a *pair-completeness error*, not a fallback.

#### `docs/i18n/translation-prompt.md`
- **Purpose:** The prompt template for the automated translation pipeline — a machine-consumed asset, excluded from pairing.
- **Key abstractions:** Three placeholders (`{{source_lang}}`, `{{target_lang}}`, `{{terminology}}`); a three-section XML output contract (`<translation>` / `<review>` / `<final>`); a self-review instruction list.
- **Data flow:** The renderer (`scripts/translation-prompt.ts`) injects the terminology table and the five **whole-document** gold pairs as few-shot conversation turns (user = full source, assistant = full finished translation), renders in either direction, and parses the three sections.
- **Non-obvious design decisions:** The prompt is written as a **priority ladder**: (1) preserve source meaning and required structure; (2) follow the injected terminology table exactly; (3) use the gold pairs to calibrate voice; (4) apply the general writing guidance. "A lower-priority rule may refine but never override a higher-priority requirement. Gold pairs calibrate voice; they are not a translation memory." The pipeline translates **one whole document per request** and does not support `{{to}}`-style segment protocols.
- **Edge cases & failure handling:** Fenced code blocks must be byte-identical including *all comments*; inline code spans stay verbatim; a Markdown line consisting only of a framing tag is escaped with one extra backslash and the parser removes exactly one escape. The `<review>` section records **actual corrections only** — "do not include reasoning transcripts, checks that passed, tentative suggestions, retractions, or no-op corrections" — and must be exactly `- 无修正` when there are none. A tentative terminology rendering may appear in `<review>` but "must not be silently adopted in `<translation>` or `<final>`".
- **Surprising:** The pipeline inserts the canonical target-language switcher **mechanically after parsing `<final>`**, because a brand-new pair has no filename the model could know.

#### `docs/postmortem/README.md`
- **Purpose:** The definition and the writing contract for incident write-ups.
- **Key abstractions:** A post-mortem is **not** an Agent Note — it is a backward-looking record of a failure. The three admission criteria: **subtle** (non-obvious mechanism), **systemic** (the escape was a gap in tests/tooling/conventions, not a one-off typo), **costly to rediscover**.
- **Data flow:** Every post-mortem opens with an **Executive summary** — one paragraph a busy reader absorbs in thirty seconds: what broke, the root cause in plain terms, why it escaped, the durable lesson — before the detailed Summary / Timeline / Root cause / Guardrails sections.
- **Non-obvious design decisions:** The interesting part is *"why our process let it through"*, not the one-line fix. The post-mortem must **link the guardrails** (tests, AGENTS.md rules, ADRs) it motivated — the artefact is the guardrail, not the narrative.
- **Edge cases & failure handling:** The four linked incidents are a de-facto catalogue of the repo's known failure classes.

#### `docs/postmortem/0001-acp-default-export-drops-inject.md`
- **Purpose:** Why the ACP server crashed on the first real editor connect despite 178 green unit tests and 100% line coverage.
- **Key abstractions:** `Loader.unwrapExports` and its `exports.default ?? exports` preference; the traceable-proxy **shadow** mechanism and the **ancestor-only** fiber walk; `ctx.get(name)` as the topology-independent lookup.
- **Data flow:** A stray `export default apply` on a namespace plugin → the Loader unwraps to the bare function → the namespace's `inject`/`name`/`Config` are discarded → `apply` runs in a fiber with no injected services → `const agents = ctx.agents` walks to the root and throws `cannot get property "agents" without inject` at *load* time.
- **Non-obvious design decisions:** The second, independent bug: reading an optional service through a **shadow** from a foreign fiber fails because the service walk is ancestor-only, while a top-level test hits an early bypass (`!ctx.fiber.runtime` → direct global-store lookup) and therefore *passes*. The lesson: **"100% line coverage was satisfied the whole time. Coverage proves lines ran; it says nothing about whether the feature works the way it ships."** — `docs/postmortem/0001-acp-default-export-drops-inject.md:89`.
- **Edge cases & failure handling:** The guardrail is a **keyless** `session/new` e2e over real stdio through the real Loader (verified to fail when `export default apply` is restored) plus `TSX_TSCONFIG_PATH` in the spawn so the subprocess runs *source*, not a possibly-stale `lib/`. The codified rule is "test the real entry path; line coverage is not behavior coverage".
- **Surprising:** "Trust the trace, not the theory" — the elegant shadow explanation was real but was the *second* bug; the first was a one-line export mistake found in minutes by a fiber-walk `console.error` after hours of plausible-but-wrong reasoning.

#### `docs/postmortem/0002-js-expression-disabled-filesystem-tools.md`
- **Purpose:** How filesystem snapshot tools were permanently disabled by a literal `!!js` object.
- **Key abstractions:** `Entry._resolveConfig()` interpolates `entry.options.config`; `Entry.disabled` tests `entry.options.disabled` **without** interpolation. The `!!js` tag is only valid under `config` and `disabled`.
- **Data flow:** Cordis Include parsed each `!!js` scalar into an *expression object*; the Loader interpolated `config` but read `disabled` directly → every filesystem entry saw a truthy object and stayed disabled in every mode → the snapshot framework accepted `UNKNOWN_TOOL` results as new expected outputs.
- **Non-obvious design decisions:** The YAML tag was **syntactically valid**, so loading produced no diagnostic — "A syntactically accepted configuration value is not necessarily evaluated at that location." A naive interpolation fix would have created a *security* risk: permission presets update bash sandbox and approval state at runtime but cannot mount, unmount, or confine the filesystem stack. The fix uses an explicit full-access overlay instead.
- **Edge cases & failure handling:** The guardrails are: an explicit `fs.cordis.yml` overlay for the scenarios, a static config check (`verify-cordis-config` rejects expression nodes in Loader entry metadata), and a snapshot guard rejecting structured `UNKNOWN_TOOL` results in fresh runs and committed fixtures. **"A snapshot refresh is fixture production, not correctness review"** — `docs/postmortem/0002-js-expression-disabled-filesystem-tools.md:46` — semantic impossibilities such as a missing registered tool need assertions independent of the expected output.

#### `docs/postmortem/0003-web-agent-gui-feedback-loop.md`
- **Purpose:** How a Web agent validated a replacement server instead of the GUI hosting its session.
- **Key abstractions:** `window.__DSH_BOOT__` (injected only by the full host), the canonical loopback URL published in the `app:web-surface` prompt section and `$DSH_WEB_URL`, and the distinction between *transport readiness* and *application readiness*.
- **Data flow:** The session cwd identified the user's Workspace but not the application directory; the agent read `apps/web/package.json`, launched bare Vite on 5173, saw HTTP 200, and declared success — while the browser threw `client-modules: window.__DSH_BOOT__ is missing or not an object` and rendered a white page. It then launched an unmanaged `dsh web` on 3334 via shell `&` and verified only that *that* replacement answered 200.
- **Non-obvious design decisions:** **"HTTP readiness, build success, and a boot manifest are different facts"** — `docs/postmortem/0003-web-agent-gui-feedback-loop.md:51` — acceptance must name the exact origin and observe the requested change there externally. The first regression test repeated the mistake in another form: a timeout killed Vite and satisfied a nonzero-exit assertion — "a timeout killed Vite and satisfied a nonzero-exit assertion. Live reproduction exposed that false positive."
- **Edge cases & failure handling:** The guardrails: the Web launcher publishes the canonical URL; standalone Vite serve mode is **rejected during configuration** (with `Server.listen()` instrumented so a transient bind cannot pass unnoticed); layered real-path tests cover the CLI request, exact production/development prompts, same-port static replacement, source watcher rebuild, host stat polling, and browser HMR under an unchanged page identity; PR evidence preserves screenshots from the original session and a real-model before/after run.

#### `docs/postmortem/0004-landlock-partial-notice-misclassified-child-failures.md`
- **Purpose:** How a benign partial-enforcement notice plus any nonzero child exit was classified as launcher failure.
- **Key abstractions:** `RunnerFailureRule` with optional allowed exit codes, case-insensitive per-line fatal signatures, and case-insensitive **exact** informational-line exclusions; the launcher contract's exit 125 for launcher failure versus the exact `landlock-run: partial enforcement (older Landlock ABI)` notice followed by the child.
- **Data flow:** The sandbox provider reduced the contract to `runnerFailureSignatures: ['landlock-run: ']`; the bash consumer joined the prefix with any nonzero exit and reported stderr's *first* line — so `false`, ripgrep's no-match exit 1, invalid-pattern exit 2, even a child-chosen exit 125, were all blamed on the sandbox. A second attribution error compounded it: the bash-backed `runRipgrep()` replaced every non-aborted rejection with a generic `SEARCH_FAILED`, hiding the structured `SandboxUnavailableError`.
- **Non-obvious design decisions:** **"Process attribution requires a conjunction of independent evidence; a shared prefix is not a protocol"** — `docs/postmortem/0004-landlock-partial-notice-misclassified-child-failures.md:52`. Informational and fatal diagnostics can share a namespace, so exclusions must be exact and narrow while unknown fatal lines stay **fail-closed**. The public result type could only express a bag of substrings; the fix is a structured rule type, not a smarter string match. The document is honest that stderr remains an in-band attribution channel: a confined child can deliberately reproduce a gated fatal line — the tighter conjunction prevents the accidental collision but does not authenticate the writer.
- **Edge cases & failure handling:** Platform-dependent behavior needs a **deterministic fake at the native boundary plus one assembled product path**; a self-skipping real-kernel test cannot carry that regression alone. Filesystem search moved to packaged ripgrep through `ctx.subprocess`, outside the sandboxed bash seam. The adapter rule generalizes: an adapter must preserve the structured failures owned by the seam below it instead of replacing them with its own nearest generic category.

The migration requires draining pending messages *before* upgrading, because queued-but-undelivered messages are **never dispatched** after the upgrade; historical `team/message/queued` and `team/message/delivered` records remain readable. Roster and task state stay durable.

#### `docs/upgrade-guide/v0.2.1-alpha.1/terminal-command-labels/guide.md`
- **Purpose:** Custom `TerminalBlock` consumers must provide localized accessible names for overflowing command lines.
- **Key abstractions:** `TerminalBlockLabels.commandLine(line: number): string`; the authored line number, one-based.
- **Data flow:** Each horizontally overflowing line uses the name for its keyboard-focusable group; lines that fit, including wrapped lines, add **no Tab stop**.
- **Non-obvious design decisions:** The original command text stays separate from the accessible name; the name is localized through the plugin's own dictionary.

#### `docs/upgrade-guide/v0.2.1-alpha.1/tool-presentation-mode/guide.md`
- **Purpose:** Tool presentation accepts `native` or `ptc`; the mixed `both` mode is rejected.
- **Key abstractions:** The `mode` fields of `@deepseek-ai/dsh-tools` and `@deepseek-ai/dsh-agent-tool-presentation`; `DSH_TOOLS_MODE`.
- **Data flow:** `native` exposes visible tools as direct function calls; `ptc` exposes `run_code` and programs call the visible tools through the generated SDK. Different agent presets can use different modes in the same application.
- **Non-obvious design decisions:** "In PTC programs, keep calls inside `run_code`; do not emit the SDK function names as direct model tool calls" — the mode is a hard contract, not a preference, and a preset-specific choice is made by editing the preset's presentation row rather than the global env var.

#### `docs/upgrade-guide/v0.2.1-alpha.1/web-listener-trust-config/guide.md`
- **Purpose:** The Web profile replaces `webRuntime` with `webStartup` and rejects a wildcard listener host.
- **Key abstractions:** `webStartup.trustedHosts`; `--trusted-host` authorities; the `connection` row.
- **Data flow:** A profile injecting `webRuntime` now waits for a service that never mounts, and an expression reading `ctx.webRuntime.trustedHosts` fails to evaluate, so the required Connection cannot start. The listener host must be one concrete IPv4 or IPv6 address of a local interface.
- **Non-obvious design decisions:** **A wildcard bind is refused at load** ("binding every interface exposes the port to the network"), while the bound IP itself is accepted by the Host fence with no `--trusted-host` entry — a proxy or DNS authority still needs one. The guide also notes that a patch **replaces the matched row's whole `config`**, so a migrated config must be restated completely, and an array-valued `!!js` expression must be written as a quoted scalar.

#### `docs/upgrade-guide/v0.2.1-alpha.1/working-directory/guide.md`
- **Purpose:** Session working directories replace the built-in `cwd` configuration.
- **Key abstractions:** The working-directory service; `working_directory({ cd })` / `working_directory({})`; `Session.header.cwd` versus the current execution directory; `output.presentationMeta` on nested PTC calls.
- **Data flow:** The loop's `{{cwd}}` prompt variable and the `cwd` config key of the ACP / DSH-SDK subagent providers are removed; a Session's current execution directory is supplied as required user context and persisted **separately from its original `Session.header.cwd`**. New subagents use the start request's `cwd` when provided, otherwise capture the parent's current directory.
- **Non-obvious design decisions:** **"Changing the execution directory does not change the original project or grant additional write permissions"** — the current directory is not a permission root. A custom prompt template that retains an unresolved `{{cwd}}` **fails before a model request**. Dynamic context providers are re-evaluated at request admission, after pre-step listeners and route preparation, so a provider must return current state rather than rely on one evaluation per step.

#### `docs/upgrade-guide/v0.2.1-alpha.2/deepseek-account-identity-watch/guide.md`
- **Purpose:** `DeepSeekAccount.watch` no longer includes Platform identity changes unless explicitly requested.
- **Key abstractions:** `deepseekAccount.watch(signal, true)` for identity subscribers.
- **Data flow:** The public watch method previously emitted a snapshot when a profile read first supplied or changed the cached Platform user id; it now emits account-state changes only by default. Credential replacement and sign-in state changes still notify every subscriber.
- **Non-obvious design decisions:** The default changes to *less* notification, and the opt-in is explicit and narrow — a plugin that refreshes `getPlatformSession()` must ask for identity changes. Repeated reads with the same id do not emit another identity notification.

#### `docs/upgrade-guide/v0.2.1-alpha.2/deepseek-account-model-catalog/guide.md`
- **Purpose:** The DeepSeek account route no longer accepts a models catalog.
- **Key abstractions:** `modelOverrides.<model id>`; `CLIENT_UPGRADE_REQUIRED`.
- **Data flow:** The route lists models from the account's `GET /models` endpoint, serves the built-in catalog until a listing loads, and accepts per-model adjustments only through `modelOverrides`. A left-over `models` field **stops the plugin at load** with `llm-deepseek-account: models is no longer configurable`.
- **Non-obvious design decisions:** A listed model may require a newer DeepSeek Harness; such a model is **hidden** and requesting it fails with `CLIENT_UPGRADE_REQUIRED`. An override the listed model rejects, or one naming an unknown model, appears as the account's diagnostic on the Models page — the failure is reported, not silently dropped.

#### `docs/upgrade-guide/v0.2.1-alpha.2/desktop-font-size-shortcuts/guide.md`
- **Purpose:** Desktop font-size shortcuts reserve key combinations previously available to custom shortcuts.
- **Key abstractions:** `Cmd`/`Ctrl` + `=`, `Shift` + `=`, `Cmd`/`Ctrl` + `-`.
- **Data flow:** Custom bindings using these combinations, including overlapping two-key chords, **remain saved but no longer execute**; Web shortcut behaviour is unchanged.
- **Non-obvious design decisions:** The Settings UI marks the conflicting binding explicitly, and "Restore default" is available when the action's default does not conflict — the migration is a UI task, not a config edit.

#### `docs/upgrade-guide/v0.2.1-alpha.2/from-default-profile-replaces-target/guide.md`
- **Purpose:** `--from-default-profile` now replaces an existing custom profile instead of refusing it.
- **Key abstractions:** `$DSH_HOME/profiles/<name>/`; shipped profile names in any letter case are still rejected as targets.
- **Data flow:** The command now replaces the target directory with a fresh copy of the template every time, then boots it (or prints the composition with a config-dump flag). The previous directory is deleted, including its `package.json` dependencies, installed `node_modules`, and `cordis.patch.yml`.
- **Non-obvious design decisions:** The guide is written to warn the affected population explicitly: "This affects anyone who repeats the command … in scripts or shortcuts and expects later runs to keep the profile's plugins or patch." The escape is to copy `cordis.patch.yml` first, then reinstall the plugins and restore the patch.

#### `docs/upgrade-guide/v0.2.1-alpha.2/operator-connect/guide.md`
- **Purpose:** Non-page Clients default to no forwarded interactions and use raw streams without browser recovery.
- **Key abstractions:** `interactions: 'none' | 'answer'`; the launch token at `GET /connect?token=…&interactions=none`; the API Cookie and the lifecycle WebSocket at the returned 302 Location.
- **Data flow:** In `none` mode the connection does not open `$events`, and `$on()` and the generation-recovery helper `$stream()` are unavailable; generated unary and raw stream methods remain usable. HTTP need not wait for the socket to open.
- **Non-obvious design decisions:** Browser authentication, existing Cookies, the shared Peer, and recovery behaviour are unchanged — browsers need no reauthentication. After lifecycle-socket closure or a Host restart, a passive caller must **perform a new connect before retrying**.

#### `docs/upgrade-guide/v0.2.1-alpha.2/pi-ai-azure-provider/guide.md`
- **Purpose:** The pi-ai Azure provider route is renamed from `azure-openai-responses` to `azure`.
- **Key abstractions:** The `azure` route includes both Responses and Chat Completions models; the Responses API identifier and the `AZURE_OPENAI_*` env var names are unchanged; `AZURE_OPENAI_DEPLOYMENT_NAME_MAP` maps a custom deployment name.
- **Data flow:** The mixed catalog cannot infer a protocol for a model id absent from the catalog, so an explicit route-level `api` overrides every model on that route — but it does not select the Azure provider.
- **Non-obvious design decisions:** "Do not edit historical Session events" — the migration is forward-only for persisted history; continuing an existing Session requires reselecting an Azure model.

#### `docs/upgrade-guide/v0.2.1-alpha.2/pi-ai-model-discovery/guide.md`
- **Purpose:** pi-ai routes that name a credential hide their models until the credential is configured.
- **Key abstractions:** `apiKeyEnv`.
- **Data flow:** A route naming a credential previously listed its configured models while the credential was missing, and requests then failed with `MISSING_CREDENTIAL`; model discovery now returns an empty catalog for such a route until the credential resolves. Other credential errors, such as a malformed key, still fail discovery.
- **Non-obvious design decisions:** The same "don't confuse listing with acceptance" caution as the DeepSeek route: "a listed catalog does not mean that the remote API accepts the key."

#### `docs/upgrade-guide/v0.2.1-alpha.2/plugin-install-over-installed/guide.md`
- **Purpose:** With HMR, installing an already-installed package fails with `already-installed`.
- **Key abstractions:** `pluginManager.installBundle(spec)` / `removeBundle(name)`; `ManagementError['code']`; the agent tools `install_bundle` / `remove_bundle`.
- **Data flow:** In an HMR profile the install now fails **before pnpm runs**, with `application: 'failed'` and `error.code: 'already-installed'`, and changes no profile file. Without HMR, installing over an installed package still runs pnpm and reports `restart-required`.
- **Non-obvious design decisions:** The removal-then-install order is the whole migration, and the guide explains why it is safe: "The removal stops the bundle's plugins and drops its packages' mappings, so the new version is mapped afresh and starts without a restart." The Web page's Update for an Official plugin does the remove-then-install itself.

#### `docs/upgrade-guide/v0.2.1-alpha.2/sdk-minimal-image-compaction/guide.md`
- **Purpose:** The `sdk-minimal` default tool roster adds `read_image` and automatically summarizes older context.
- **Key abstractions:** `read_image`; the `compaction-basic` row with `auto`; the route image budget.
- **Data flow:** Automatic compaction sends an **additional** model request to summarize older history when context pressure reaches the configured threshold. The complete Session log remains stored as **uncompressed JSONL**; images that exceed the route budget are permanently replaced by attachment/path placeholders so the request can retry.
- **Non-obvious design decisions:** "Clients that pin tool names, benchmark prompt size, or count model requests must account for these defaults" — a change in *request count* is a breaking change for a client that measures cost. Image reading requires an adapter route that declares image input. The escape is a small documented patch that disables `read`/`readImage`/`write`/`edit` and `compaction-basic.auto`.

#### `docs/upgrade-guide/v0.2.1-alpha.2/stored-credentials-precedence/guide.md`
- **Purpose:** Stored credentials now precede environment fallbacks when the store is mounted.
- **Key abstractions:** `$DSH_HOME/.credentials.yaml` (or `~/.dsh/.credentials.yaml`) with `refs`; `$cwd/.env`; `$DSH_HOME/.env`; the shipped `headless` profile's three-row restoration patch.
- **Data flow:** Earlier releases used the exported variable before the stored `refs` entry with the same name; now the stored entry wins, the exported variable applies only while the file stores no value for that name, and the two `.env` files apply only after both. A running harness reloads the file, so the next request reads the exported variable without a restart.
- **Non-obvious design decisions:** The shipped `headless` profile **disables the credential store entirely** (credential store, authorization, and the DeepSeek account provider), so saved API keys and sign-ins no longer authenticate headless jobs by default — a deliberate narrowing of what an unattended profile can do. The verification instruction is precise about not leaking secrets: "Check names and presence without printing credential values."

#### `docs/upgrade-guide/v0.2.1-alpha.3/plugin-engines-dsh/guide.md`
- **Purpose:** Plugin compatibility checks read `engines.dsh` before DSH `peerDependencies`.
- **Key abstractions:** `engines.dsh`; the renamed `peers` → `requirements` key on `IncompatiblePlugin` and `PluginCompatibility`.
- **Data flow:** An own `engines.dsh` range decides alone and the peers are ignored; the peer rule applies only when `engines.dsh` is absent. `workspace:` values are valid only in peers — in `engines.dsh` they are incompatible. A non-object `engines` or a non-string `engines.dsh` makes the manifest unreadable for compatibility, which refuses the package.
- **Non-obvious design decisions:** The refusal record's key is `engines.dsh` for the engines rule and the peer package name for the fallback, so the consumer can tell *which* rule fired. The command `dsh plugin --profile <profile> add <package@version>` is the named verification.

#### `docs/upgrade-guide/v0.2.1-alpha.4/account-notification-fields/guide.md`
- **Purpose:** `AccountBonusNotification` exposes unvalidated optional metadata and permits notices without an expiry.
- **Key abstractions:** `campaign`, `amount`, `currency`, `grantedAt` as optional unvalidated `JsonValue`; `orderId`, `message`, `expiresAt`, optional `title`.
- **Data flow:** An **empty `expiresAt` means the notification never expires**; `orderId` accepts arbitrary strings rather than requiring UUIDs.
- **Non-obvious design decisions:** "Treat an empty `expiresAt` as no expiry before parsing timestamps" — the empty string is a *meaningful* value, not a missing one, which is the same "one value states one fact" rule from `general.md` applied to a wire type. The client must narrow the optional metadata before using it, because presence and format are no longer guaranteed.

They are produced by `pnpm run verify-translation-pairing --write <pair>`, are derived from the two `.md` files I read in full, and carry no authored prose. I opened the head of each (all 80) to confirm the format and the section keys; I did not read them line by line, because their content is a hash of content I have already read.

The interesting variation among them: the `cordis-api/*` records all use the key `/` (the generated English has a single top-level heading structure that the pairing tool treats as one section), while the hand-authored pages use heading-slug paths like `/tool-authoring-reference` or `/cookbook-adding-a-workspace-package`.

## 2. Ideas worth stealing

1. **One canonical JSON value per tool call, with the UI derived from it.** A tool returns exactly one typed value; the model-facing prose and the durable card are two *separate* projections of it, and the durable card's data comes from `output.presentationMeta` so it survives session replay without persisting the canonical value. `docs/cookbook/adding-a-tool.md:48`. *Why it transfers:* August Trading's desk tools currently mix human-readable text with structured results. Splitting "what the model reads" from "what the card replays" would let a trade card re-render identically after a restart. **UNIQUE** to this repo.

2. **A tool's presenters must be pure functions of `(args, result)` — no I/O, no clock, no session reads — because they run on live streaming *and* on replay.** `docs/cookbook/adding-a-tool.md:87`. *Why it transfers:* any August Trading card that shows a price, a timestamp, or a "current" value must derive it from the recorded result, not re-read it. This is the same discipline August already needs for its `render-probe` (rendered rows must match) but stated as a tool-authoring rule. **UNIQUE** here.

3. **Projection as the only read path, with a cache miss as an explicit state rather than a silent slow path.** `docs/defensive-patterns/conversation-and-session.md:7` and `:50`. *Why it transfers:* August has a projection-like concept (session-projection is explicitly referenced by the harness); the transferable rule is the *no second read path* prohibition plus "the 'small session may be read in full' exception was removed and is not reconsidered." **CONVERGENT** (pi and hermes-agent also push a single canonical store).

4. **Retention by one auditable predicate: `refCount == 0 && inflight == 0`, and never enumerate reclaimable items from business state.** `docs/defensive-patterns/conversation-and-session.md:85`. *Why it transfers:* August's trade journal, chat history, and learning notes are all "retained until nobody needs them"; a single predicate plus explicit `retain`/`release` handles replaces every ad-hoc cleanup list. **UNIQUE** here.

5. **A new "active/current" singleton is refused outright; one piece of data gets several views, each carrying its own reference.** `docs/defensive-patterns/general.md:87`. *Why it transfers:* August has a global "current conversation" and a global "current trade" in places. The rule is that a *service or instance field* expressed through DI may carry it, never a module-level field. **CONVERGENT** in spirit across repos (all three avoid module-level mutable singletons), **UNIQUE** in stating it as a reviewed prohibition.

6. **One error class plus a `<domain>/<reason>` code table, with four placement rules for where a code may be declared.** `docs/cookbook/adding-a-remote-api.md:51`. *Why it transfers:* August's provider errors (`toFriendlyProviderError`) and trade-plan refusals (the R:R floor, the ATR stop bands) would benefit from one code vocabulary with a stated owner per code. **UNIQUE** here.

7. **A post-mortem is "the rule plus the defect it prevents", and its artefact is the guardrail it motivated.** `docs/postmortem/README.md:9`, `docs/defensive-patterns/README.md`. *Why it transfers:* August's `docs/plan/full-audit.md` and `open-items.md` are already close to this shape; the transferable bit is the *admission criteria* (subtle, systemic, costly to rediscover) — it tells you which incidents are worth a write-up and which are not. **CONVERGENT** (hermes-agent also keeps incident notes).

8. **A regression guard must be proven to FAIL on the unfixed code.** `docs/cookbook/responding-to-pr-review-on-a-stack.md` (step 4). *Why it transfers:* August's `render-probe` and `boot-probe` are the right shape; the "watch it go red, then revert" discipline is the part worth adopting explicitly in the plan documents. **UNIQUE** here.

9. **A snapshot refresh is fixture production, not correctness review — semantic impossibilities need assertions independent of the expected output.** `docs/postmortem/0002-js-expression-disabled-filesystem-tools.md:46`. *Why it transfers:* this is the single most important lesson for August's recorded-session tests: a test that only compares against a recorded fixture proves determinism, not correctness. An "UNKNOWN_TOOL"-class impossibility must be rejected *before* the fixture is accepted. **UNIQUE** here.

10. **A bilingual doc pair is three files with per-section blob hashes, and a drifted pair is patched minimally against the edited side's diff rather than re-translated.** `docs/i18n/README.md:10`. *Why it transfers:* if August ever needs a second language, this is a working, mechanically-gated design; the transferable idea for English-only use is the *section-keyed hash record*, which turns "are these two docs in sync?" into a cheap, mergeable, reviewable artefact. **UNIQUE** here.

11. **Bump a persisted format only when an effective discriminator cannot prevent unsafe interpretation; otherwise record a same-version change with a compatibility explanation.** `docs/cookbook/adding-a-session-format-version.md:23` and `docs/cookbook/reviewing-persistence-type-changes.md:51`. *Why it transfers:* August has a persisted notebook and a persisted chat schema; the rule "a structural difference can remain same-version with evidence of safe interpretation or refusal" plus a machine-recorded compatibility note is a cheaper, safer alternative to a version bump. **UNIQUE** here.

12. **Model Experience is a mandatory per-package README section: what the model sees, its token effect, and its KV-Cache effect.** `docs/cookbook/adding-a-package.md:105`. *Why it transfers:* August's prompt assembly (constants/prompts, promptRegistry) has no equivalent discipline. A per-capability "token effect / cache effect" note is exactly what August's AGENTS.md discusses informally ("the answer is prose, the row does not shout") but never *records*. **UNIQUE** here.

13. **A shared layer's isolation level is a published table, and a feature absorbs its own requirement in its own package.** `docs/defensive-patterns/client-components.md:450`, `docs/defensive-patterns/general.md:124`. *Why it transfers:* August's `services/` tree has exactly this problem (a "center" service that grows a branch per feature). The rule "a business capability owns itself; the center layer holds the registry structure and the disposal lifecycle" is a direct, actionable restructuring rule. **CONVERGENT** (all three repos separate the extension point from the feature).

14. **The evidence rule: measure the changed path before and after, in one environment on one input, and do not dilute the difference by attaching the same hook to both sides.** `docs/defensive-patterns/general.md:149`. *Why it transfers:* August's plan mentions benchmarks; the "same hook on both sides cancels the signal" warning is the part that actually breaks naive before/after measurements. **UNIQUE** here.

## 3. Trading-specific findings

This shard is documentation, not trading code, so most of the six trading questions belong to other shards. What it *does* answer:

- **Long-lived monitoring & scheduled work:** the mechanism is a plugin registering model-callable scheduling tools, with a due timer delivering through `followup(…, {source: {kind: 'schedule'}})` — `docs/cookbook/extension-cookbook.md:127`. What makes it reliable is *not* in this shard (it is the `schedule` / `ui-schedule` rows and the `deliveryHistoryDays` field referenced by the v0.1.7 and v0.2.0 upgrade guides). The transferable reliability property is the one the general rules give: a due timer must not be scheduled by a callback that races the event loop, and a missed run must be recoverable rather than silently dropped.
- **Human-in-the-loop approval:** the harness's approval surface is a **waterfall** — `approval/request` lets a policy answer instead of the user, while the permission system returns `ask` from `tools/pre-execute` and is answered through `ctx.approval` — `docs/cookbook/extension-cookbook.md:127`. The discipline for a consequential action is that *a plugin may answer on the user's behalf*, and the extension point is a documented, typed decision rather than an ad-hoc prompt.
- **Post-mortem / reflection loops:** the closest analogue in this shard is the **skill-maintenance loop** — `docs/cookbook/maintaining-dsh-code-review.md`. It is a reflection loop with all the properties a trading post-mortem loop needs: a *window* (two UTC days, overlapping and idempotent), a *candidate* that only becomes a change after a human decision, a **manifest linking each proposed rule to the source human feedback and the landed commit**, an explicit "no candidate" outcome that is *not* a failure, and a **fail-closed** rule for a bad adapter batch. It also carries the "what stops bad rules accumulating" answer: the human operator chooses discard / batch / promote, and a rule already present in the current skill is classified `covered` and does not re-enter as a candidate.
- **Multi-agent:** the harness's answer is *not* debate. Delegation is a **managed activation**: the tool returns `{ kind: 'activation', subagentId }`, the runtime delivers the final answer as a **parent completion notice**, and the child may be continued later (Spawn/Fork) but external providers execute once — `docs/upgrade-guide/v0.2.1-alpha.1/subagent-activations/guide.md`. Persona and tool filtering are **not** per-call knobs; they come from an Agent Preset composition, and there is "no replacement per-child tool-name filter". Where debate would be wasted: any child whose result must be attributed to a specific parent message — the general rules explicitly warn that a shared `running` interval cannot be attributed to one follow-up.
- **Structured logs the model can query:** the harness's equivalent of a trade log is the **Session log**: an event stream persisted as **JSONL**, with `session/event` as the durable carrier of Assistant settlements, turn/step boundaries, and tool activity, and `session/event → JSONL` for a replayable trace — `docs/cookbook/extension-cookbook.md:127`. Replay is `sessions.create(id, { seed })`. Crucially, the log is **uncompressed** even when the model sees a summarized history: "The complete Session log remains stored as uncompressed JSONL" (`docs/upgrade-guide/v0.2.1-alpha.2/sdk-minimal-image-compaction/guide.md`). The trade-log lesson: keep the raw record intact; compress only what goes to the model.
- **Staying simple as features accumulate:** the whole `defensive-patterns/` directory is the answer, and it is a *list of prohibitions* rather than a list of features: no new `active`/`current` singleton; no module-level cache or `globalThis` bypass; no business branch in a shared layer; no new `resolve` hook; no third `tsconfig` variant; no hand-written `include`/`external` list; no new export key outside the standard set; no module-scope `await`; no top-level-await. Each has a *judged condition* a reviewer applies and a named approver for exceptions — this is how the feature count stops from becoming the product.

## 4. Non-obvious decisions and gotchas

1. **A default export on a plugin silently discards `inject`.** `Loader.unwrapExports` prefers `exports.default ?? exports`, so a namespace plugin with an extra `export default apply` loses its whole namespace and the plugin loads with no injected services — `docs/postmortem/0001-acp-default-export-drops-inject.md:56`. The error surfaces as a confusing `cannot get property "agents" without inject`.
2. **`ctx.<name>` and `ctx.get(name)` are not interchangeable.** The property proxy resolves by an **ancestor-only** fiber walk and throws through a foreign "shadow"; `ctx.get(name)` is the topology-independent lookup and is strict by default — `docs/postmortem/0001-acp-default-export-drops-inject.md:118`. Use `ctx.get` for a service you read opportunistically but did not declare in `inject`.
3. **A top-level test bypasses the fiber walk.** `if (!ctx.fiber.runtime) return ctx.reflect.get(prop, false)` — so the same code throws in production and passes in a unit test. This is the mechanism behind post-mortem 0001's second bug and is the general reason "100% line coverage" proved nothing there.
4. **`!!js` is interpolated only under `config` and `disabled`.** Entry metadata such as `disabled` is read *without* interpolation, and a `!!js` value is truthy — so `disabled: !!js ...` silently keeps the entry disabled (`docs/postmortem/0002-js-expression-disabled-filesystem-tools.md`).
5. **A `!!js` expression is syntactically valid, so nothing warns.** Only a *static* config check catches it — the "verifiably evaluated where you think it is" rule.
6. **A waterfall listener that forgets `next()` silently swallows the default behaviour for everyone downstream** — `docs/cordis-tutorial/04-events.md`. The repo makes this a standing rule.
7. **A plugin that never loads is usually PENDING, not broken.** `ctx.registry.values()` → `runtime.fibers` → `fiber.state === FiberState.PENDING` is the diagnostic; and a PENDING fiber keeps Node's event loop alive, so the process exits 0 silently.
8. **Async disposers run concurrently.** Reverse registration order holds, but two async disposers do not sequence; teardown that must be ordered goes into one disposer.
9. **`ctx.on` is owned by the fiber; a listener registered in a plugin dies with it.** But a listener registered *outside* any fiber (e.g. at module scope) will not.
10. **Presentation is a first-class, typed contract.** A tool's UI card is a `card`-tagged render intent (`generic` / `terminal` / `diff` / `read` / `search` / `web`), and the Web Client does **not** consume `presentCall`/`presentResult` at all — it registers its own keyed slot — so defining Host presentation methods alone adds no Web card.
11. **`read` and `search` have no *call* view.** Their pending state stays a generic card because the content only exists after `execute`; the completed view is reconstructed from persisted `result.meta`, and a `search` result must carry `truncated`/`total` so a UI never presents a capped result as complete.
12. **A `key` must name an identity the data actually has.** `key={index}` over a mutable list makes every following row keep its previous state on new data — an expanded row or an in-progress edit lands on the wrong item.
13. **A plugin that "reads one large global state at the top and hands it down" re-renders its whole subtree on any field change** — the stated cause of frame loss in a long streaming session (`docs/defensive-patterns/client-components.md:7`).
14. **A component created during render is a new React *type* each pass**, so React remounts it and resets expanded rows, focus, and scroll position — `docs/defensive-patterns/client-components.md:95`.
15. **The `Loader four` and a default export are mutually exclusive**; the same is now a reviewed package-surface rule (`docs/defensive-patterns/package-surface.md:7`).
16. **HTTP 200 is not application readiness.** `window.__DSH_BOOT__` is injected only by the full host; bare Vite returns 200 and renders a white page (`docs/postmortem/0003-web-agent-gui-feedback-loop.md`).
17. **A shared stderr prefix is not a protocol.** Informational and fatal diagnostics share the `landlock-run:` namespace, so exclusion must be exact and narrow while unknown fatal lines stay fail-closed (`docs/postmortem/0004-landlock-partial-notice-misclassified-child-failures.md`).
18. **An empty string can be a meaningful value.** `expiresAt: ''` means *never expires*, not *missing* — and must be handled before any timestamp parsing (`docs/upgrade-guide/v0.2.1-alpha.4/account-notification-fields/guide.md`).
19. **A listener that only observes a waterfall must call `next()`.** Not calling it is a deliberate short-circuit, and forgetting it is the single most common cause of "my hook swallowed the tool call".
20. **A green i18n gate is not a correct translation.** "A green gate means the pair was confirmed consistent at these exact contents, not that the confirmation was sound" — `docs/i18n/README.md:44`. The same honesty is required of any automated gate: it can check hashes and structure, not meaning.

## 5. Weak spots

1. **The rule corpus is enormous and duplicative, and it is prose rather than machine-checked.** `defensive-patterns/general.md` alone states fifteen rules, each with a judged condition, a boundary, an approver, and two code examples — several hundred lines of review guidance that only a human reviewer applies. The rules contradict each other in tone (`useLayoutEffect` needs a domain expert's sign-off; a `resolve` hook is refused outright) and the exceptions are numerous, which weakens the "no exceptions" rhetoric. August should adopt the *shape* (rule + judged condition + a mechanical gate) and not the volume.
2. **The upgrade guides are written for end users of a packaged desktop app, and the sharding of a 42-entry release corpus is by directory rather than by theme.** A reader chasing "what changed about the tool API" must open many files. The `kind: upgrade-guide` frontmatter and a consistent `Change` / `Migration` skeleton keep it navigable, but there is no cross-version index in this shard.
3. **Some rules are stated but not enforced, and one page admits it.** `docs/defensive-patterns/package-surface.md:75` lists export keys (e.g. `./brand` in 5 packages, `./worker` in 4) that have *no documented meaning* and are "pending review, not a pattern to copy" — the repository documents its own violations of its own rule instead of fixing them, and the enforcement is a human reading the page. Similarly, the "recompute the distribution" `python3` one-liners printed in the docs are a manual substitute for a CI gate that plainly could exist.
4. **The Chinese mirrors double the corpus, and the i18n machinery is a whole subsystem (manifest, pairing gate, hash records, a translation prompt template, a terminology table, style samples) maintained for a documentation set.** That is a large fixed cost for a repository whose product is a harness; the transferable insight is the *section-keyed hash record* (cheap, mergeable, reviewable), not the whole pipeline.
