# hermes-agent :: hermes-optional-mcps

**Files in shard:** 66 (read: 66, skipped with reason: 0)
**What this shard covers:** the repository's entire **optional MCP catalog** — 66 `manifest.yaml` files, one per third-party tool server that Hermes is willing to connect to. Every file is a `config` (Tier 2): a small, hand-reviewed YAML record describing *where* a vendor-hosted MCP lives, *how* it authenticates, *which of its tools are safe to leave enabled*, *what the user should read after installing*, and *when the composer should suggest it*. The set as a whole is not a list of connectors — it is a **security policy expressed as data**: the catalog is the only place a third-party tool surface enters the agent, so the curation decisions recorded in these files (what is excluded, what is left on, what the user is warned about) are the most transferable artifact in this shard. The one trading-shaped entry is `robinhood` (a real-trading agentic connector); `twelve-data` is the market-data read-only connector; `plaid` and `paypal` are financial but not trading.

### 1.1 Catalog anatomy — how a manifest becomes a running connector

Read for context from outside the shard (the loader, not part of this shard's file list):

- **The approval model is the directory itself.** Every entry except `n8n-official` opens with the two-line banner `# Nous-approved MCP catalog entry.` / `# Presence in this directory = approval. Merged via PR review.` (e.g. `optional-mcps/airtable/manifest.yaml:1-2`). The module docstring says the same: *"Entries are added only by merging a PR into hermes-agent; presence in `optional-mcps/` = Nous approval (no community tier, no other trust signals)"* — `hermes_cli/mcp_catalog.py:1-5`. There is no runtime store of "approved" servers; the tree *is* the allow-list, and it is reviewed by the same pull-request gate as code.
- **The schema is validated hard, in a fixed order.** `_parse_manifest` (`hermes_cli/mcp_catalog.py:311-345`) requires `manifest_version == 1` (`mcp_catalog.py:26`, `321-326`), a `name` matching `^[A-Za-z0-9_-]+$`, a non-empty `description`, then validates `transport → auth → tools → suggest → install` — *"Validation order (transport, auth, tools, suggest, install) determines which error surfaces"* (`mcp_catalog.py:334`).
- **Two tool-selection modes, and they are mutually exclusive.** `ToolsSpec` (`mcp_catalog.py:79-91`) documents `default_enabled` (pre-checked in the install checklist; applied directly if the probe fails) and `default_excluded` (an *exclude*-mode counterpart — everything not matching stays enabled, including tools the vendor adds later). `_parse_tools` rejects both being set: *"mutually exclusive"* (`mcp_catalog.py:241-242`). This is the single most important design decision in the shard: **exclude-mode manifests never probe** (`mcp_catalog.py:630-644`), so a 3,300-tool vendor surface can be curated by a handful of glob patterns that survive vendor growth.
- **An invalid manifest is skipped, not fatal — but it is surfaced.** `list_catalog` skips bad entries and records them in `_CATALOG_DIAGNOSTICS` as `invalid` or `future_manifest` (`mcp_catalog.py:353-380`); the picker and the web router read that so a UI can say "update Hermes" (`hermes_cli/mcp_picker.py:178`, `hermes_cli/web_routers/mcp.py:465`) rather than silently showing a shorter list.
- **Secrets never enter `config.yaml`.** Non-secret env values are inlined recursively into the server block (`_inline_non_secret_value`, `mcp_catalog.py:523-536`); secrets stay as `${VAR}` references resolved from the profile's `.env` at load time (`mcp_catalog.py:822-826`). The validator enforces the contract in both directions: an `http`+`api_key` entry must declare the exact env var the Authorization header references (`mcp_catalog.py:201-212`), and any `${VAR}` inside `auth.oauth` must be declared in `auth.env` or the OAuth flow would send a literal placeholder and fail with `invalid_client` (`mcp_catalog.py:223-228`).
- **A user's own tool choice survives a reinstall.** `_read_prior_tool_list` reads the existing `tools.include`/`tools.exclude` **before** the entry is overwritten (`mcp_catalog.py:562-573`, `818-819`), and `_apply_tool_selection` gives the prior selection priority over the manifest default (`mcp_catalog.py:615-721`).
- **The user's choice of "everything" is stored as no filter at all**, so tools the vendor adds later are auto-enabled rather than silently dropped (`mcp_catalog.py:709-716`); and "no tools today" is stored as an explicit empty include so it does not widen to "all tools" when the server later advertises some (`mcp_catalog.py:674-679`).
- **`suggest` drives the desktop "brand pill"**: keywords + host suffixes, matched case-insensitively whole-word (`SuggestSpec`, `mcp_catalog.py:93-106`; matching normalisation `mcp_catalog.py:282-286`; surfaced to the composer at `hermes_cli/web_routers/mcp.py:428`).

## 2. Ideas worth stealing

1. **The catalog directory IS the allow-list; approval is a code review, not a runtime flag.** Every file carries `# Presence in this directory = approval. Merged via PR review.` (`optional-mcps/airtable/manifest.yaml:1-2`, and 64 siblings). *Where:* `optional-mcps/*/manifest.yaml:1-2`; *loader:* `hermes_cli/mcp_catalog.py:1-5`. *Why it transfers:* August Trading's tool surface (`services/tools/toolForge`, `services/analysis/DeskToolsService`) would get the same property for free if the set of *approved* tool kinds were a checked-in registry merged by PR, rather than a user-configured list. **CONVERGENT** — the `pi` and `deepseek-harness` shards are the other two references; the "capability allow-list as reviewable code" pattern is the single most common idea across all three.
2. **Exclude-mode curation: a short list of *globs* that survives the vendor adding tools later.** `default_excluded` writes `tools.exclude` and leaves everything else — including future tools — enabled (`hermes_cli/mcp_catalog.py:79-91`, `630-644`); Cloudflare's list is ~40 patterns covering ~1,400 of ~3,300 tools (`optional-mcps/cloudflare/manifest.yaml:32-105`). *Why it transfers:* a curated **include** list rots the moment a vendor ships a new capability; an **exclude** list only has to be right about what you refuse. August Trading's desk tools and the model-authored `toolForge` tools would benefit from the same "refuse-by-pattern, allow-by-default" grammar.
3. **One disclosure layer, never two.** Cloudflare's `?codemode=false` is pinned precisely to avoid stacking the vendor's server-side `search()/execute()` indirection on top of Hermes's own `tool_search` (`optional-mcps/cloudflare/manifest.yaml:15-27`). *Why it transfers:* August Trading already has a tool catalogue and a desk-tools surface; the rule generalises to *"if you own a tool-discovery layer, tell every vendor to emit the raw surface rather than a search proxy"*.
4. **Measure the token cost of a tool surface and write the number into the artifact.** *"At Hermes's measured ~600 tokens/tool schema average, all 37 would add ~16-22k tokens to EVERY API call while enabled — larger than the entire Hermes core toolset"* (`optional-mcps/comfy-cloud/manifest.yaml:24-27`); and AllTrails' *"5 tools … ~24K tokens total"* (`optional-mcps/alltrails/manifest.yaml:33-37`). *Why it transfers:* August Trading's context-window discipline (`utils/contextWindow.ts`) has no per-tool schema accounting; a measured tokens-per-tool constant would let the app refuse to enable a tool that costs more than the answer is worth.
5. **Refuse the escape hatches, and write the refusal as policy in the data.** Generic SQL/GraphQL "execute anything" tools are excluded across four unrelated vendors — `query-particle-sql` (`attio/manifest.yaml:23-24`), `execute_query` + `create_cloud_connection` (*"raw ClickHouse-SQL escape hatch + direct-DB credential minting"*, `betterstack/manifest.yaml:23-26`), the *"Advanced API access" trio — a generic execute-any-GraphQL escape hatch (meta-layer — Hermes policy: no server-side API-execute indirection)"* (`monday/manifest.yaml:22-24`), `all_monday_api` — plus *"server-side API-execute indirection"* as the named Hermes policy. *Why it transfers:* a single, named rule ("no generic execute-anything tool") is auditable; four per-vendor ad-hoc rules are not. **UNIQUE** to this shard's phrasing, but the pattern is a general one.
6. **Exclude anything that speaks to the outside world on the model's behalf.** `schedule_voice_agent_call` places *"REAL outbound AI phone calls to contacts"* (`close/manifest.yaml:25`); `create_notification` *"pings other users' bell/email"* (`monday/manifest.yaml:23-24`); `railway-agent` *"acts outside Hermes's per-tool approval loop"* (`railway/manifest.yaml:24`); `report_session_summary` is *"outbound telemetry; excluded per Hermes policy (no telemetry without explicit user opt-in)"* (`comfy-cloud/manifest.yaml:41`); `feedback-to-devs` is an *"outbound feedback channel"* (`kiwi/manifest.yaml:26-29`); Gamma's per-person viewer tracking is *"privacy-sensitive telemetry-grade analytics"* (`gamma/manifest.yaml:19-21`). *Why it transfers:* this is a five-vendor convergence on one rule — **side-effecting or outbound tools are excluded by default, not merely warned about.** August Trading's equivalent: any tool that could notify, transact, or publish stays off the default path.
7. **"Search only — booking happens on the linked sites, never in-conversation."** Written verbatim for Kiwi (`kiwi/manifest.yaml:39-40`) and trivago (`trivago/manifest.yaml:32-33`). *Why it transfers:* the strongest possible statement of the boundary between *advising* and *executing* — August Trading's trade-plan → log → order pipeline is exactly this boundary, and the phrasing ("never in-conversation") is worth stealing verbatim for its clarity.
8. **Search-only connectors are allow-listed by default; spending connectors are allow-listed to the read-only subset.** `rentahuman` enables only `search_humans`, `browse_taste_humans`, `list_bounties`, `search_bounties` and keeps everything that *"post or fund bounties, message people, accept applicants, book services, or manage payments"* disabled until explicitly selected (`rentahuman/manifest.yaml:17-18`, `28-36`); `motherduck` enables 9 of 39 (`motherduck/manifest.yaml:21-25`); `comfy-cloud` 20 of 37; `kiwi` 1 of 2. *Why it transfers:* a default posture of *public read-only discovery* for anything connected to money or people.

## 3. Trading-specific findings

- **Long-lived monitoring & scheduled work:** **not in this shard.** The catalog is install-time configuration; no manifest carries a schedule, a retry, a catch-up rule or a breaker. (Adjacent, in the same repo but not this shard: `cron/suggestion_catalog.py` seeds *suggested* cron jobs that the user accepts, and `cron/suggestions.py` latches a dismissal so a suggestion is never re-offered.)
- **Human-in-the-loop approval:** the shard does not implement the gate, it **feeds** it, and it states the gate's *terms* in prose. The runtime gate lives at `tools/mcp_tool_handlers.py:60-135`: on a `trust: untrusted` server, any tool **without** `readOnlyHint=true` must be approved individually, the gate is **fail-closed** on an approval-system error (`mcp_tool_handlers.py:118-123`), and a denied call returns *"The command was NOT run. Do not retry without explicit user direction."* (`mcp_tool_handlers.py:134-135`). The manifests then curate *around* that gate: `railway-agent` is excluded because it *"acts outside Hermes's per-tool approval loop"* (`railway/manifest.yaml:24`), and `robinhood` keeps live-trading tools **on** because *"Hermes's normal tool-approval flow applies"* (`robinhood/manifest.yaml:46-47`). **The audit trail is the approval prompt itself plus a log line — `logger.info("MCP trust gate: user %s '%s' on %s server '%s'", …)` (`mcp_tool_handlers.py:130-131`) — not a persisted decision record.**
- **Post-mortem / reflection loops:** **not in this shard**, but the manifests *preserve* post-mortems in-place as comments: Atlassian's dead `/v1/sse` endpoint keeps its root cause — *"OAuth succeeded but every handshake failed; issue #91538"* (`atlassian/manifest.yaml:15-19`) — so a future reader cannot re-add it. This is a cheap, effective pattern: **the reason a decision was made lives next to the decision.**
- **Multi-agent:** **not in this shard**, except as a *negative* signal: two connectors ship a vendor-side agent as a single opaque tool — `railway-agent` and Grafana's `ask_assistant` (*"opaque delegation to Grafana Assistant (an agent meta-tool) that also bills Assistant usage per call"*, `grafana/manifest.yaml:29-32`) — and **both are excluded**, the Grafana one for the cost reason. Where debate or delegation is offered as one meta-tool, Hermes prefers a flat, individually-approvable surface.
- **Structured logs the model can query:** **not in this shard** (no storage, no log format). The closest thing is the catalog's own diagnostics: `_CATALOG_DIAGNOSTICS` — a list of `(entry_name, kind, message)` tuples where `kind` is `future_manifest` or `invalid` (`hermes_cli/mcp_catalog.py:350`, `353-380`) — surfaced to the UI so a broken or newer manifest is *named* rather than silently missing (`hermes_cli/web_routers/mcp.py:465`).
- **Staying simple as features accumulate:** the shard's whole shape is the answer. **66 integrations, one 250-line schema, zero per-vendor code.** A new vendor is one directory and one YAML file; every cross-cutting concern (auth, secrets, tool selection, suggestion, install notes) is handled by the same loader. The one-time costs are amortised: `_apply_tool_selection` (`mcp_catalog.py:615-721`) is the only place that probes, prompts, and writes a filter, for all 66.

## 4. Non-obvious decisions and gotchas

1. **`default_enabled` and `default_excluded` are mutually exclusive, and the difference is not cosmetic.** Exclude-mode manifests **never probe** the server: the curated list is written as-is and *everything else stays enabled*, including tools the vendor adds later (`hermes_cli/mcp_catalog.py:630-644`). Include-mode manifests probe, show a curses checklist, and — if the probe fails — fall back to the manifest's `default_enabled` or to no filter at all (`mcp_catalog.py:651-672`).
2. **A user's prior tool choice outranks the manifest on reinstall.** The prior `include`/`exclude` list is read *before* the entry is overwritten (`mcp_catalog.py:562-573`, `818-819`). But an exclude-mode manifest with **no prior include** short-circuits the probe and keeps the prior **exclude** list verbatim (`mcp_catalog.py:633-638`). A reinstall can therefore never silently re-enable a tool the user turned off.
3. **"All tools" is stored as the *absence* of a filter**, so tools the vendor adds later are auto-enabled; "no tools" is stored as an *explicit empty include*, so it does not widen to "all" later (`mcp_catalog.py:674-679`, `709-716`). Two opposite user intents need two different encodings.
4. **`connector_slug` ≠ `name`.** 19 of the 66 entries pin a `connector_slug` that differs from the directory/`name` — `atlassian` → `jira`, `betterstack` → `better_stack_mcp`, `prisma-postgres` → `prisma`, `cloudflare` → `cloudflare_mcp`. It must match `^[a-z0-9][a-z0-9_-]*$` (`mcp_catalog.py:289-294`).
5. **Two entries still use the older `/sse` endpoint** (`paypal/manifest.yaml` → `mcp.paypal.com/sse`, `square/manifest.yaml` → `mcp.squareup.com/sse`) while the rest use `/mcp`. The manifest does not explain why, and the loader does not care — `transport.type` is just `http` with a `url` (`mcp_catalog.py:174-192`). A reader who assumes "every catalog entry is `/mcp`" will mis-diagnose these two.
6. **`n8n-official` is the odd entry out twice**: it is the only manifest without the "Nous-approved / Presence in this directory = approval" banner, and the only one whose `transport.url` is a `${ENV}` placeholder rather than a literal (`n8n-official/manifest.yaml:5-13`). Both are deliberate (banner omitted because the entry's own comment explains the distinct name; URL templated because the instance is user-specific), but a validation rule that requires the banner would reject it.
7. **The Figma client_name spoof is a real, working identity hack.** Figma's DCR endpoint allowlists exact client names — *"Claude Code"* and *"Codex" succeed; "Hermes Agent" 403s"* (`figma/manifest.yaml:13-15`) — so Hermes registers as `"Claude Code"` for that host (`tools/mcp_oauth.py:1103`, `1117-1131`), while Figma also *"advertises auth_method=none yet demands the returned client_secret at the token endpoint"*, so the registration is forced confidential (`mcp_oauth.py:1128-1130`). **A manifest comment that names the code path (`tools/mcp_oauth.apply_oauth_provider_defaults`) is the only thing that keeps this discoverable.**
8. **`suggest.hosts` is a curated negative list as much as a positive one.** `netlify` omits `netlify.app`, `vercel` omits `vercel.app`, `webflow` omits `webflow.io` — because pasted preview links are about *the site*, not about managing the platform (`netlify/manifest.yaml:16-17`, `vercel/manifest.yaml:16-17`, `webflow/manifest.yaml:16-17`). And `square` omits the keyword `square` (*"the English word is everywhere"*, `square/manifest.yaml:8-9`). **Suggestion triggers are precision-engineered, not brand lists.**
9. **The `redirect_port` a manifest pins is honoured exactly, and it collides with the CIMD pool.** `_configure_callback_port` gives `oauth.redirect_port` precedence over the five-port CIMD pool (`tools/mcp_oauth.py:1079`; pool at `mcp_oauth.py:942`), and `_resolve_redirect_uri` builds `http://<redirect_host>:<port>/callback` from the same two fields (`mcp_oauth.py:1094-1098`). Asana pins `27890` (`asana/manifest.yaml:36-38`) — which is also `_CIMD_PORTS[0]`. The pinned path **skips** `_reserve_callback_port()` (the socket-holding reservation that closes the select→bind TOCTOU race, `mcp_oauth.py:1083-1088`) and binds later via the `reuse_address` path, and the pinned port is not recorded in `_assigned_cimd_ports` (`mcp_oauth.py:965`, `1081-1082`) — so a CIMD registration and a pinned-port flow can target the same port. Asana requires an *exact* redirect match, so a mismatch is a hard OAuth failure, not a soft one.
10. **Two of the excludes lists are written in two naming shapes on purpose.** Better Stack's docs show display labels while the wire uses snake_case, and the OAuth gate meant the wire names could not be enumerated before authenticating — so the list carries both (`betterstack/manifest.yaml:27-35`). *"Entries below cover BOTH shapes … unmatched entries no-op harmlessly."* The same no-op-harmless principle is stated for Semgrep's drifting vendor surface (`semgrep/manifest.yaml:23-25`) and Grafana's defensive excludes (`grafana/manifest.yaml:36`).

## 5. Weak spots

1. **The curation lives in YAML comments and prose, not in a test.** There is no test in this shard asserting that `close` still excludes `schedule_voice_agent_call`, that `robinhood` still carries its CAUTION, or that `comfy-cloud`'s 20-tool list matches the server. The excludes are only as durable as a reviewer's memory; a well-meaning PR that regenerates a manifest from the vendor's current tool list would quietly re-enable the voice-agent cluster. (`tests/hermes_cli/test_mcp_catalog.py` tests the *loader*'s handling of `default_excluded` — it does not test any specific entry's policy.)
2. **The exclude lists are hand-curated against surfaces nobody in the repo can see.** Better Stack's ~106 tools and Cloudflare's ~3,300 are described from vendor docs and pre-auth inspection only; the manifest itself admits the names could not be enumerated (`betterstack/manifest.yaml:27-29`). The policies are therefore partly best-effort, and the glob patterns may silently stop matching when the vendor renames a tool.
3. **Inconsistent shapes inside a uniform-looking set.** `n8n-official` lacks the banner every other entry has; `paypal` and `square` use `/sse` while the rest use `/mcp`; `miro` and `plaid` URLs carry a trailing slash; `unreal-engine` is the only loopback no-auth entry; 19 of 66 pin a `connector_slug` and 47 do not, with no rule stated for when a slug is required. The schema is permissive by design, so the catalog's conventions drift unless someone enforces them.
