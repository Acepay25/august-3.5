# hermes-agent :: hermes-state-gateway

**Files in shard:** 2 (read: 2, skipped with reason: 0)
**What this shard covers:** the gateway-facing persistence layer of Hermes' `SessionDB` — a SQLite-backed store that keeps a *routing index* (which chat maps to which agent session), the *peer* lookup that reattaches an incoming message to its session after a restart, *orphan* detection/repair for rows that lost their routing identity, a persisted *hygiene failure streak* that drives an escalating cooldown ladder, *backend heartbeats* for liveness, a *handoff state machine* for moving a session between platforms, and the *profile identity* surgery (rename vs delete). The second file adds the Telegram DM topic-mode tables: topic↔session bindings with a per-profile namespace and a lazily-applied schema migration.

Both files are mixins bound onto `SessionDB` through the MRO; neither owns the connection. They talk only through four primitives: `_read_ctx`, `_execute_write`, `_write_sql`, `_read_all` (`hermes_state_gateway.py:4`).

### `hermes_state_gateway.py` (1025 lines, 60 KB)

- **Key abstractions:**

- **Data flow:** an inbound platform event carries a *peer tuple* (`source`, `user_id`, `chat_id`, `chat_type`, `thread_id`, optional `profile_name`). `find_latest_gateway_session_for_peer` first tries the durable `session_key` on the row (`_PEER_BY_KEY_SQL`), then falls back to the full peer tuple (`_PEER_BY_TUPLE_SQL`, `:77`), both under a profile fence and a "reset boundary" fence. The mapping is published by `record_gateway_session_peer` (`:234`), which writes the routing columns onto the `sessions` row *and* (separately) a `gateway_routing` index row whose `entry_json` names the owning `session_id`. Reads of the routing index happen through `gateway_routing_entry_for_session` (`:375`).
- **Non-obvious design decisions:**
  - **"Recoverable" vs "reset" end reasons are two named sets, and the fence between them is the whole recovery policy.** `_RECOVERABLE_END_REASONS = ("agent_close", "ws_orphan_reap", "superseded_by_resume", "startup_orphan_reap")` (`hermes_state_common.py:190`) are *accidents* — recoverable. `_RESET_END_REASONS = ("session_reset", "session_switch", "idle", "daily", "suspended", "resume_pending_expired")` (`hermes_state_common.py:179`) are *deliberate boundaries*. A row ended by a reset reason after the candidate's last activity **rejects** the candidate (`:67-73`), so an explicit `/new` is never silently undone by recovery reaching behind it.
  - **A completed handoff keeps its row recoverable whatever end reason it carries** (`_HANDOFF_OWNED_ROW_SQL:59`). The source interface's teardown runs *after* ownership moved to the destination and can stamp a terminal reason before the destination's first reply; without this clause the handed-off leg is orphaned and a fresh empty session is minted in its place. Deliberate closes are still fenced by the reset rule, so the exception is "ownership was transferred", never "a handoff was attempted".
  - **`record_gateway_session_peer` self-heals a missing target row** (`:274-292`). The `UPDATE` silently no-ops if the row is absent (deferred `create_session` write, or a crash between publishing the route and creating the row), so the method INSERTs the row with full identity instead. The comment names the reason: an identity-less row created later by the lazy `update_token_counts` writer would be *unroutable forever*.
  - **Profile fence** (`:520-528`): a Telegram DM's peer tuple is identical for every bot (chat_id == user_id, no thread), so a sibling profile's legacy row in a shared store would otherwise be adopted. A row is "ours" when `profile_name` is the store's owner or NULL (legacy rows this store minted). Stores outside the profile tree derive no owner and stay unfenced (`_own_profile_name` returns None — `hermes_state_sessions.py:338`).
  - **Ranking is "rows with messages win, but an empty keyed row still beats None"** (`_PEER_BY_KEY_SQL:71-73`). `None` means the gateway mints a new id while the transcript may live under a compression child.
  - **A "never-active" prune needs its own selector** (`:334-373`) because the ordinary `bulk prune`/`archive` are pinned to `ended_at IS NOT NULL`. The predicate is a 7-way "no evidence of a turn": no title, no `last_activity_at`, zero message/tool-call/API-call/input-token/output-token counters, and no row in `messages`. `pinned`/`archived` = explicit keep intent, so they are excluded.
  - **`older_than_days < 0` raises** (`:343-346`) — a negative retention builds a *future* cutoff that matches every never-active keyed row, i.e. a typo becomes a mass delete.
  - **The never-active prune skips rows under a live turn lease or compression lock** (`:429-440`): the predicate reads committed state, so a keyed row whose *first* turn lease is already held (messages not yet flushed) would be deleted mid-turn.
  - **`purge_profile_state` terminalizes instead of deleting delivery obligations** (`:815-827`): pending obligations become `state='abandoned'` (a terminal state the ledger's own retention prunes), while delivered history is left exactly as it was. Routing keys and heartbeat rows — pure bookkeeping for a dead name — *are* hard-deleted.
  - **`rekey_profile_state` refuses on a collision** (`:678-702`): a routing key or a topic binding that would collide under the new namespace raises `ValueError` rather than silently merging two identities.
  - **`session_gateway_runtime` is a precedence ladder for restoring the provider that actually served a session** (`:846-891`): nested `gateway_runtime` (gateway sync / CLI `/model`) → top-level `provider`/`base_url`/`api_mode` (TUI) → `billing_provider` filling a missing provider (the only durable record for a session that never ran `/model`) → a bare `custom` billing class falling back to `billing_base_url` so the reader's "bare-custom heal" can recover `custom:<name>` from the endpoint. Bare buckets (`auto`, `custom`) are *not* routable identities; `auto` is filtered so resume falls back to the ambient default. Empty dict on parse failure — resume uses ambient config.
  - **Heartbeat identity is `profile@host:pid` and `started_at` is the *process* start time** (`:893-908`): a respawn cannot inherit a dead predecessor's heartbeat, and a backend whose previous run died is not mistaken for a freshly-spawned sibling.
  - **`fail_handoff` is a compare-and-swap** (`:989-1001`). Waiters that give up must pass `only_states=("pending",)`: once the watcher has claimed the row (`running`) it owns the terminal state, and an unconditional waiter-side fail races the dispatch — the gateway would overwrite `failed` → `completed` after the user was told the gateway was down (split-brain: the handoff delivered anyway).
  - **`reclaim_stale_running_handoffs` fails rather than re-queues** (`:1003-1025`). A `running` row at watcher startup belongs to a *previous* gateway that died mid-dispatch, and it is poisonous: `request_handoff` only accepts NULL/`completed`/`failed`, so the session could never hand off again, with no error surfaced. The dead gateway may already have switched the session key and dispatched the synthetic turn, so a blind retry risks *double delivery*; a clean terminal state the user can retry from is right.
- **Edge cases & failure handling:**
  - Every JSON parse of a routing `entry_json` is wrapped in `except (ValueError, TypeError, RecursionError)` and the row is skipped (`:381`, `:396`) — a malformed or over-nested entry must not take down the routing scan.
  - `get_handoff_state` (`:947`), `list_pending_handoffs` (`:960`) and `reclaim_stale_running_handoffs` (`:1017`) swallow exceptions, but the last one logs a `logger.warning(..., exc_info=True)` — "swallow but never silently", because a persistently failing reclaim leaves poisonous `running` rows and the operator needs a trace.
  - `has_pending_handoffs` (`:979`) is a bounded existence probe (`LIMIT 1`) and the caller's idle gate **fails open** on error.
  - `_reap_inactive_orphan_desktop_holders` (`:180-232`) **fails closed**: anything whose parent, age, argv or network connections cannot be *proved* safe remains a repair-blocking holder. It is Linux-only and `psutil`-optional (returns `[]` rather than raising when either is missing).
  - `replace_gateway_routing_entries` (`:311-327`) deletes the whole scope and re-inserts inside one write; it returns the keys that were **skipped as retired routes** so the `sessions.json` mirror must leave them out too.
- **Surprising:**
  - `gateway_routing_entry_for_session` (`:375-385`) and `_routing_entries_for_sessions` (`:387-400`) read the **entire** `gateway_routing` table and `json.loads` every entry in Python, because the target `session_id` lives only *inside* `entry_json` — there is no column to index. Every routing lookup and every prune pays a full-table scan.
  - The file mixes process management (`psutil` reaping, `:180`), profile identity surgery (`:665`), routing (`:296`), heartbeats (`:893`) and a handoff state machine (`:938`) in one 1025-line mixin.

  - `list_gateway_sessions` (`:463-486`) calls `self.flush_token_counts()` first, because full rows carry token/cost totals and queued async accounting deltas must be drained or the list is stale.

### `hermes_state_telegram.py` (370 lines, 19 KB)

- **Purpose:** Telegram DM topic-mode tables and the binding between a Telegram forum topic and a Hermes session — plus the migration that creates them.
- **Key abstractions:**
  - `SessionTelegramTopicsMixin` (`:92`) — `apply_telegram_topic_migration` (`:119`), `enable_telegram_topic_mode` (`:164`), `disable_telegram_topic_mode` (`:198`), `is_telegram_topic_mode_enabled` (`:220`), `get_telegram_topic_binding` (`:229`), `list_telegram_topic_bindings_for_chat` (`:240`), `get_telegram_topic_binding_by_session` (`:251`), `delete_telegram_topic_binding` (`:259`), `bind_telegram_topic` (`:304`), `is_telegram_session_linked_to_topic` (`:341`), `list_unlinked_telegram_sessions_for_user` (`:350`).
  - `_topic_read(read, empty)` (`:97`) — the read-path wrapper that makes every topic query tolerant of an absent or pre-v3 table.
  - `_TOPIC_TABLES` (`:28`) — `(table, column list, DDL)` triples for `telegram_dm_topic_mode` and `telegram_dm_topic_bindings`.
  - `_normalize_telegram_topic_profile_name` (`:18`) — empty/missing → `"default"`; the docstring warns that multiplexed callers must pass the *routed* profile (`source.profile`), never the process-global active profile.
- **Data flow:** a Telegram DM topic thread (`chat_id`, `thread_id`) is bound to one `sessions.id` and one `session_key` in `telegram_dm_topic_bindings`. The reverse lookup (`get_telegram_topic_binding_by_session:251`) is served by a **UNIQUE index on `session_id`** (`:149-152`), so a session can be linked to only one topic. `list_unlinked_telegram_sessions_for_user` (`:350`) finds the user's Telegram sessions that have no binding, for the UI that offers to attach one.
- **Non-obvious design decisions:**
  - **The migration is deliberately NOT part of startup reconciliation** (`:119-128`). It runs on explicit `/topic` opt-in only, so an operator can upgrade and keep the old bot behaviour until a user asks for it. This is the opposite of the usual "migrate everything at boot" reflex, and it is deliberate: the tables exist only for the feature.
  - **A read path heals a stale schema.** `_topic_read` (`:97-111`) catches `sqlite3.OperationalError` containing `no such column: profile_name` — a pre-v3 table left by an upgrade — runs the migration, and **retries once**. Without this, the write-only migration is never reached and topic mode silently reads as off forever. If the heal fails, it logs a warning and reads as empty rather than raising.
  - **`profile_name` leads the PRIMARY KEY of both tables** (`:34`, `:50`). A private chat's `chat_id` *is* the user id, identical across bots sharing one `state.db`; without the profile column the tables collide between bots.
  - **SQLite cannot ALTER a PK or an FK, so the v1/v2 → v3 upgrade rebuilds the table** (`:135-147`). `_rebuild_table` runs inside the open `BEGIN IMMEDIATE`, so a crash rolls back instead of stranding rows. A `{table}_new` left behind by an older build's `executescript` crash is dropped first; the legacy table is still intact. v1 bindings had no `ON DELETE CASCADE`, so pruned sessions left orphan rows that the v3 FK (`foreign_keys=ON` on the writer) would reject — only live rows are copied across.
  - **Deleting the last binding disables topic mode in the same transaction** (`:285-300`). A user who disabled topics in the *Telegram client* (not via `/topic off`) would otherwise stay stuck in a mode that can no longer receive anything; the check is a read *inside* the write, so there is no read-after-prune race.
  - **Binding is one-to-one, enforced in the write transaction** (`:317-326`): rebinding the same `(profile, chat, thread)` is idempotent; linking the same session to a *different* topic raises `ValueError`.
  - **Cleanup hot paths never raise** (`:262-266`, `:283-284`): `contextlib.suppress(sqlite3.OperationalError)` and a `return 0` mean an absent or unmigrated table is a silent no-op.
- **Edge cases & failure handling:**
  - `delete_telegram_topic_binding` exists because the Bot API can confirm a topic was deleted *externally*; without the prune, the recovery logic in `gateway.run._recover_telegram_topic_thread_id` cheerfully redirects future inbound messages to the deleted topic, so tool progress, approvals and replies land in the wrong place (`:259-272`).
  - `list_unlinked_telegram_sessions_for_user` falls back to a profile-*unscoped* query if the scoped one raises `OperationalError` (`:360-369`) — an absent bindings table means every session is unlinked, not that the list is empty.
  - `disable_telegram_topic_mode` uses `contextlib.suppress` around both the UPDATE and the binding DELETE (`:207-217`).
  - `is_telegram_topic_mode_enabled` and the other reads go through `_topic_read_one`/`_topic_read_all` (`:113-117`), so a missing table reads as `None`/`[]` and never creates one.
- **Surprising:**
  - The two topic tables are *not* created by startup reconciliation, so a fresh install genuinely has no `telegram_dm_topic_*` tables — and the whole module is written to survive that (every read tolerates absence, every write either creates them via the explicit migration or is suppressed).
  - `enable_telegram_topic_mode` stores Telegram *capability* flags (`has_topics_enabled`, `allows_users_to_create_topics`, `capability_checked_at`) alongside the mode — the mode records what the chat was allowed to do, so a later capability check can be compared against what was recorded.

## 2. Ideas worth stealing

All marked **UNIQUE** — this shard is one repo's persistence layer, and I could not verify cross-repo convergence from this shard alone.

1. **Persist the failure streak against a rotation-stable id, not the live object.** `increment_hygiene_failure_streak` (`:641`) keys on `session_key`, and the comment at `gateway/run.py:130-134` explains why: hygiene builds a *fresh* `AIAgent` per run and re-binds state every time, so the in-process counter was structurally always 0 and a session whose summary model always timed out retried on a fixed interval forever. The persisted streak drives an escalating cooldown ladder (`gateway/run.py:155-157`), and a *successful* compression resets it (`reset_hygiene_failure_streak:659`). **Why it transfers:** August Trading's automation runs are the same shape — a scheduled job that keeps failing on a fixed interval, with the only counter living on an object that is recreated per run.
2. **A handoff/transfer state machine with compare-and-swap and a "poisonous state" reclaim.** `request_handoff` (`:938`) → `claim_handoff` (`:972`) → `complete_handoff`/`fail_handoff` (`:983`, `:989`), plus `reclaim_stale_running_handoffs` (`:1003`) which *fails* stranded `running` rows at startup rather than re-queueing them. **Why it transfers:** the same machine models "a scheduled run was interrupted mid-flight" — fail it cleanly so the user can retry, and never blind-retry, because the previous process may already have delivered.
3. **Compare-and-swap on the terminal write, so two writers cannot both claim the outcome.** `fail_handoff(..., only_states=("pending",))` (`:989-1001`) exists because an unconditional waiter-side fail races the dispatcher and produces a split brain (user told "the gateway is down" while the handoff actually completed). **Why it transfers:** any August Trading surface where a timeout-driven abort and a completion can race — the automation run row, the desktop/Electron IPC.
4. **A delete/restore fence: a tombstone that makes resurrection impossible.** `retire_gateway_routes` (`:410`) publishes a fence so that "a whole-index snapshot taken before a delete in another profile's store cannot restore it when it is saved after it" (`:413-416`); the underlying predicate is `ROUTE_RETIRED_SQL` (`hermes_state_mutation_retirement.py:343-355`), where a *permanent* marker records a delete and an `expires`-bearing marker records a sweep that ages out at a 7-day horizon (`RETRY_HORIZON_S = 7 * 86400`). **Why it transfers:** this is the rule-lifecycle answer — a rule/lesson deleted by a post-mortem must not come back when a stale snapshot is written afterwards, and a *sweep* deletion is explicitly allowed to expire.
5. **Refuse to guess when the evidence is ambiguous, and say why in the record.** `find_orphaned_gateway_sessions` (`:532-588`) returns `adoptable=False` with a machine-readable `reason` ("ambiguous: more than one keyed predecessor matches this window", "ambiguous: more than one unkeyed session claims this predecessor") rather than picking one, and `adopt_orphaned_gateway_session` (`:590`) re-verifies the pair inside the write transaction so a concurrent heal makes it a no-op. **Why it transfers:** the same "report, don't guess" discipline belongs on any repair path in August Trading (e.g. reattaching a trade record to a plan).
6. **Persist the runtime route that actually served a session, and restore by a documented precedence ladder.** `session_gateway_runtime` (`:846-891`): nested `gateway_runtime` → top-level `provider`/`base_url`/`api_mode` → `billing_provider` fill-in → bare `custom` class healed from `billing_base_url`. Bare buckets are not routable identities. **Why it transfers:** August Trading already persists `modelsUsed` per row; the ladder is the missing half — how to *restore* the exact provider/base-url a row was served by rather than recombining the stored model with today's ambient default.
7. **Heartbeat identity carries the process start time, so a respawn is never mistaken for a fresh sibling.** `register_backend_heartbeat` (`:893-908`) requires a `backend_id` stable for the process lifetime (`profile@host:pid`) *and* a `started_at` that is the process start; `prune_stale_heartbeats` (`:918`) reclaims rows past a staleness window. **Why it transfers:** the same trick distinguishes "a stale lease" from "a worker that just started", which is exactly the confusion in any long-lived scheduled-work runner.
8. **A "never-active" detector with a seven-way no-evidence predicate and an explicit negative-retention guard.** `list_never_active_keyed_sessions` (`:334-373`) — no title, no activity, zero of six counters, no message row — plus `older_than_days < 0` raising rather than building a future cutoff that matches everything. **Why it transfers:** the same predicate shape ("routed but never answered") detects leaked fixtures and orphaned automations in August Trading's own stores.
9. **Migrations on explicit opt-in, plus a read path that heals a stale schema once.** `apply_telegram_topic_migration` (`:119`) is not in startup reconciliation, and `_topic_read` (`:97`) catches the exact `no such column` error, migrates, and retries. **Why it transfers:** August Trading has several lazily-created tables; the "read as empty, heal once, never create on read" contract is the safe version.
10. **Column-existence gating instead of table-existence gating.** `_optional_table_columns` (`:156-172`) returns the *live column set* of each optional table and callers gate on the column actually being there (`adapter_profile`, `profile_name`, `session_key`) rather than on the table existing. **Why it transfers:** this is what makes a schema version bump safe for an old store — the migration never has to run eagerly just to satisfy a query.
11. **Terminalize, don't hard-delete, a pending obligation; hard-delete only pure bookkeeping.** `purge_profile_state` (`:815-827`) sets `state='abandoned'` on pending delivery obligations (a terminal state the ledger's own retention prunes) and leaves delivered history untouched, while routing keys and heartbeats — bookkeeping for a name that no longer exists — are deleted outright. **Why it transfers:** a direct answer to "what stops bad rules from accumulating" — you retire them to a terminal state and let a retention sweep reclaim them; you do not erase the evidence.
12. **Namespace-scoped routing with an explicit "this key belongs to that profile" string prefix.** `agent:<name>:` prefixes, rewritten by `rekey_profile_state` (`:665-772`) across five tables *and* inside the JSON payload of the routing entries (`:748-769`). **Why it transfers:** multi-tenant-ish separation (profile / workspace / strategy) without a second database.

## 3. Trading-specific findings

- **Long-lived monitoring & scheduled work:** this shard holds the *durability* half of Hermes' scheduled-work story, not the scheduler itself. Three pieces transfer directly. (a) A persisted failure streak keyed on a stable id, driving an escalating cooldown ladder and reset on success (`hermes_state_gateway.py:641`, `:659`; ladder at `gateway/run.py:155-157`) — the "breaker after repeated failed runs" that a per-run object cannot hold. (b) A heartbeat table with a stable `backend_id` and a process-start `started_at`, plus a staleness-window prune (`:893`, `:918`) — liveness that survives a restart without a dead predecessor's lease being inherited. (c) A handoff/interrupt state machine whose stranded `running` rows are failed, not retried, at startup (`:1003`), because the dead process may already have delivered. The cron scheduler itself lives in the `hermes-cron` shard; this shard is the persistence those jobs lean on.
- **Human-in-the-loop approval:** not in this shard. This shard is the *mechanism* a handoff would use (`request_handoff` → `claim_handoff` → `complete_handoff`/`fail_handoff`, `:938-1001`), including the compare-and-swap that keeps two writers from both claiming the outcome, and the `handoff_error` column that records *why* a transfer failed. The approval decision and its audit trail live elsewhere.
- **Post-mortem / reflection loops:** the closest analogue is the **retirement fence** (`retire_gateway_routes:410`, `ROUTE_RETIRED_SQL` at `hermes_state_mutation_retirement.py:343-355`): a deleted thing gets a tombstone in `state_meta` so a stale snapshot cannot resurrect it; a *sweep*'s tombstone carries `expires` and ages out at a 7-day horizon (`RETRY_HORIZON_S`, `:402`), while a *delete*'s tombstone is permanent. Two tiers — permanent for a deliberate removal, expiring for a sweep — is exactly the discipline needed to keep a learned-rules store from accumulating bad rules.
- **Multi-agent:** the shard's rule is the interesting part. A **branch or delegate child must never inherit the parent's routing key**: `adopt_orphaned_gateway_session` (`:611-617`) copies the donor's routing metadata *only* for compression forks ("parent already ended with end_reason='compression'"), because "Delegate/subagent children are spawned while the parent is still live and must NOT inherit routing keys, or peer recovery could repoint gateway traffic into a subagent's session." The `_COMPRESSION_LINEAGE_CTE` (`:25`) encodes the same membership rule. Debate-vs-subagent is not adjudicated here; what this shard shows is that subagent traffic must be *kept out* of the parent's conversation identity.
- **Structured logs the model can query:** SQLite with FTS elsewhere; here the shape is `sessions` + `messages` plus a per-row "last active" expression computed from several columns (`_sql_session_last_active`, `hermes_state_common.py:272`) and a `_preview_raw` first-user-message projection using `INDEXED BY` to avoid a full-session sort (`hermes_state_common.py:160-166`). The routing index itself is a `scope → session_key → entry_json` table with a JSON payload — cheap to write, but (see weak spots) unindexed for the lookup that matters.
- **Staying simple as features accumulate:** the shard's strongest simplicity move is that **the topic tables do not exist until the feature is used** (`apply_telegram_topic_migration:119`, deliberately excluded from startup reconciliation) and every read tolerates their absence. It also keeps the *policy* in named SQL constants at the top of the file (`:25-174`) rather than inlining predicates, so the recovery rules can be read as one table.

## 4. Non-obvious decisions and gotchas

1. **`session_key` is not a lookup key that can be derived — it is the durable routing identity.** `find_latest_gateway_session_for_peer` (`:488`) can rebuild a *missing or pruned* `sessions.json` mapping from the row's own `session_key`; that is why `record_gateway_session_peer` (`:234`) treats the routing columns as the durable write and `gateway_routing` as the index, not the other way round.
2. **Two different end-reason sets, and the fence direction matters.** `_RESET_END_REASONS` (deliberate) *blocks* recovery of an older row; `_RECOVERABLE_END_REASONS` (accidental) *permits* it. A reader who merges the two sets silently resurrects conversations the user deliberately ended.
3. **`_HANDOFF_OWNED_ROW_SQL` (`:59`) is a deliberate hole in the fence**, and it is easy to misread as a bug: a row whose ownership *transferred* must survive a terminal end_reason stamped by the outgoing interface's teardown.
4. **The `gateway_routing` table has no column for the owning `session_id`** — it lives inside `entry_json`, so every ownership lookup is a full-table scan plus a `json.loads` per row (`:375-400`).
5. **`ROUTE_RETIRED_SQL` reads `json_extract` inside `CASE WHEN json_valid(...)`** (`hermes_state_mutation_retirement.py:346-353`) because `json_extract` *raises* `malformed JSON` on invalid input even behind an `AND json_valid(...)` guard. Any new JSON read over that table needs the same wrapper.
6. **`rekey_profile_state` is namespace string surgery** — `substr(session_key, 1, ?) = ?` against the `agent:<name>:` prefix (`:708-711`, `:748-750`). A key that does not follow the convention silently escapes the rename, and the method reports per-table `counts` but does not fail on a partial rename.
7. **Telegram's private `chat_id` is the user id, identical across bots** — hence `profile_name` leads both primary keys (`hermes_state_telegram.py:34`, `:50`). Forgetting it means one bot's topic state silently overwrites another's in a shared store.
8. **A v1 `telegram_dm_topic_bindings` table (no `ON DELETE CASCADE`) leaves orphan rows that the v3 FK would reject**, so the rebuild copies only rows whose session still exists (`:140-142`). A migration that copies everything will fail the next session prune.
9. **The handoff `failed` write truncates the error to 500 characters** (`fail_handoff:1001`, `reclaim_stale_running_handoffs:1015`) — a long traceback is silently cut.

## 5. Weak spots

1. **Unindexed ownership lookups on the routing index.** `gateway_routing_entry_for_session` (`:375`) and `_routing_entries_for_sessions` (`:387`) `SELECT` the whole table and `json.loads` every entry, because the owning `session_id` is only inside `entry_json`. Every routing lookup, every prune and every orphan scan is O(routes) with a JSON parse each — the single hottest-looking anti-pattern in the shard, and it is duplicated in two methods.
2. **`prune_never_active_keyed_sessions` reports an approximate routing count.** `routing_deleted` is computed by counting candidate routes *before* the delete and subtracting the kept rows (`:453`, `:458`) rather than reading the actual number of routes removed; a concurrent writer re-adding a route makes the number wrong in both directions.
3. **Two unrelated responsibilities in one mixin, and heuristic repair with magic numbers.** The file mixes process reaping (`psutil`, `:180`), profile identity surgery (`:665`), routing (`:296`), heartbeats (`:893`) and a handoff state machine (`:938`) on a single very wide object; and the orphan-contiguity rule hinges on a hard-coded `_ORPHAN_ADOPTION_MAX_GAP_S = 900.0` (`hermes_state_sessions.py:469`) — a magic window that the code acknowledges can splice two conversations if it is wrong (the ambiguity refusal at `:569-570` is the mitigation, not a fix).
