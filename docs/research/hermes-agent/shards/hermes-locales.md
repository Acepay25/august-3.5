# hermes-agent :: hermes-locales

**Files in shard:** 35 (read: 35, skipped with reason: 0)
**What this shard covers:** the entire bundled internationalisation catalogue tree of Hermes Agent — 17 languages × 3 UI surfaces, plus the two machine-generated *key inventories* that act as the schema for the surfaces whose strings do not live in YAML. Concretely: `locales/<lang>.yaml` is the **core** surface (the Python agent, the gateway and the CLI — nested YAML, English base `en.yaml` with 3,486 leaf keys), `locales/<lang>.tui.yaml` is the **TUI** surface (flat dotted keys, 1,356 keys, no English file because the TUI's English base is TypeScript in `ui-tui/`), and `locales/_keys.desktop.json` / `locales/_keys.tui.json` are the exported key sets for the desktop (Electron/React) and TUI surfaces, used to validate third-party language packs. There is no *market*, *order*, *position* or *strategy* vocabulary anywhere in this shard — the trading-adjacent content is entirely about **approval gating, scheduled-job reliability, session-storage failure and turn lifecycle copy**.

---

## 1. File-by-file

### Tier 1 — load-bearing source: full entry

The shard's files are all classified `config`, so formally none of them is Tier 1. Two of them are nevertheless **load-bearing schema**, not configuration: they are the contract that any third-party language pack is checked against, and a wrong entry in them silently drops a translation. They get full entries.

### `locales/_keys.desktop.json`
- **Purpose:** the committed, machine-derived inventory of every leaf key in the **desktop** surface catalogue (`apps/desktop/src/i18n/en.ts`), so that `hermes plugins validate` can check a third-party pack's `<lang>.desktop.yaml` against it.
- **Key abstractions:** a single object `{ "surface": "desktop", "keys": [ … ] }` (`:1-3`). `keys` holds **5,245** dotted leaf paths, sorted, one per line (first key `agents.activeCount` at `:4`, last key `zones.zoneTag` at `:5248`, closing `]`/`}` at `:5249-5250`).
- **Data flow:** produced by `apps/desktop/scripts/i18n-keys.mjs` — the script bundles `src/i18n/en.ts` with esbuild, walks the exported tree with `flattenKeys()` (`i18n-keys.mjs:23-34`), sorts, and renders `{surface, keys}` via `renderKeysFile()` (`:36-38`). `--check` compares the rendered text to the file on disk and throws "out of date with src/i18n/en.ts" if they differ (`:88-98`). The build **never writes it** — a dirty checkout would break `hermes update` (`i18n-keys.mjs:5-9`).
- **Non-obvious design decisions:**
  - The inventory is a *committed build artefact*, not a runtime file — it exists so a **Python** validator can check a **TypeScript** catalogue (`hermes_cli/plugin_validate_locales.py:22` `_KEY_EXPORTS`).
  - "Function-valued entries are keys too (a pack overrides them with a positional `{0}`/`{1}` string)" (`i18n-keys.mjs:6-8`) — so a key may exist in the inventory without a string in the English catalogue.
  - Unknown keys in a pack are a **warning, not an error** (`plugin_validate_locales.py:105-108`): "a pack written against a newer or older Hermes still installs, it just carries dead keys".
- **Edge cases & failure handling:** when the export file is absent, `reference_keys()` returns `None` and the surface's key check is **skipped, never failed** (`plugin_validate_locales.py:30-47`, `:102-104`). A broken reference is logged at debug level — "a broken reference is a Hermes bug, not the pack's".
- **Surprising:** the prefix histogram is very lopsided — `settings.*` alone is 1,494 keys (28%), `assistant.*` 369, `connectorsPage.*` 226, `sidebar.*` 207, `composer.*` 198, `commandCenter.*` 184, `skills.*` 180, `shell.*` 169, `messaging.*` 165. 56 top-level namespaces in total, the smallest (`intro`, `remoteDisplayBanner`) having exactly one key. A 5,245-string surface is far larger than the whole 3,486-key core catalogue.

### `locales/_keys.tui.json`
- **Purpose:** the same idea for the **TUI** surface — the reference key set a third-party `<lang>.tui.yaml` pack is validated against.
- **Key abstractions:** a **bare JSON array** of 1,356 dotted strings (`:1` is `[`, `:2` is the first key `billing.autoReload.aDifferentCard`, `:1357` is the last `userMessages.turn.withProvider`, `:1358` is `]`). No `surface` wrapper — unlike `_keys.desktop.json`.
- **Data flow:** consumed by `hermes_cli/plugin_validate_locales.py:30-47`, which tolerates both shapes (`data.get("keys") if isinstance(data, dict) else data`). There is no generator script for this file in the shard's reach — it is hand-maintained, unlike the desktop export.
- **Non-obvious design decisions:** the TUI surface is split into **40+ namespaces by feature** (`billing.*`, `canonical.*`, `chatBits.*`, `composer.*`, `connection.*`, `connectors.*`, `content.*`, `gatewayMsg.*`, `help.*`, `hints.*`, `hubs.*`, `journey.*`, `libText.*`, `pickers.*`, `prompt.*`, `secure.*`, `session.*`, `slashCmd.*`, `status.*`, `subscription.*`, `userMessages.*`). The `canonical.*` namespace is the interesting one: it holds the **failure vocabulary of the input pipeline** — `canonical.submit.admissionNotConfirmed`, `canonical.submit.deliveryNotResent`, `canonical.submit.executionUnconfirmed`, `canonical.submit.imageNotSubmitted`, `canonical.submit.inputRetained`, `canonical.submit.legacyUnconfirmed`, `canonical.queue.notSavedDraftKept`, `canonical.queue.notSavedQueueKept`, `canonical.queue.statusInputNotSaved`. Every one of these is a *distinct, named* way a submission can fail to be confirmed — and the copy for each says the input was **retained**, not lost.
- **Edge cases & failure handling:** `session.common.interpolationFailed` exists as a key — the TUI has a first-class string for a failed interpolation, which the core surface handles by returning the unformatted string (`agent/i18n.py:238-243`).
- **Surprising:** `userMessages.turn.*` is organised **by layer and code**, not by message: `userMessages.turn.code.auth.{title,hint}`, `.code.billing.*`, `.code.contextOverflow.*`, `.code.overloaded.*`, `.code.rateLimit.*`, `.code.upstreamBlocked.*`, `.code.sslCertVerification.*`, `.code.payloadTooLarge.*`, `.code.providerPolicyBlocked.*`, `.code.contentPolicyBlocked.*`, `.code.formatError.*`, `.code.serverError.*`, `.code.timeout.*` — each with a separate `hint` and `hintNoRetry` variant. The turn-failure taxonomy is a *data table* with 12 error codes × 2 recovery hints, not prose.

## 2. Ideas worth stealing

1. **A committed, generated key inventory is the contract for anything that extends a surface** — `locales/_keys.desktop.json` is derived from TypeScript (`apps/desktop/scripts/i18n-keys.mjs:23-38`) and shipped so a Python validator can check a third-party pack (`hermes_cli/plugin_validate_locales.py:30-47`). *Why it transfers*: August Trading can export its prompt-copy keys (or its validation-schema keys) into a committed JSON and check any extension against it, instead of letting extensions invent key names. **UNIQUE** to hermes-agent in this set.
2. **Three separate invariant tests, not one "does it load"** — `tests/agent/test_i18n.py:39-48` asserts the key set matches **in both directions** (missing *and* extra); `:50-71` asserts the `{placeholder}` token set matches English per key ("a mistranslated placeholder would either raise KeyError at runtime or silently drop the interpolated value"); `:73-80` asserts no literal `\n` survives (a double-escaped newline renders as visible `\n` text). The **placeholder-parity** test is the one worth copying into any system that interpolates values into prompts. **CONVERGENT** in spirit with a single-source canonical-module discipline; **UNIQUE** in this exact form.
3. **Layered catalogs where *every* layer may be partial** — `agent/i18n_layers.py:1-13`: plugin packs > user overlay (`$HERMES_HOME/locales/<lang>.yaml`) > bundled > the same chain for English > the bare key. A user can override a single string without forking the catalogue. *Why it transfers*: an operator-facing override file for trading copy, with no need to re-ship the app.
4. **The base file carries the comments; the translations carry none** — `en.yaml` holds 51 comment lines stating real platform constraints (Discord button ≤ 80 chars, Telegram toast cut at 200 chars, MarkdownV2 bodies). A translator editing `de.yaml` sees none of it. *Why it transfers*: keep the constraint documentation next to the *English* truth and reference it from the pipeline, rather than duplicating it into every language where it will rot.
5. **`t()` never raises** — `agent/i18n.py:231-243`: target language → English → the bare dotted key; a format failure logs a warning and returns the **unformatted** string. The system degrades instead of throwing inside a turn.
6. **The failure mode of a missing catalogue is documented and gated in CI** — `nix/checks.nix`'s `bundled-locales` check is a regression for #23943/#27632/#35374, where sealed Nix venvs dropped `locales/` and the UI started showing raw keys like `gateway.reset.header_default`. The check asserts the directory exists, ≥ 16 catalogues exist, and `en.yaml` is present. *Why it transfers*: gate the "no raw key ever reaches the user" property in the build, not just in a unit test.
7. **Localise the machine's *input* vocabulary, not only its output** — `locales/en.yaml:18-25` (`approval.inputs.*`) are comma-separated synonym lists, and every language **appends** its own natives (ja: `承認,はい,了解,許可,実行,確認`; ru: `одобрить,да,ок,подтвердить,д`). A parser that only understood English keywords would fail every non-English user. *Why it transfers*: any August Trading approval/confirm flow needs the same treatment.
8. **Per-surface catalogues, not one global file** — `agent/i18n_layers.py:30-31` defines three surfaces (`core`, `tui`, `desktop`); the core catalogue is nested YAML, the TUI catalogue is flat dotted keys, and the desktop surface ships **no bundled YAML at all** (only its key inventory). A TUI string never bloats the CLI catalogue.
9. **The "silent" convention is data the model can rely on** — `locales/en.yaml` documents that a cron response starting with `[SILENT]` suppresses delivery and that an empty script stdout is a silent tick (surfaced in `tips.t149`/`t298`). *Why it transfers*: August Trading's automation/notifier can adopt a literal, machine-checked "no alert" sentinel instead of a magic boolean.
10. **A structured error taxonomy with a fixed recovery hint per code** — `gateway.errors.*` (`locales/en.yaml:679` onward) and the TUI's `userMessages.turn.code.*.{title,hint,hintNoRetry}` split every provider failure into a named code with a *specific* next action. *Why it transfers*: the trading app's provider-error surface should be a table, not a switch of prose.
11. **A single vocabulary of duration/relative-time strings** — `cli.shared.ago_seconds / ago_minutes / ago_hours / duration_s / duration_m / duration_ms / duration_hm / duration_dhm` (`locales/en.yaml:2120-2129`) — one place that knows how to say "3m 12s", so no component invents its own.

## 3. Trading-specific findings

- **Human-in-the-loop approval is a four-tier, localised, audited decision.** `locales/en.yaml:1-46` defines the dangerous-command prompt with **once / session / always / deny** tiers, an unconditional **blocklist** (`:17`), and four exact input vocabularies (`:18-25`). A separate `gateway.exec_approval` block (`:612-...`) adds the `smart_deny` mode — "owner override applies to this one operation only" (`:616`). Every tier's outcome is written back into the chat (`cli.approval.outcome_once / outcome_session / outcome_always / outcome_deny`, `locales/en.yaml:2382-2385`), and a **summary** line records *what did not happen* — "You denied this {noun} — it did not run." / "No answer within {window} — the {noun} did not run." (`:27-33`). This is the audit trail: the decision, its scope, its subject, and its consequence, in one sentence.
- **A timeout is a denial, and the copy says so.** `approval.timeout` (`:11`) — "⏱ No answer in {waited} — **the command was not run**. Ask again to retry, or raise the limit: `hermes config set approvals.timeout {suggested}`". The message states the negative outcome, offers a retry, and hands the operator the exact config key with a pre-computed value. `gateway.exec_approval.timed_out_notice` (`:618`) repeats it: "⌛ Approval timed out after {window} — the command was NOT run."
- **Scheduled work has a write-failure breaker with an explicit catch-up.** `gateway.cron_store.unwritable` (`locales/en.yaml:882`) names the store, the error and *since when*, and says jobs are being skipped; `gateway.cron_store.recovered` (`:883`) says "Cron store {store} is writable again; **{skipped} skipped run(s), catching up once per job**." That is the idempotent-catch-up pattern a monitoring system needs, expressed in one line of user-facing copy.
- **A scheduled job cut short by a restart is told it will run again.** `gateway.shutdown.cron_interrupted` (`:869`) — "Scheduled job '{job}' was cut short because Hermes is {action}; no result this run. It will run again on schedule, or run it now with `hermes cron run {job}'." The job, the reason and the two recovery paths.
- **"Heartbeat" (in-process, idle-triggered) and "cron" (durable) are explicitly different products.** `gateway.heartbeat.set` (`:942`) ends with "Lives while the gateway runs — use `hermes cron` for durable schedules", and `cli.commands.heartbeat.set_note` repeats it. The copy refuses to let a user mistake an in-memory timer for a durable schedule.
- **A busy session has three named input modes, and the user is always told which.** `gateway.busy.behavior_queue_short` (`:745`), `behavior_steer_short`, `behavior_interrupt_short`, each with a long form, plus `busy.status` — "**Busy input mode: `{mode}`** / Messages while busy: _{behavior}_". Queue, steer and interrupt are the three ways a trading app must answer "what happens if I type now?" — here they are a named, switchable, user-visible mode.
- **Storage failure stops the turn rather than losing the message.** `explainer.persistence.locked` (`locales/en.yaml:3632`) — "the turn was stopped because session storage was busy … Your message should already be saved — please send it again in a moment." Alongside `disk`, `corrupt`, `fts_index`, `deleted_wal`, `replaced`, `turn_lease` — a **failure-mode catalogue for the store**, each with its own recovery instruction. Direct analogue of "your trade was logged but the journal write failed".
- **Auto-reset and context exhaustion are told to the user, not hidden.** `gateway.session.auto_reset_notice` (`:824`) and `gateway.errors.context_overflow` (`:679`) both name the cause and give two concrete commands.

## 4. Non-obvious decisions and gotchas

- **There is no `en.tui.yaml`.** The TUI's English base lives in TypeScript in the `ui-tui/` package. `agent/i18n.py:164-177` (`surface_catalog`) skips the bundled layer for the core surface ("the Python renderer already has it") and loads `<lang>.tui.yaml` for the TUI ("the TUI ships only an English catalog in-tree, so its bundled translations live in `locales/<lang>.tui.yaml`"). A reader looking for the English TUI catalogue in this directory will not find it.
- **The desktop surface has no bundled translations either** — only its *key inventory*. The desktop catalogues are TypeScript (`apps/desktop/src/i18n/<lang>_*.ts`), and third parties supply `<lang>.desktop.yaml` packs. So of the three surfaces, only **core** is YAML-bundled-and-translated; TUI is YAML-translated; desktop is inventory-only.
- **Two different JSON shapes for the same idea.** `_keys.tui.json` is a bare array; `_keys.desktop.json` is `{surface, keys}`. `plugin_validate_locales.py:43-46` handles both: `data.get("keys") if isinstance(data, dict) else data`.
- **Two different placeholder conventions.** Core uses **named** `{count}`/`{error}`; the TUI uses **positional** `{0}`/`{1}` because a TUI English entry may be a *function*. The convention is stated in every `.tui.yaml` header (`locales/af.tui.yaml:2-3` — "Function-valued en entries use positional {0}, {1} placeholders"). `agent/i18n.py:239` applies `str.format(**format_kwargs)` — **named only** — so the core and TUI interpolators cannot be the same code.
- **The core catalogue is nested; the TUI catalogue is flat dotted.** `agent/i18n_layers.py:51-60` (`flatten`) converts nested → dotted at load time for the core; the TUI files are authored flat. `parse_locale_file` (`:73-83`) is the strict form used for registration and validation; `flatten` silently drops non-string leaves and `non_text_leaves` (`:63-70`) reports them for the validator.
- **Line count is not a parity signal.** `en.yaml` is 3,975 lines and `fr.yaml` 4,196, for the *same* 3,486 keys, because translations use YAML block scalars. Only the *parsed* key set is meaningful.
- **A regex key-extractor mis-parses block scalars.** `hu.yaml:111-113` puts `Prompt: "{preview}"` on a continuation line of a `|+` block; a naive `^\s*key:` scan reports a spurious `gateway.background.Prompt` key. Only a real YAML parser is safe.
- **`t()`'s last resort is the bare dotted key** (`agent/i18n.py:236`). A missing catalogue therefore shows `gateway.reset.header_default` to the user — the exact symptom the Nix `bundled-locales` check was written for.
- **`SUPPORTED_LANGUAGES` is a hard-coded Python tuple** (`agent/i18n.py:33-35`), not derived from the files on disk. The Nix gate only asserts "≥ 16 catalogues exist", so the *set* on disk and the *set* in code can drift without any check failing.
- **Unknown keys in a third-party pack are a warning, not an error** (`plugin_validate_locales.py:105-108`) — the pack installs and carries dead keys.
- **Two strings are deliberately left untranslated in English** because they shipped in Spanish / Chinese before i18n existed: `platform.google_chat.attachment_fallback` (`en.yaml:1456`) and `platform.wecom.media` (`en.yaml:1509`). The Spanish text lives in `es.yaml` and the Chinese in `zh.yaml`; the English catalogue keeps the legacy text verbatim.

## 5. Weak spots

1. **The translation set is machine-shaped and almost certainly machine-translated.** Every one of the 16 non-English core catalogues is exactly 3,924 lines, and every one of the 16 TUI catalogues is exactly 1,359 lines with an identical 1,356-key set. That is the signature of one bulk generation run, not of 32 human translation efforts. Afrikaans, Irish, Georgian and Hungarian coverage for a developer-agent CLI is a *coverage claim*, not a *quality* claim; the native approval synonyms (`locales/en.yaml:19` and every translation) read like dictionary output.
2. **No test pins the TUI catalogues' key parity.** `tests/agent/test_i18n.py` parametrizes over `i18n.SUPPORTED_LANGUAGES` and reads `locales/<lang>.yaml` — the **core** surface only. The 16 `.tui.yaml` files match `_keys.tui.json` today (verified here), but nothing in the test suite enforces it; only `hermes plugins validate` checks *third-party* packs against the inventory. A dropped key in `ja.tui.yaml` would ship silently.
3. **The staleness check is asymmetric.** `_keys.desktop.json` has a `--check` mode that fails when the export drifts from `en.ts` (`apps/desktop/scripts/i18n-keys.mjs:88-98`), but there is **no equivalent export or check for the TUI inventory**, and the core surface has no inventory at all (the validator reads `en.yaml` directly, `plugin_validate_locales.py:36-38`). A stale `_keys.tui.json` would silently reject valid packs.
4. **The platform constraints live only in English.** The Discord ≤ 80-char button limit, the Telegram 200-char toast cap, the MarkdownV2 escaping rules and the `~20 chars` mobile-truncation note are comments in `en.yaml` — a translator editing `ja.yaml` sees none of them, and a code change to a button label has nothing to catch a regression.
5. **`approval.inputs.*` is an unbounded, undocumented quasi-API.** Each language appends 4-6 native synonyms to the English list, and neither `en.yaml` nor the loader imposes a cap, a normalisation rule, or a "first match wins" contract on the list. The list is now load-bearing parsing surface with no owner.
