# pi :: pi-coding-agent-test

**Files in shard:** 346 (read: 344, skipped with reason: 2)
**What this shard covers:** the *entire* test suite of `packages/coding-agent` in the `pi` reference harness — 346 files, 5.7 MB, 100 % of them classified `tests` by the pre-computed shard manifest. Because the shard's declared type for every file is `tests`, the brief's Tier-2 rule applies to the whole set: every file was opened, and one line per file records what it actually pins. The files promoted to **full entries** below are the ~30 that pin the harness's load-bearing invariants (agent-session lifecycle, compaction/context management, session-tree persistence, tool dispatch, skill loading, and the two test harnesses) — they were read line by line because a reader stealing ideas needs their exact shape, not their names. The shard is a **characterization suite**, not a unit suite: the `test/suite/` directory (`packages/coding-agent/test/suite/README.md:1`) is explicitly the "new harness-based test suite around `AgentSession` and `AgentSessionRuntime`", and it is forbidden from using real provider APIs, real keys, network calls or paid tokens. What the shard proves is therefore *behaviour of the agent loop under a fake provider*, which makes it the single most transferable artefact in `pi` for anyone building a tool-driven analyst app.

## 1. File-by-file

### Tier 1 — read in full (the load-bearing behaviour of the harness)

#### `packages/coding-agent/test/agent-session-auto-compaction-queue.test.ts`
- **Purpose:** pins the auto-compaction decision logic of `AgentSession` — when a turn must be compacted, when it must *not*, and when a retry is forbidden.
- **Key abstractions:** `AgentSession._checkCompaction(assistantMessage, skipAbortedCheck?)` and `AgentSession._runAutoCompaction(reason: "overflow" | "threshold", willRetry: boolean)` (both reached through an explicit cast, because they are private).
- **Data flow:** a fake `streamFn` emits a synthetic assistant message; `_checkCompaction` looks at the *last successful* assistant usage in agent state and calls `_runAutoCompaction` with a reason.
- **Non-obvious design decisions:**
  - "Stale" usage is ignored: an assistant message older than the last compaction entry must not trigger a threshold compaction (`agent-session-auto-compaction-queue.test.ts:246` — "should ignore stale pre-compaction assistant usage on pre-prompt compaction checks").
  - An **error** message (e.g. `529 overloaded`) carries no usage, so the decision is made from the last *successful* assistant's usage, but only if that usage is post-compaction (`agent-session-auto-compaction-queue.test.ts:219`, `:262`).
  - **Overflow recovery is attempted exactly once.** A second `_checkCompaction` on the same overflow does not re-compact, and the session ends with the fixed string `"Context overflow recovery failed after one compact-and-retry attempt. Try reducing context or switching to a larger-context model."` (`agent-session-auto-compaction-queue.test.ts:186`).
  - The threshold is computed from the *selected model's* `contextWindow` minus `reserveTokens`, not from a constant, so a catalog change does not break the test (`agent-session-auto-compaction-queue.test.ts:215`).
- **Edge cases & failure handling:** compaction with only agent-level queued messages must **not** auto-`continue()` (`agent-session-auto-compaction-queue.test.ts:70`); zero-usage and pre-compaction-only usage both suppress the threshold.
- **Surprising:** the test reaches into private methods with `as unknown as { _runAutoCompaction: ... }` casts — the private surface is the *contract* under test.

#### `packages/coding-agent/test/agent-session-branching.test.ts`
- **Purpose:** proves that forking a session truncates history at a chosen user message and that forking works identically in `--no-session` (in-memory) mode.
- **Key abstractions:** `AgentSessionRuntime.fork(entryId)` → `{ cancelled, selectedText }`; `AgentSession.getUserMessagesForForking()`.
- **Data flow:** user messages are addressed by **entry id**, not by index; the runtime forks, the new session starts empty, and the forked text is handed back to the editor.
- **Non-obvious design decisions:** a fork is a *session-level* operation, not a message-level one — `runtimeHost.fork()` replaces the whole session object, and `session` must be re-read from the host afterwards (`agent-session-branching.test.ts:96`).
- **Edge cases & failure handling:** in `--no-session` mode `session.sessionFile` is `undefined` (not `null`) — the two are different absence encodings and the test asserts each separately (`agent-session-branching.test.ts:110`).
- **Surprising:** forking from a *middle* message keeps the prefix (`session.messages.length === 2`, not 0), while forking from the first message empties the session.

#### `packages/coding-agent/test/agent-session-compaction.test.ts`
- **Purpose:** end-to-end (real LLM) verification that manual compaction produces a summary, mutates the session, persists a `compaction` entry, and emits paired events.
- **Key abstractions:** `AgentSession.compact()` → `{ summary, tokensBefore }`; entry type `compaction` with `summary`, `firstKeptEntryId`, `tokensBefore`; events `compaction_start` / `compaction_end`.
- **Data flow:** `session.prompt()` → agent → `session.compact()` → summary written as the **first message** of the new context with role `compactionSummary` → `sessionManager.appendCompaction(...)` → the session file gains one `compaction` entry.
- **Non-obvious design decisions:**
  - The compacted context's first message is a dedicated role (`compactionSummary`), not a user message with summary text — a separate role means a renderer can style it without string sniffing (`agent-session-compaction.test.ts:120`).
  - `compaction_start` / `compaction_end` are a **pair** with a `reason` (`manual` here) and, on the end event, `aborted` and `willRetry` flags (`agent-session-compaction.test.ts:160`).
  - The compaction entry records `firstKeptEntryId` — a *pointer into the entry tree*, not a message count — so the kept window can be re-derived from the log.
- **Edge cases & failure handling:** compaction works with no session file at all (`--no-session`); the entry list is still correct in memory (`agent-session-compaction.test.ts:138`).
- **Surprising:** the events are exactly `{ type: "compaction_start", reason: "manual" }` — an exact-equality assertion, so the event shape is frozen.

#### `packages/coding-agent/test/agent-session-dynamic-provider.test.ts`
- **Purpose:** pins that a provider can be registered or overridden **at runtime** — at extension load, at `session_start`, or from inside a slash command — and that the change reaches the next request without a reload.
- **Key abstractions:** `pi.registerProvider("anthropic", { baseUrl })`; `pi.registerProvider(nativeProviderObject)`; `AgentSession.model.baseUrl`.
- **Data flow:** extension factory → `DefaultResourceLoader` → `AgentSession` → `session.agent.streamFunction` is replaced in the test to *capture* the `baseUrl` the next request would use.
- **Non-obvious design decisions:** the test does not assert on `session.model.baseUrl` alone; it swaps the stream function and captures `model.baseUrl` **at request time** (`agent-session-dynamic-provider.test.ts:84`) — i.e. the assertion is on what the wire would see, not on a cached field.
- **Edge cases & failure handling:** a command-time registration must apply "without reload" — the extension command handler runs, then the next prompt uses the new base URL (`agent-session-dynamic-provider.test.ts:135`).
- **Surprising:** native `pi-ai` providers can be registered wholesale (an object with `id`, `auth`, `getModels`, `stream`) — the harness treats "override a field of a known provider" and "add a whole provider" as one API.

#### `packages/coding-agent/test/agent-session-dynamic-tools.test.ts`
- **Purpose:** pins that a tool registered *after* session start is still callable, is declared in the system prompt, and carries provenance metadata.
- **Key abstractions:** `AgentSession.getAllTools()`, `getActiveToolNames()`; `tool.sourceInfo` = `{ path, source, scope, origin }`; `tool.promptSnippet` / `tool.promptGuidelines`.
- **Data flow:** extension `session_start` handler → `pi.registerTool(...)` → `session.bindExtensions({})` → the tool registry refreshes and the **system prompt is rebuilt** to include `- dynamic_tool: <snippet>` and its guidelines (`agent-session-dynamic-tools.test.ts:130`).
- **Non-obvious design decisions:**
  - Provenance is a first-class field with four axes: `source` (`builtin` | `inline` | `sdk` | `extension`), `scope` (`temporary` | …), `origin` (`top-level` | …), and `path` (`builtin:read`, `<sdk:sdk_tool>`, `<inline:1>`) (`agent-session-dynamic-tools.test.ts:118`).
  - **A tool without a `promptSnippet` is callable but invisible** — it is in `getAllTools()` and in `getActiveToolNames()`, but its name and description are absent from the system prompt (`agent-session-dynamic-tools.test.ts:189`). Prompt visibility is a *separate* switch from availability.
  - The bash tool can opt out of exposing session state to the model via `exposeSessionEnvironment: false`; when it does, the `PI_*` variables are absent (`agent-session-dynamic-tools.test.ts:79`).
- **Edge cases & failure handling:** before `bindExtensions`, the dynamically registered tool is *not* in the registry at all (`agent-session-dynamic-tools.test.ts:113`).
- **Surprising:** `PI_SESSION_ID`, `PI_SESSION_FILE`, `PI_PROVIDER`, `PI_MODEL`, `PI_REASONING_LEVEL` are injected into the tool environment — the model can read its own routing state.

#### `packages/coding-agent/test/agent-session-retry.test.ts`
- **Purpose:** pins the automatic-retry policy: exponential backoff with a hard cap, the event pair, and the guarantee that `session.prompt()` does not resolve before the *whole* agent loop is finished.
- **Key abstractions:** `settings.retry = { enabled, maxRetries, baseDelayMs, maxAgentDelayMs }`; events `auto_retry_start` (with `attempt`, `delayMs`) and `auto_retry_end` (with `success`); `session.isRetrying`.
- **Data flow:** `streamFn` fails the first N calls with `stopReason: "error"`, then succeeds; the session retries with backoff.
- **Non-obvious design decisions:**
  - The delay sequence is `baseDelay * 2^n` **capped** by `maxAgentDelayMs`: the test asserts exactly `[1, 2, 4, 5]` for `baseDelayMs: 1, maxAgentDelayMs: 5` (`agent-session-retry.test.ts:171`) — a regression for issue #8826, where an uncapped backoff would have hung the agent.
  - **The retry resolves the *turn*, not the message.** A regression test proves `prompt()` waits for the tool loop that a *retried* response started (`agent-session-retry.test.ts:236`: "prompt waits for full agent loop when retry produces tool calls") — previously `_resolveRetry()` unblocked `waitForRetry()` on the first `message_end` while tools were still executing.
  - A delayed `message_end` handler must not delay the prompt's completion (`agent-session-retry.test.ts:184`).
- **Edge cases & failure handling:** `maxRetries: 2` means **3 total calls** (initial + 2 retries) and the events are `start:1, start:2, end:success=false` (`agent-session-retry.test.ts:152`).
- **Surprising:** a provider `network_error` finish reason is classified as retryable (`agent-session-retry.test.ts:196`).

#### `packages/coding-agent/test/agent-session-runtime-events.test.ts`
- **Purpose:** pins the **session lifecycle event order** and the cancellation points of the session switch/fork machinery.
- **Key abstractions:** events `session_start`, `session_before_switch`, `session_before_fork`, `session_shutdown`; `AgentSessionRuntime.setBeforeSessionInvalidate()`, `.setRebindSession()`.
- **Data flow:** `runtimeHost.newSession()` / `.switchSession(file)` / `.fork(entryId)` → `session_before_switch`/`session_before_fork` (cancellable) → `session_shutdown` → invalidate the old extension context → rebind → `session_start`.
- **Non-obvious design decisions:**
  - The exact order is pinned by array equality: `["session_before_switch", "session_shutdown", "session_start"]` (`agent-session-runtime-events.test.ts:122`).
  - **A captured extension context is invalidated, not silently dead.** After a replacement, using the old `pi`/`ctx` throws a *teaching* error: `"This extension ctx is stale after session replacement or reload. Do not use a captured pi or command ctx after ctx.newSession(), ctx.fork(), ctx.switchSession(), or ctx.reload()…"` (`agent-session-runtime-events.test.ts:203`).
  - `session_before_switch` returning `{ cancel: true }` leaves the current session file untouched and suppresses both the shutdown and the start (`agent-session-runtime-events.test.ts:139`).
- **Edge cases & failure handling:** a fork at a non-existent entry id is still cancellable and emits `session_before_fork` with `position: "at"` (`agent-session-runtime-events.test.ts:196`).
- **Surprising:** `session_before_switch` fires with `targetSessionFile: undefined` for a *new* session and with the target path for a *resume* — the event payload distinguishes the two reasons (`new` | `resume` | `fork`).

#### `packages/coding-agent/test/agent-session-stats.test.ts`
- **Purpose:** pins the separation between **session totals** (all money/tokens ever spent) and **current context usage** (what is in the window right now).
- **Key abstractions:** `AgentSession.getSessionStats()` → `{ tokens, cost, totalMessages, contextUsage: { tokens, contextWindow, percent } }`; `getUsageCostBreakdown(entries)`.
- **Data flow:** entries are appended to the `SessionManager` (messages, compactions, branch summaries, cache-warm usage entries) and the stats are derived from the entry list.
- **Non-obvious design decisions:**
  - After a compaction, current context usage is **`null`**, not 0 — "unknown", because the kept window has no assistant usage yet (`agent-session-stats.test.ts:130`). Reporting 0 would be a lie that the UI could render as "0 % used".
  - Totals cover *all* entries, including history that compaction removed (`375_000` input tokens in `agent-session-stats.test.ts:130`), while context usage covers only what survives.
  - Tool and summary usage is grouped into a synthetic bucket `"Tools/summaries"`, separate from `"<provider>/<model>"` (`agent-session-stats.test.ts:238`) — so a model-attributed cost total is never polluted by tool overhead.
  - A **cache-warm** usage entry counts toward totals and cost, adds **zero** messages, and is labelled `kind: "cache_warm"` with a `note` (`agent-session-stats.test.ts:203`).
- **Edge cases & failure handling:** a zero-usage assistant message is ignored when looking for the post-compaction anchor (`agent-session-stats.test.ts:253`).
- **Surprising:** the cost breakdown is *computed from the entry list*, not accumulated in a counter, so it is reconstructible after a reload.

#### `packages/coding-agent/test/agent-session-tree-navigation.test.ts`
- **Purpose:** pins the "go back in time" mechanic: navigate the session tree, optionally summarising the branch you are leaving.
- **Key abstractions:** `AgentSession.navigateTree(entryId, { summarize, customInstructions })` → `{ cancelled, aborted, editorText, summaryEntry }`; entry type `branch_summary`; `session.abortBranchSummary()`.
- **Data flow:** tree node → `navigateTree` → (optional) an LLM summary of the abandoned branch → a `branch_summary` entry whose `parentId` is the node being left → the leaf moves to the summary entry.
- **Non-obvious design decisions:**
  - The summary is attached to the **parent of the target**, not to the target: navigating to a nested user message makes the parent have two children (the message and the summary) (`agent-session-tree-navigation.test.ts:141`).
  - Navigating to a **user** message puts that message's text in the editor; navigating to an **assistant** message leaves the editor untouched and the leaf on the assistant entry (`agent-session-tree-navigation.test.ts:73`).
  - `abortBranchSummary()` during summarisation leaves the session **completely unchanged** — same entry count, same leaf (`agent-session-tree-navigation.test.ts:174`).
  - `customInstructions` are appended as an "Additional focus" section and are verified to have been obeyed (`agent-session-tree-navigation.test.ts:222`).
- **Edge cases & failure handling:** navigating to the current leaf is a no-op; `summarize: false` creates no entries at all.
- **Surprising:** the *branch you leave* is what gets summarised, not the branch you return to.

#### `packages/coding-agent/test/compaction.test.ts`
- **Purpose:** the unit-level core of context management — how tokens are estimated, where the cut point is, and what a compaction prepares.
- **Key abstractions:** `calculateContextTokens`, `estimateContextTokens`, `getLastAssistantUsage`, `shouldCompact`, `findCutPoint`, `prepareCompaction`, `compact`, `DEFAULT_COMPACTION_SETTINGS`; `buildSessionContext(entries, leafId?)`.
- **Data flow:** session entries → `estimateContextTokens` (last non-zero assistant usage + trailing-token estimate) → `shouldCompact(tokens, contextWindow, settings)` → `findCutPoint(entries, start, end, keepRecentTokens)` → `prepareCompaction` → `{ firstKeptEntryId, messagesToSummarize, turnPrefixMessages, isSplitTurn, turnStartIndex, tokensBefore, previousSummary }` → LLM summary → a `compaction` entry.
- **Non-obvious design decisions:**
  - The cut is computed from **actual token differences between entries**, not from entry counts (`compaction.test.ts:309`).
  - **A cut that lands mid-turn is legal and is reported explicitly** as `{ isSplitTurn: true, turnStartIndex }`, and the turn's prefix is separated out as `turnPrefixMessages` so the summary can be written for a partial turn (`compaction.test.ts:344`).
  - **System messages are not conversation history.** `prepareCompaction` ignores them: `messagesToSummarize` is empty and the system entry is not counted (`compaction.test.ts:452`).
  - **Re-compaction is skipped when the kept window still fits** — `prepareCompaction` returns `undefined` and nothing happens (`compaction.test.ts:474`).
  - When the window moves past previously kept messages, the *previous* compaction's kept messages are re-summarized, and `previousSummary` is carried forward **as data, not as prose to re-include** (`compaction.test.ts:492` asserts the new summary does not contain the old summary's text).
  - An oversized trailing tool result forces the cut to fall back to the **latest valid cut point before it** (regression #9740, `compaction.test.ts:397`).
- **Edge cases & failure handling:** `getLastAssistantUsage` skips aborted messages *and* all-zero usage (`compaction.test.ts:196`, `:213`); `shouldCompact` returns false when disabled.
- **Surprising:** the estimate is `lastNonZeroUsage.tokens + trailingTokens` — an *estimate* anchored on the last real measurement, not a tokenizer over the transcript.

#### `packages/coding-agent/test/compaction-extensions.test.ts`
- **Purpose:** pins the extension hooks around compaction: `session_before_compact` (cancellable, overridable) and `session_compact` (after the fact).
- **Key abstractions:** `SessionBeforeCompactEvent { preparation, branchEntries }`; `SessionCompactEvent { compactionEntry, fromExtension }`.
- **Data flow:** compaction requested → `session_before_compact` → (optional `{ cancel }` or `{ compaction }`) → summary produced or supplied → entry saved → `session_compact`.
- **Non-obvious design decisions:**
  - An extension may **replace the summary entirely** by returning `{ compaction: { summary, firstKeptEntryId, tokensBefore } }`; the event then carries `fromExtension: true` (`compaction-extensions.test.ts:172`).
  - **A throwing extension does not break compaction** — the default summary is used and `fromExtension` is `false` (`compaction-extensions.test.ts:219`).
  - Multiple extensions run in **registration order**, and the "before" hooks all run before the "after" hooks (`compaction-extensions.test.ts:268`: `["extension1-before", "extension2-before", "extension1-after", "extension2-after"]`).
- **Edge cases & failure handling:** cancelling throws `"Compaction cancelled"` and the `session_compact` event never fires (`compaction-extensions.test.ts:157`).
- **Surprising:** the event payload carries only *data*; the session manager and model runtime live on the session/context, not on the event (`compaction-extensions.test.ts:145`).

#### `packages/coding-agent/test/compaction-summary-reasoning.test.ts`
- **Purpose:** pins the *request* the summariser makes — reasoning level, cache policy, session routing, and what a summary is not allowed to be.
- **Key abstractions:** `generateSummary`, `generateSummaryWithUsage`, `completeSummarization`, `compact`; request options `{ reasoning, apiKey, cacheRetention, sessionId, toolChoice }`.
- **Data flow:** `compact(preparation, model, apiKey, …)` → `completeSimple(model, context, options)` → text + usage → the compaction result.
- **Non-obvious design decisions:**
  - **Summarisation runs with prompt caching OFF** (`cacheRetention: "none"`) *and* a **fresh routing session per call** — each summary is an isolated request (`compaction-summary-reasoning.test.ts:107`, `:111`). A cached summary would reuse a prefix that is about to be discarded.
  - A caller-supplied `sessionId` is honoured for routing but **still** forces `cacheRetention: "none"` (`compaction-summary-reasoning.test.ts:120`).
  - **Three rejections are hard failures**: a summariser that emits a *tool call* (`"Summarization attempted to call a tool"`, `compaction-summary-reasoning.test.ts:158`), a split-turn variant (`"Turn prefix summarization attempted to call a tool"`, `:170`), and a `stopReason: "length"` summary (`"generation hit the token cap"`, `:182`).
  - A length-limited summary is therefore **never persisted** (regression #7048).
  - Reasoning is only set for reasoning-capable models *and* a non-`off` thinking level (`compaction-summary-reasoning.test.ts:200`, `:214`).
- **Edge cases & failure handling:** a split turn with no history still sends the previous summary forward so the context is not lost (`compaction-summary-reasoning.test.ts:129`).
- **Surprising:** Anthropic "refusal fallback" is deliberately **not** implemented here — it is left to `pi-ai` model metadata (`compaction-summary-reasoning.test.ts:226`).

#### `packages/coding-agent/test/compaction-serialization.test.ts`
- **Purpose:** pins how a conversation is turned into text for the summariser.
- **Key abstractions:** `serializeConversation(messages)` → string; label grammar `[User]:`, `[Assistant]:`, `[Assistant tool calls]:`, `[Tool result]:`.
- **Non-obvious design decisions:**
  - **Only tool results are truncated** (at 2000 characters, with the literal tail `"[... 3000 more characters truncated]"`) — user and assistant text is never cut (`compaction-serialization.test.ts:5`, `:33`).
  - **Thinking blocks are omitted entirely** from the summary input (`compaction-serialization.test.ts:57`).
- **Edge cases & failure handling:** a 1500-char tool result is *not* truncated — the threshold is a real cut, not a "keep the head" heuristic.

#### `packages/coding-agent/test/compaction-nested-calls.test.ts`
- **Purpose:** one test, but a load-bearing one: files touched by *nested* tool calls must reach the compaction's file-op ledger.
- **Key abstractions:** `createFileOps()`, `extractFileOpsFromMessage(message, fileOps)`, `computeFileLists(fileOps)` → `{ readFiles, modifiedFiles }`.
- **Non-obvious design decisions:** a nested `write` call whose **arguments were too large to keep** is not counted as a modified file (only `argumentsBytes` survived) (`compaction-nested-calls.test.ts:29`).
- **Surprising:** the read/write ledger is what lets a compaction summary say "I read these files and changed those", so a nested call that is not recorded is a lie in the summary.

#### `packages/coding-agent/test/nested-tool-calls.test.ts`
- **Purpose:** pins the "tool calls a tool" mechanism — nesting ids, event emission, usage accounting, concurrency, and the recorder's hard limits.
- **Key abstractions:** `NestedToolCallRunner`, `NestedCallRecorder`, `NESTED_CALL_LIMITS`; ids of the form `call/1`, `call/1/1`.
- **Data flow:** a model-issued call `call` → a tool invokes `runner.execute("call", "leaf", {})` → a nested call id `call/1` → events `tool_execution_start/update/end` carrying `parentToolCallId` → a per-parent record `{ calls, complete }` → the tool result carries `nestedCalls`.
- **Non-obvious design decisions:**
  - Nested ids are **path-like** and below the caller (`call/1/1`), so a transcript renders a tree without a separate index (`nested-tool-calls.test.ts:76`).
  - **Usage is summed at every depth and counted once**: the middle tool returns only its *own* usage, because the leaf's usage is counted by the recorder (`nested-tool-calls.test.ts:109`).
  - Tools may declare `executionMode: "sequential"`, and the runner **serialises** concurrent calls to them while leaving parallel tools free (`nested-tool-calls.test.ts:145`: max concurrency 1 vs 3).
  - The recorder has **three** separate limits: per-call argument bytes, total argument bytes (32 KiB — four 7000-byte chunks fit), and a max call count; exceeding them marks the record `complete: false` and replaces oversized arguments with `argumentsBytes` (`nested-tool-calls.test.ts:203`, `:220`).
- **Edge cases & failure handling:** a missing tool produces an `isError: true` result rather than throwing (`nested-tool-calls.test.ts:44`).
- **Surprising:** `takeRecord()` is destructive — the record is handed out **once** (`nested-tool-calls.test.ts:95`).

#### `packages/coding-agent/test/file-mutation-queue.test.ts`
- **Purpose:** pins a per-file serialisation queue for mutating tools — the thing that stops two parallel edits to the same file from clobbering each other.
- **Key abstractions:** `withFileMutationQueue(path, fn)`; used by both the `edit` and the `write` tool.
- **Data flow:** `editTool.execute(...)` → `withFileMutationQueue(resolvedPath, …)` → read → transform → write → release.
- **Non-obvious design decisions:**
  - The queue key is the **realpath**, so a symlink and its target share one queue (`file-mutation-queue.test.ts:68`).
  - **Different files proceed in parallel**; the same file is serialised (`file-mutation-queue.test.ts:54`).
  - **The queue is held until the write actually settles — even if the caller aborted.** Two tests prove the second write cannot start until the first write's `writeFile` returns, even after `controller.abort()` (`file-mutation-queue.test.ts:121`, `:163`). The aborted operation still rejects with `"Operation aborted"`, and the file ends up with the *second* write's content.
  - The **edit and write tools share one queue** (`file-mutation-queue.test.ts:96`), so a `write` cannot land between an `edit`'s read and its write.
- **Edge cases & failure handling:** two parallel edits to the same file both survive (`file-mutation-queue.test.ts:79`).
- **Surprising:** the abort semantics are "the mutation is abandoned but the *lock* is kept until the in-flight write returns" — a deliberately conservative choice.

#### `packages/coding-agent/test/tools-manager.test.ts`
- **Purpose:** pins the external-tool bootstrap (`fd`, `ripgrep`) — version discovery, download, and error reporting.
- **Key abstractions:** `getLatestVersion(repo)`, `ensureTool(name, onStatus)`; `ToolStatus = { type: "info" | "warning", message }`.
- **Non-obvious design decisions:**
  - The version is resolved from the **GitHub release redirect** with `redirect: "manual"` — no API call, no token, no rate limit (`tools-manager.test.ts:28`).
  - The redirect body is explicitly **discarded** (`response.bodyUsed === true`) so the socket is released (`tools-manager.test.ts:60`).
  - Failures are **specific**: `"… HTTP 404 without redirect"` vs `"… unexpected redirect to https://github.com/login"` (`tools-manager.test.ts:70`, `:78`).
  - Status is delivered through a **callback**, and the function never writes to the console itself (`tools-manager.test.ts:88`).
  - The error **cause chain** is flattened into the message: `"Failed to download fd: fetch failed: connect ETIMEDOUT …"` (`tools-manager.test.ts:104`).
- **Edge cases & failure handling:** `PI_OFFLINE=1` turns the download into a warning and skips it entirely.
- **Surprising:** a 302 to a *login* page is treated as a distinct failure from a 404 — "the redirect exists but is not a release" is a different user problem.

#### `packages/coding-agent/test/tool-system-prompt-contributions.test.ts`
- **Purpose:** one rule enforced for all eight built-in tools: **the tool's schema and its prompt contribution cannot drift apart**.

## 3. Trading-specific findings

- **Long-lived monitoring & scheduled work — mostly *not* in this shard, but the one thing here that matters is the "breaker" shape.** No cron/automation code appears in this test tree; that lives in another shard. What *is* here is the pattern a monitoring job needs: a bounded retry with a hard cap and a **single** recovery attempt, after which the failure is reported in plain language rather than retried forever (`packages/coding-agent/test/agent-session-auto-compaction-queue.test.ts:186`, `packages/coding-agent/test/agent-session-retry.test.ts:152`, `packages/coding-agent/test/suite/regressions/6647-compaction-retries-transient-stream-drop.test.ts:1`).
- **Human-in-the-loop approval — the *hooks* exist, and cancellation is a first-class return value.** `session_before_compact` can return `{ cancel: true }` and the operation throws `"Compaction cancelled"` (`packages/coding-agent/test/compaction-extensions.test.ts:157`); `session_before_switch` / `session_before_fork` can cancel a session switch or fork and the session is left untouched (`packages/coding-agent/test/agent-session-runtime-events.test.ts:139`). The approval *record* is the event stream, and the `agent_settled` event exists precisely so a caller can wait for the decision to be final (`packages/coding-agent/test/suite/regressions/6363-agent-settled-event.test.ts:1`).
- **Post-mortem / reflection loops — the "branch summary" is the reference's reflection primitive, and it is *bounded by construction*.** When the trader navigates away from a line of reasoning, the abandoned branch is summarised and that summary is the new leaf (`packages/coding-agent/test/agent-session-tree-navigation.test.ts:120`). The gate on bad rules accumulating is structural: a summary is one entry with one `parentId`, replacing a subtree rather than appending to it, and re-summarising a kept window is explicitly *skipped* when the window still fits (`packages/coding-agent/test/compaction.test.ts:474`).
- **Multi-agent — the reference does *not* do debate; it does one agent plus composable sub-tools, and the trade-off is explicit.** "Codemode" lets the model write a script that calls tools; the test pins that the *script* is the thing the model sees, that nested calls run in parallel, and that only the script result comes back (`packages/coding-agent/test/suite/agent-session-codemode.test.ts:1`). The "jev-router" example is the closest thing to multi-agent: a router that lets one model make the first edit and switches models for the rest (`packages/coding-agent/test/jev-router-example.test.ts:1`). Debate is absent; the value is in *routing*, not in arguing.
- **Structured logs the model can query — a JSONL session file IS the log, and it is the compaction input.** Every turn is an append-only entry (`message`, `compaction`, `branch_summary`, `model_change`, `thinking_level_change`, `label`, `usage`, `custom`) in a single JSONL file (`packages/coding-agent/test/session-manager/file-operations.test.ts:1`, `packages/coding-agent/test/session-manager/tree-traversal.test.ts:1`). There is no database: the tree *is* the index, and `buildSessionContext` is a pure projection from entries to messages. A malformed line is skipped and the valid ones are kept (`packages/coding-agent/test/session-manager/file-operations.test.ts:1`). August Trading's SQLite trade log is heavier than it needs to be for the *reasoning* history.
- **Staying simple as features accumulate — the "prompt snippet" contract and the "one tool, one contribution" test are the guard rails.** A tool that adds a schema must also add a `promptSnippet`, or a test fails (`packages/coding-agent/test/tool-system-prompt-contributions.test.ts:24`). A skill must have a description, or it is skipped with a diagnostic (`packages/coding-agent/test/skills.test.ts:79`). The "don't become the product" mechanism is a *table-driven test over the feature list*, not a policy document.

## 4. Non-obvious decisions and gotchas

1. **`describe.skipIf(!API_KEY)` is the norm, not the exception.** Roughly a third of the shard's e2e files make *real* LLM calls (`packages/coding-agent/test/agent-session-compaction.test.ts:32`). The newer `test/suite/` files forbid this outright. A reader who assumes "all these tests are hermetic" will misread the whole shard.
2. **The subscription/privacy expectation is asymmetric.** A compaction summary is allowed to be written by an extension (`fromExtension: true`) and the extension may even *replace* the tokens-before number with `999` (`packages/coding-agent/test/compaction-extensions.test.ts:172`) — a test explicitly asserting that a bogus value is accepted. The boundary is drawn at "the summary text is data", not at "the numbers are data".
3. **`getSessionStats().tokens` counts tokens that no longer exist in the context.** The test asserts `375_000` input tokens for a session whose live context is tiny (`packages/coding-agent/test/agent-session-stats.test.ts:130`). This is deliberate (spend is spend) but it is exactly the kind of number a UI will get wrong.
4. **`session.messages` and `sessionManager.getEntries()` are two different histories.** The test harness has to *synchronise* them by hand (`packages/coding-agent/test/agent-session-stats.test.ts:96`: `session.agent.state.messages = sessionManager.buildSessionContext().messages`) — the agent's state is not automatically derived from the session log.
5. **The system prompt is declared once and diffed into patches between requests** (`packages/coding-agent/test/system-prompt-updates.test.ts:1`), and a *forced* prompt is sent as the leading prompt of a run and **never recorded** in the transcript. A transcript therefore does not contain the whole truth about what the model was told.
6. **Tool-result images that cannot be decoded are kept, not dropped** (`packages/coding-agent/test/tool-result-images.test.ts:1`) — losing a tool's output because one attachment is broken is worse than a broken attachment.
7. **Bash output is written into the transcript as a `bashExecution` message, and a bash result does *not* emit `message_end`** (`packages/coding-agent/test/suite/agent-session-bash-persistence.test.ts:1`) — so the "one message_end per message" invariant has an exception.
8. **`read` truncates a file by lines *and* by bytes, and says which** (`packages/coding-agent/test/tools.test.ts:1`). Truncation is reported, never silent.
9. **A forked session can be "unflushed"** — forking fails with a *reason* rather than corrupting the transcript (`packages/coding-agent/test/suite/agent-session-runtime.test.ts:1`).
10. **The compaction cut can land between two assistant messages of the same turn**, and the harness handles it by separating `turnPrefixMessages` from `messagesToSummarize` (`packages/coding-agent/test/compaction.test.ts:344`). A summariser that only sees whole turns would lose the user's ask.

## 5. Weak spots

1. **The test suite is enormous and partly redundant.** `packages/coding-agent/test/compaction.test.ts`, `packages/coding-agent/test/suite/agent-session-compaction.test.ts` and `packages/coding-agent/test/agent-session-compaction.test.ts` all pin compaction; `agent-session-concurrent`, `agent-session-queue` and `agent-session-prompt` overlap heavily. A reader must check three places before concluding "compaction is covered".
2. **Many tests reach into private methods with `as unknown as { _runAutoCompaction: ... }` casts** (`packages/coding-agent/test/agent-session-auto-compaction-queue.test.ts:75`). The private surface is the contract, which means the contract is not enforceable by the compiler and will break silently on a rename.
3. **A large share of the suite is API-key gated and therefore unrun in most CI configurations** (`describe.skipIf(!API_KEY)`), and the shard's own "characterization" naming (`packages/coding-agent/test/suite/agent-session-compaction.test.ts:125`) signals that these tests are *describing* behaviour rather than *specifying* it. A characterisation suite locks in whatever the code happened to do — including the parts you would want to change.
4. **The legacy harness and the new harness coexist**, and `packages/coding-agent/test/test-harness.ts:466` has to *throw* when the wrong one is used. Two harnesses, two event shapes, and a `suite/README.md` rule that only a human enforces.
5. **The `regressions/` directory is a changelog of bugs, not a taxonomy.** 84 files named by issue number, with no grouping by subsystem, makes "what is still fragile in compaction?" a manual read. The failure-message assertions (e.g. the exact overflow-recovery sentence at `packages/coding-agent/test/agent-session-auto-compaction-queue.test.ts:186`) also make refactors more expensive than they need to be.
