# pi :: pi-evals-telemetry

**Files in shard:** 50 (read: 50, skipped with reason: 0)

**What this shard covers:** Two adjacent packages from the `pi` monorepo that exist to *measure* the agent rather than serve it. `packages/evals` is a behavioural experiment harness: it builds two Docker images that differ only in whether Pi's documentation is present, runs the same eval case in both (a control/treatment pair), and refuses to publish a headline number unless every pair completed cleanly. `packages/telemetry` is a vendor-neutral tracing contract: a callback-scoped span API with no exporter, no ambient context and no backend dependency, plus an in-memory reference adapter, a plain-text trace renderer, and a reusable adapter-conformance suite. Together they are the repo's answer to two questions August Trading keeps asking — "is this change actually better?" and "what happened during that turn?".

**Label basis for §2:** `CONVERGENT` means a second reference repo ships the same *shape* of thing. That was checked at directory level only (`deepseek-harness/packages/telemetry` with an `otel` sub-package owning event/session logs and a transport; `hermes-agent/evals/` holding many one-concern probe scripts); the detailed mechanisms below were read only in this shard, so convergent labels claim shape, not identical behaviour.

### Tier 1 — load-bearing source: full entry

### `packages/evals/src/harness.ts`
- **Purpose:** the vitest-evals adapter — it turns Pi's coding agent into an eval participant: one isolated session per case, in a throwaway home/agent dir/workspace, with the credential scrubbed, the prompt variant enforced, and the run's transcript and token/cost telemetry captured as harness artifacts.
- **Key abstractions:** `createPiCodingAgentHarness(options)` / `createPiDocumentationEvalHarness(options)` (`:471`, `:517`); `PiCodingAgentInput = string | Array<{type:"prompt";content:string} | {type:"reload"}>` — a case can be a *sequence* of prompts and `reload` steps, which is how "configure then use" workflows are tested; `PiCodingAgentHarnessOptions` (`name`, `model`, `noTools`, `tools`, `customTools`, `workspaceFiles`, `transformSystemPrompt`, `expectedPiDocumentation`); `DOCUMENTATION_EVAL_TOOLS = ["read","write","edit","grep","find","ls"]` (`:485`); `applyIsolatedEnvironment` (`:82`); `enterToolSandbox` (`:154`); `verifySystemPrompt` (`:257`); `excludePiDocumentation` (`:494`); `resolveModelSelection` (`:70`).
- **Data flow:** `createHarness` hands the adapter `{input, signal, setArtifact}` → `runPiCodingAgent` (`:275`) → `mkdtemp` a sandbox root → `applyIsolatedEnvironment` swaps `HOME`/`USERPROFILE`/`PI_CODING_AGENT_DIR` and deletes every `PI_EVAL_*` variable, returning a restore closure (`:82-105`) → credential is read *once* from the host agent dir into an `InMemoryCredentialStore` (`:314`) → `ModelRuntime.create` → workspace seeded from `workspaceFiles` → `createAgentSessionFromServices` → the sandbox UID is entered *after* the session is created (`:365`) → the prompt/reload sequence runs → `toTranscriptEvents` converts the session messages into flat transcript events (message / tool_call / tool_result) → `getSessionStats()` supplies tokens, tool calls and cost → the session file is read and stored as the `piSessionJsonl` artifact (`:426`) → the temp root is removed.
- **Non-obvious design decisions:**
  - The eval file is trusted, the *agent* is not: `enterToolSandbox` (`:154`) refuses to run unless the process is root, then `setgroups([])/setgid/setuid` to UID 65532 and **re-verifies** that the demoted process can no longer read every transformed module (`:130 protectTransformedModules`, which chmods Vite's `ssr/` transform cache to 0600 *after* the modules were loaded — otherwise the model could read the judges through the loader cache).
  - The credential is removed from disk (`rm(authPath)`) and from `process.env` when the sandbox identity is set, then restored in `finally` (`:322-334`, `:441-443`): the model cannot read its own API key from the filesystem.
  - `verifySystemPrompt` (`:257`) asserts the prompt that was *actually sent* matches the intended variant (`\n<rules>\n` present, `\n<docs>\nPi documentation (read only` present iff `expectedPiDocumentation`). This is the guard that makes the control arm a real control.
  - `excludePiDocumentation` (`:494`) removes the docs section by **marker**, not by regex, and fails closed if the markers or the `<cwd>` section are missing — it refuses to guess.
  - `promptAgent` (`:238`) treats `stopReason` of `stop`/`toolUse` as success and anything else as a failure, and an empty final text with `stopReason: "stop"` as a failure — an empty answer is an error, not a pass.
- **Edge cases & failure handling:** cleanup errors are aggregated with the run error via `AggregateError` and never swallowed (`:410-425`); a missing session file is itself an error ("Pi eval produced no session file"); the transform-system-prompt path remembers the forced prompt because a forced prompt is not recorded in the transcript (`:389`); `signal` abort is forwarded to `session.abort()` and awaited in `finally`.
- **Surprising:** `createPiDocumentationEvalHarness` **throws unless** `PI_EVAL_CONTAINER === "1"` *and* a sandbox identity is set (`:523-527`) — the documentation harness cannot be constructed on a developer machine at all, by design; the host-only `createPiCodingAgentHarness` has no such guard, which is why `smoke.eval.ts` can run locally.

### `packages/evals/src/report.ts`
- **Purpose:** turns per-arm Vitest JSON into a paired control/treatment comparison with headline lift, efficiency deltas, blocked-pair diagnostics and a flag list.
- **Key abstractions:** `EvalObservation` (identity + metrics + a discriminated `outcome`: `scored`/`unscored`/`skipped`/`pending`/`errored`); `ExpectedEvalRun`; `EvalComparisonReport` (`schemaVersion: 3`); `EvalSetComparison`; `BlockedPair`; `OperationalMetricTotal`; `readTaskObservation` (`:136`); `summarizeEvalObservations` (`:359`); `formatEvalComparisonReport` (`:436`); `classifyCaseStatus` (`:101`); `persistSession` (`:122`).
- **Data flow:** the CLI hands one arm's `vitest.json` → `readTaskObservation` cross-checks the raw Vitest report against the vitest-evals workspace (`assertions.length === 1`, `assertion.fullName === "<eval set> <case>"`, `caseResult.status === assertion.status`, `run.usage.provider/model` must equal the *planned* model) → the session artifact is written to `<variant>/sessions/<sha256>/session.jsonl` → metrics are validated (`optionalMetric` rejects NaN/negative) → the score is validated to 0..1 → an observation is emitted → `groupPairs` joins expected runs with observations → `resolvePair` (`:249`) decides eligible vs blocked → `summarizeEvalObservations` computes pass rates, lift, metric deltas and flags.
- **Non-obvious design decisions:**
  - **Fail closed.** A pair is eligible only when *both* arms produced exactly one scored observation; anything else (missing, duplicate, skipped, pending, unscored, errored) becomes a `BlockedPair` with a human-readable reason, and `publishHeadline` (`:379`) refuses to compute *any* pass rate for that eval set while a single pair is blocked. The README states the rule at `packages/evals/README.md:103`.
  - **Missing ≠ zero.** `operationalTotal` (`:306`) returns `{availableRuns, total: null}` when nothing was measured, so an unmeasured metric can never be silently summed as 0.
  - **The model identity is part of the observation.** If the run reports a different provider/model than the plan, the arm is `errored`, not scored (`:161`) — a mis-provisioned eval cannot pollute the comparison.
  - Flakiness is *derived*, not reported: `comparisonFlags` (`:336`) records each case's pass/fail per run and raises `flaky` if the same case ever produced both. Saturation flags (`control-saturated`, `treatment-saturated`) and `no-lift`/`negative-delta` come from the same function.
  - `difference()` rounds to 15 significant digits (`Number((a-b).toPrecision(15))`) so float noise does not print as `-1.1e-17`.
- **Edge cases & failure handling:** a report that cannot be read is `errored`, not skipped; a malformed metric (negative, NaN, infinite) makes the whole observation `errored` (`:168-176`) rather than publishing a partial number; a missing session artifact does **not** invalidate an otherwise scored eval (`:176` — the session is evidence, the score is the result).
- **Surprising:** `readTaskObservation` persists the session snapshot *before* validating the score (`:160`), so even a failed arm leaves its transcript behind — the failure is auditable.

### `packages/evals/src/plan.ts`
- **Purpose:** turns discovered cases into the full execution plan (case × variant × repetition) and parses Vitest's discovery output into a stable case identity.
- **Key abstractions:** `DOCUMENTATION_VARIANTS = ["without_docs","with_docs"]`; `DiscoveredEvalCase` (`file`, `fullName`, `evalSet`, `caseId`); `EvalTask`; `parseDiscoveredCases`; `createTaskPlan`.
- **Data flow:** Vitest `list --json` output → `parseDiscoveredCases` splits the test name on `" > "` into `<eval set> > <case>` and rejects anything else → `createTaskPlan` emits one task per (case, variant, run number).
- **Non-obvious design decisions:** the identity format `"<eval set> > <case>"` is a **hard requirement**, enforced with a `TypeError`, because it is what makes the two variants' discovery outputs comparable (`:31`). Duplicate identities are rejected at parse time (`:37`).
- **Edge cases & failure handling:** a model identity must contain exactly one `/` and not start or end with one (`:46`); `runsPerVariant` must be a positive safe integer (`:50`).
- **Surprising:** **the variant order alternates by run number** (`:54`): run 1 is control→treatment, run 2 is treatment→control. With a single container per arm this is a cheap, real defence against ordering bias (a warm image, a rate limit, or a provider-side cache favouring whichever arm goes first).

### `packages/evals/src/cli.ts`
- **Purpose:** the orchestrator — parse flags, build images, discover cases in both variants, plan the cohort, run every arm, and write the report.
- **Key abstractions:** `parseEvalCli`; `artifactRunId()` (`<timestamp>_<uuid>`); `containerPath`; `normalizeDiscoveredFile`; `compareDiscovery` (`:106`); `createTaskPlan`; `readTaskObservation`; `summarizeEvalObservations`.
- **Data flow:** flags/env → `provider`/`model` must come as a *pair* (CLI or `PI_PROVIDER`/`PI_MODEL`; half a pair is an error, `:60-66`) → selected files default to `globSync("evals/**/*.docs.eval.ts")` → the artifact directory `.eval/<timestamp>_<uuid>` is created with mode 0700 (`:128-130`) → `buildImages()` → `requireEvalAuthFile` (the host `auth.json` must contain a credential *for the selected provider*, `packages/evals/src/docker.ts:67`) → discovery in both variants → `compareDiscovery` → `protocol.json` (model, images, cases, tasks) + a **sha256 protocol digest** (`:163`) → `expected-runs.json` → the arms run one at a time, each writing its observation to `observations.jsonl` as it goes (`:179-183`) → `report.json` + `report.txt` → **exit code 1 if any pair was blocked** (`:192`).
- **Non-obvious design decisions:** the CLI refuses to run a non-`.docs.eval.ts` file through the documentation runner (`:126`) — the two runners have different guarantees; a file path must resolve inside the package (`:98`); discovered paths must be inside the container package prefix `/repo/packages/evals/` (`:102`).
- **Edge cases & failure handling:** the observations file is rewritten after *every* arm (`:181`), so a run that dies mid-way still leaves a usable partial ledger — the same "write as you go" discipline this research brief mandates.
- **Surprising:** the CLI mixes host-side orchestration with per-variant container runs and does **all** the pairing in-process; the container only ever writes a `vitest.json`, and every decision about what that file means lives in `report.ts` on the host.

### `packages/evals/src/docker.ts`
- **Purpose:** image build + one-arm container execution.
- **Key abstractions:** `BuiltImages`; `buildImages()`; `requireEvalAuthFile(provider)`; `dockerArgs(context, variant, outputDirectory, entrypointArgs)`; `discoverCases`; `runTask`.
- **Data flow:** `buildImages` runs `docker build --target <variant>` for each variant and captures the image id with `docker image inspect` (the ids are recorded in the protocol, so a report names the exact images it ran against); `runTask` mounts a per-task output directory and runs the image with `--project docs <file> --testNamePattern "^<eval set> <case>$"` (the pattern is regex-escaped, `docker.ts:170`); the resulting `vitest.json` path is returned, or `undefined` if the container produced none.
- **Non-obvious design decisions:** every container runs `--read-only` with two `--tmpfs` mounts (`/tmp` and the Vite temp dir) (`:101-104`); the sandbox UID/GID 65532 and the artifact owner UID/GID are passed as env vars so the entrypoint can `chown` the artifacts back to the host user after the run; the auth file is bind-mounted **read-only** at `/run/pi-eval-secrets/auth.json`; the per-task output directory is created with mode 0700.
- **Edge cases & failure handling:** `execute` turns a spawn error into a thrown error and a non-zero status into a status code the caller must check; `requireSuccess` throws with the command and status; `runTask` returns `undefined` for a missing report, which the CLI turns into an `errored` observation.
- **Surprising:** the image name is hashed from the **repository root path** (`createHash("sha256").update(repositoryRoot)`, `docker.ts:44`) — two checkouts get two different image tags, so two worktrees cannot collide on a stale `:local` tag.

### `packages/evals/docker/entrypoint.ts`
- **Purpose:** the in-container runner — validate the image, demote the process, and exec Vitest.
- **Key abstractions:** `assertWorkspace` (`:27`); `assertRootOnly` (`:73`); `assertSandboxCannotRead` (`:80`); `chownTree` (`:65`); `parseId`.
- **Data flow:** `assertWorkspace()` → the container's `/repo` must contain exactly `node_modules, package.json, packages, vitest.base.ts`; `/repo/packages` exactly `evals`; every internal Pi dependency must be free of `docs/ examples/ src/ test/ tests/` and of `readme*`/`changelog*` (otherwise internal docs could act as alternate instructions) (`:39-50`); the `without_docs` variant must *not* contain the coding-agent README/CHANGELOG/docs/examples, the `with_docs` variant must contain them **and they must be non-empty** (`:52-64`); then every evaluator path is checked to be root-only *and* unreadable by the sandbox UID — the latter by actually spawning a child as UID 65532 that tries to read the path and failing if it succeeds (`:80-88`); the coding-agent entry point must resolve to `dist/index.js` (`:103`); the auth file is copied into a per-run agent dir owned by the sandbox user; `HOME` is redirected; then Vitest runs with `--reporter=vitest-evals/reporter --reporter=json --outputFile=/artifacts/vitest.json`, or `vitest list --json` in discovery mode.
- **Non-obvious design decisions:** the entrypoint *asserts the shape of its own image* before doing anything — a wrong image is a loud failure, not a silently contaminated experiment; `assertSandboxCannotRead` is a real probe, not a permission assumption; the container requires an explicit `.eval.ts` file argument (`if (evalFiles.length === 0) throw`, `:120`) so it can never be started in a vague mode.
- **Edge cases & failure handling:** `PI_EVAL_VARIANT` must be exactly `without_docs` or `with_docs` (`:54`); the artifacts directory is chowned back to the host UID at the end (`:147-151`); `process.exit(result.status ?? 1)` propagates the test failure.
- **Surprising:** the entrypoint is the *only* place that knows the two variants differ, and it re-verifies the difference **at run time** — so an image built from a stale cache cannot silently serve the wrong arm.

### `packages/evals/docker/install-runtime.mjs`
- **Purpose:** build the runtime that both variants share — pack the workspace packages, install them as a consumer would, and stage the evaluator sources.
- **Key abstractions:** `produceArtifactSet` / `installConsumer` from the repo's own `scripts/` (the "consumer-install machinery"); `codingAgentName`.
- **Data flow:** `produceArtifactSet({build:false, outDir, repoRoot, source:null})` → `installConsumer` installs only the coding-agent package into `/opt/evaluator/install` → `npm install --ignore-scripts --omit=dev` adds the evaluator's own dev dependencies (vitest, vitest-evals) → **symmetry pass**: every *other* workspace package has its `docs/ examples/ src/ test/ tests/` and `readme*`/`changelog*` deleted from the install, so no internal package can leak documentation to the model (`:44-58`) → the staged tree (`package.json`, `vitest.base.ts`, `packages/evals/{package.json,src,evals,docker}`) is copied into `/opt/evaluator/root`.
- **Non-obvious design decisions:** `npm install --ignore-scripts` everywhere — the untrusted repo's lifecycle scripts never run inside the image; the evaluator's dependencies are installed with `--no-save` so the staged package.json stays authoritative.
- **Edge cases & failure handling:** the script requires exactly one CLI argument (`:12`); a missing package directory is skipped rather than fatal (`:40`).
- **Surprising:** `source: null` is passed to `produceArtifactSet` with the comment "Docker build contexts may omit Git metadata" — the packer is told not to rely on git.

### `packages/evals/docker/Dockerfile`
- **Purpose:** the experimental control itself, expressed as a multi-stage build.
- **Key abstractions:** stages `builder` → `without-docs-install` → `evaluator` → `without_docs` / `with_docs`.
- **Data flow:** the builder mounts the repository ephemerally, runs `npm ci --ignore-scripts && npm run build:offline`, then `install-runtime.mjs /opt/evaluator`. `without-docs-install` copies the install and **removes only the coding-agent's README, CHANGELOG, docs and examples**. Both final stages copy the *same* `node_modules`; they differ solely by `PI_EVAL_VARIANT`. The `evaluator` stage `chmod -R go-rwx` the evaluator sources and `chmod go-rwx` the two config files, and creates `/run/pi-eval-secrets` mode 0700.
- **Non-obvious design decisions:** the comment at the top is the design statement: "Both variants use the same installed runtime. The control removes only the coding-agent documentation whose effect the experiment measures." Everything else — the prompt-section removal, the tool allowlist — is applied by the harness, so the *only* difference between arms is the presence of docs; `node:24-slim` for both stages keeps the base identical.
- **Edge cases & failure handling:** the `--mount=type=bind` of the repo is ephemeral by design, so `node_modules` and `dist` created in `/repo` are discarded and only `/opt/evaluator` persists.
- **Surprising:** the entrypoint runs as `node --experimental-strip-types docker/entrypoint.ts` — TypeScript is executed directly, with no build step for the runner itself.

### `packages/evals/evals/acme-server.ts`
- **Purpose:** a local fake provider API (two wire protocols) so provider-configuration evals need no network and no real key.
- **Key abstractions:** `createAcmeServer(mode: "openai" | "stream")`; `AcmeServer` (`start/stop/reset/origin/baseUrl/validRequestReceived`); `OPENAI_PROVIDER_ID`, `OPENAI_MODEL_ID`, `STREAM_*` constants; `STREAM_API_DOCUMENTATION` (a JSON document shipped as a *workspace file* to the agent).
- **Data flow:** the server binds port 0 on 127.0.0.1 → `/v1/chat/completions` emits SSE chunks (`chat.completion.chunk` + a usage chunk + `[DONE]`); `/generate` emits NDJSON `text_delta`/`usage`/`done` events → it records `validRequestReceived` only when the *probe prompt* was received, which is how the eval proves the model actually called the API it was asked to configure.
- **Non-obvious design decisions:** the credential check is exact (`authorization: Bearer resolved-acme-key` vs `x-acme-key: resolved-stream-key`); a non-probe success is explicitly *not* a valid probe; `reset()` clears the flag between cases.
- **Edge cases & failure handling:** 404 on an unknown path, 405 on a non-POST, 415 on a wrong content type, 400 on unparsable JSON, 422 on a non-object body or a bad model/stream flag, 401 on a bad credential — every failure mode is a distinct status with a literal message the test asserts on.
- **Surprising:** the "API documentation" the agent reads is a **generated fixture written into the workspace**, not a file in the repo — the agent must read a spec and implement against it.

### `packages/evals/evals/configured-runtime.ts`
- **Purpose:** the oracle — after the agent has configured a provider or model, reload the configuration and probe the live runtime to see what actually happened.
- **Key abstractions:** `loadConfiguredModelRuntime(agentDir)`; `inspectProvider(runtime, scenario)`; `inspectAddedModel(runtime, providerId, modelId)`; `ProviderScenario`; `ModelFields`; `ProviderRuntimeOutput`/`AddedModelOutput` (both `{result: …} | {error: string}`).
- **Data flow:** `ModelRuntime.create({modelsPath, authPath, modelsStorePath, allowModelNetwork: false})` → `runtime.refresh({allowNetwork:false})` → `getError()` is checked **first** (a broken `models.json` is reported, not thrown) → the model is looked up → `completeSimple(model, context, options)` performs one real probe → the response's text, stop reason and token usage are returned alongside the *resolved model fields* (context window, max tokens, cost tiers, input modalities).
- **Non-obvious design decisions:** `allowModelNetwork: false` on both create and refresh — the runtime must not phone home to fetch a model list, or the eval would be testing the network rather than the configuration; `inspectAddedModel` compares against a **pristine** runtime (`modelsPath: null`) to prove that adding a model did not *replace* the provider's built-in list (`existingModelsPreserved`).
- **Edge cases & failure handling:** every failure is returned as `{result: {error: string}}` — the eval compares structure, so a missing model or a malformed config is a graded outcome, not a crash; the returned model is the *runtime's* view of the model, not the fixture's expectation.
- **Surprising:** `inspectProvider` returns the probe response **and** `validRequestReceived` from the fixture server — two independent witnesses (the runtime's answer and the wire's answer) must agree.

### `packages/evals/evals/documentation-audit.eval.ts`
- **Purpose:** a *host* eval (no Docker) that asks the agent to audit every documentation page against the implementation and demands a structured verdict.
- **Key abstractions:** a custom tool `submit_documentation_audit` defined with `defineTool` — parameters `verdict: "match"|"mismatch"|"inconclusive"` and `explanation: string`, `additionalProperties: false`, `constrainedSampling: {type:"json_schema", strict:"prefer"}`, and `terminate: true` (`:27`) so the tool call *ends the turn*; `it.for(pages)` — one case per markdown file under `packages/coding-agent/docs` (`:44`); `toolCalls(result)` from vitest-evals.
- **Data flow:** the page list is globbed at module load → each page becomes an `it` case → the prompt states the page, the repository root, and the *evidence standard* ("Report a mismatch only for a clear, user-visible contradiction… names, comments, types, isolated helpers, and tests are not sufficient evidence by themselves… Missing internal detail, ambiguous wording, hypothetical misuse, and undocumented edge cases are not mismatches") → the agent reads the page and the implementation → it must call the tool exactly once → the test asserts one call, `status === "ok"`, and `verdict === "match"`.
- **Non-obvious design decisions:** the prompt teaches the *epistemic standard* explicitly, because a documentation audit without one produces false mismatches; the assertion message includes the explanation so a failure prints the agent's reasoning (`expect(auditCall?.arguments?.verdict, typeof explanation === "string" ? explanation : undefined)`); the tool's `terminate: true` prevents the model from continuing to chat after submitting.
- **Edge cases & failure handling:** a missing or duplicate tool call fails the case; a failed tool call fails the case; `verdict` is constrained by the schema so a malformed verdict cannot be smuggled through.
- **Surprising:** the *expected* verdict is "match" for every page — the eval asserts the **absence of documentation bugs**, which is the hard direction. It is a regression suite over the docs, not a test of the agent's optimism.

### `packages/evals/evals/openai-provider.docs.eval.ts` and `packages/evals/evals/custom-provider.docs.eval.ts`
- **Purpose:** two paired "configure a provider" evals — one for an OpenAI-compatible chat-completions provider, one for a custom streaming (NDJSON) provider.
- **Key abstractions:** `createAcmeServer("openai" | "stream")`; `inspectProvider`; `StructuredOutputJudge({expected, match:"strict", allowExtras:false})`; the `reload` step in the prompt sequence.
- **Data flow:** the server starts before all, the API key is published in `process.env.ACME_API_KEY` / `ACME_STREAM_API_KEY` and deleted after → the prompt gives the agent the provider id, the base URL, where the documentation is and which env var holds the credential → `{type:"reload"}` makes the runtime pick the new configuration up → the oracle then probes the provider and compares the whole result object **strictly** (exact model fields, exact response text, exact token counts).
- **Non-obvious design decisions:** the *credential is only in the environment*, never in the prompt, so the agent must resolve it; the custom-streaming case additionally ships the API documentation as a workspace fixture the agent must read and implement against; `judgeThreshold: null` means a low score is **data**, not a failed suite (the README makes this explicit: "A low score is data, not an infrastructure failure").
- **Edge cases & failure handling:** `beforeEach(() => server.reset())` keeps the probe flag from leaking between cases; `afterAll` deletes the env var and stops the server.
- **Surprising:** the strict judge compares **token counts** (`inputTokens: 3, outputTokens: 2`) — the fake server reports fixed usage, so the comparison proves the runtime *read* the usage block rather than inventing it.

### `packages/evals/evals/models.docs.eval.ts`
- **Purpose:** prove that adding a model to an existing provider does not replace that provider's built-in models.
- **Key abstractions:** `inspectAddedModel`; `StructuredOutputJudge` strict.
- **Data flow:** the prompt asks for one new `openai/fixture-chat` model with an exact display name, text-only input, reasoning on, a 32,768-token window, a 4,096 max output and zero cost → `reload` → the oracle compares against a pristine runtime's model list and returns `existingModelsPreserved`.
- **Non-obvious design decisions:** the expected object is the *complete* model field set, so a partially-configured model is a mismatch rather than a near-miss; the expected `existingModelsPreserved: true` is the actual subject of the test — the "add without breaking" property is a first-class assertion.
- **Edge cases & failure handling:** `inspectAddedModel` returns a structured error for a missing provider, a provider with no models, or a missing model.
- **Surprising:** the model is added to a **built-in** provider (`openai`) rather than a custom one — the hard case, because a naive implementation might replace the provider's whole model list.

### `packages/evals/evals/extensions.docs.eval.ts`
- **Purpose:** prove the agent can create an extension with a tool, reload, and then *use* the tool it created.
- **Key abstractions:** `StructuredOutputJudge` (strict over `{response, extensionErrors, toolLoaded, toolResult}`) plus `ToolCallJudge({expectedTools:[{name:"hello", arguments:{name:"Bob"}}]})` — two judges on one case.
- **Data flow:** prompt 1 → "create a hello tool extension" → `reload` → prompt 2 → "use the hello tool to greet Bob and respond with exactly the tool's greeting" → the oracle reads `session.resourceLoader.getExtensions()` for errors and tool presence, and finds the last non-error `toolResult` for `hello` in the transcript.
- **Non-obvious design decisions:** the outcome is judged on **both** the artifact (the extension loaded, no loader errors) **and** the behaviour (the exact tool arguments and the exact returned text) — "it exists" is not "it works"; the expected result is compared as a whole object with `allowExtras: false`.
- **Edge cases & failure handling:** `extensionErrors` is part of the judged payload, so a broken extension load is a failure even if the text matched.
- **Surprising:** this eval requires the *same agent* to author the tool and then call it — a self-consistency loop, closer to a real user's session than a unit test.

### `packages/evals/evals/tui.docs.eval.ts`
- **Purpose:** a UI eval — does a customisation of the interactive footer keep the rest of the status line intact?
- **Key abstractions:** `RecordingTerminal` (`:24`) — a fake terminal implementing the TUI's terminal interface (columns/rows/kitty protocol/`write`/`moveBy`/`clearLine`/…); the synchronized-output markers `\x1b[?2026h` / `\x1b[?2026l` are used to slice the write stream into discrete **renders**; `createJudge<PiCodingAgentInput, TuiFooterOutput>` (`:192`) with `Levenshtein` from `autoevals` (`:12`, `:229`); `InteractiveMode`, `AgentSessionRuntime`, `createAgentSessionFromServices`, `SessionManager.inMemory`.
- **Data flow:** the harness runs the agent (which must write an extension that replaces the built-in `42.2%/272k (auto)` context readout with a ten-cell bar) → the oracle builds a *second, offline* session whose model has a synthetic 272,000-token context window, seeds an assistant message with a chosen percentage of context used, and drives `InteractiveMode` against the `RecordingTerminal` → each render is captured and the built-in status line is extracted by matching `/\d+(?:\.\d+)?%\/272k(?: \(auto\))?/` → the judge checks: no extension errors, the context window and percentage reported by `getContextUsage()` match, the rendered bar matches the expected glyphs, the old numeric format is **gone**, and the *rest* of the status line is preserved to at least the Levenshtein similarity of the built-in line (with the bar replaced by a `{context}` placeholder).

This is a reusable pattern: capture the built-in behaviour at test time, then assert the delta.

### `packages/telemetry/src/index.ts`
- **Purpose:** the vendor-neutral telemetry contract — span/context types, the settled-snapshot store types, and the type-level schema machinery.
- **Key abstractions:** `TelemetryContext` (`:98`) with `startSpan(options, callback)` and optional `metrics`/`propagation` capabilities; `TelemetrySpan` (`:105`); `SpanOptions` (`:24`); `SpanLink`; `SpanStatus`; `StoredSpan` (`:33`), `StoredTrace`, `StoredMetric` (`:78`); `TraceQuery` (`:55`), `MetricQuery` (`:70`); `TelemetryStore` (`:91`); `TelemetryPropagation`/`TelemetryCarrier`; `defineTelemetrySchema` (`:175`); `createTypedSpanStarter` (`:452`); the whole `Infer*`/`ExactTelemetryAttributes` type family; `createTypedMetrics` (re-exported from `metrics.ts`).
- **Data flow:** a *schema* is plain JSON-serializable data (`version`, `spans`, optional `metrics`); `createTypedSpanStarter(context, schemas)` binds the schemas to one parent context and returns an overload set keyed by span name → at runtime it is a thin wrapper over `telemetryContext.startSpan` that rebinds the starter to the child span (`:437-450`). The schema is used **only for type inference** — no runtime validation, no retention.
- **Non-obvious design decisions:**
  - **The span has no public `end()`.** Settlement is the callback's, so a span cannot leak (README:108). Every post-settlement call is inert.
  - **No ambient context.** The package explicitly refuses `AsyncLocalStorage` (README:519) so the same code runs in the browser, a worker and Node; the parent is always passed as an argument.
  - **`startAttributes` vs `endAttributes`** is a *knowledge-timing* distinction, not two storages (README:424-449): start attributes are required-if-declared and passed at creation; end attributes are always optional enrichment.
  - `ExactTelemetryAttributes<Expected, Actual> = Actual & Record<Exclude<keyof Actual, keyof Expected>, never>` — a *closed* attribute bag that rejects unknown keys even when the value arrives from a variable.
  - `UniqueTelemetrySchemas` makes duplicate span names across composed schemas a **compile-time** error, not a runtime surprise (`:397-410`).
  - `TelemetryStore` is deliberately separate from the recording contract (`:91`) so a query backend (the repo ships a SQLite one elsewhere) can differ from the recorder.
- **Edge cases & failure handling:** `SpanStatus` is a union with an optional error detail; an expected failure is expressed by *setting the status explicitly* rather than by throwing (README:110-121).
- **Surprising:** the contract is deliberately **unspecified for malformed input** ("Adapters trust typed instrumentation inputs; behavior for malformed values is unspecified", CHANGELOG) — validation is pushed to the type system, which is a rare and defensible choice for an instrumentation contract.

### `packages/telemetry/src/memory.ts`
- **Purpose:** the in-memory reference adapter — it records spans and measurements, and doubles as the `TelemetryStore` used by the tests.
- **Key abstractions:** `InMemoryTelemetryContext` (`:282`), implementing `TelemetryContext`, `TelemetryPropagation`, `TelemetryMetrics` **and** `TelemetryStore`; `RecordedTelemetrySpan` (`:37`), `RecordedTelemetryEvent`, `RecordedTelemetryLink`, `RecordedTelemetryMeasurement`; the private `InMemoryTelemetryState`; the module-level `contextCarriers` WeakMap (`:98`) that maps a `TelemetryContext` handle to its carrier.
- **Data flow:** `startSpan` → `startInMemorySpan` creates a mutable record (`:133`), pushes it to `state.spans`, and hands the callback a `TelemetrySpan` façade whose `addEvent`/`setAttributes`/`setStatus` mutate the record while it is unsettled → on settle, `endedMs` is computed from a **monotonic** clock (`performance.now()`) against `startedMs` (wall clock) and an `endSequence` counter is allocated → `getSpans()` returns detached snapshots; `storedSpans()` (`:339`) filters to settled spans only and maps them to the backend-neutral `StoredSpan`; `findTraces` (`:368`) groups by trace id, filters on the *earliest* span's name/start/errors/attributes and paginates with an opaque cursor; `findMetrics` (`:412`) maps each raw measurement to a **count-one** row in its ten-second interval.
- **Non-obvious design decisions:**
  - The carrier codec is three keys: a recorder `scope` (a UUID), a numeric `span`, and an inherited `trace` (`:150-154`). It is deliberately **not** a wire format — "Its keys are an implementation detail, not a public wire format for other adapters" (README:283) — but it survives a JSON round trip and works across processes with no shared registry (proved by `test/propagation.test.ts`).
  - `extract` (`:315`) **falls back to the recorder root** when the carrier is absent or malformed, and treats recognised identifiers as opaque strings — no format validation.
  - A child started from a **settled** parent becomes an *inert* span (`:188`) — the callback still runs and its result is preserved, but nothing is recorded. This is the same "post-settlement calls are inert" rule as the contract.
  - `copyAttributes` (`:110`) copies arrays and drops `undefined` — so a caller mutating its own attribute object after the call cannot rewrite history.
  - `intervalMs` is a 10-second bucket floor (`Math.floor(Date.now()/10_000)*10_000`, `:267`).
- **Edge cases & failure handling:** an exception thrown by the callback sets the status to `error` **unless an explicit status was already set** (`:230-236`) — the last explicit status wins; the error is re-thrown unchanged; the settled flag makes every later mutation a no-op.
- **Surprising:** `getSpans()` deliberately exposes **no timestamps** (the normalised snapshots carry `settled` and `endSequence` instead) while `getTrace()` exposes wall-clock `startedMs/endedMs` — the raw recorder view is timestamp-free, the store view is not (README:281, `test/store.test.ts`).

### `packages/telemetry/src/metrics.ts`
- **Purpose:** the metric capability contract and the typed metric binder.
- **Key abstractions:** `TelemetryMetrics` (factories `counter`/`upDownCounter`/`histogram`); `TelemetryCounter`, `TelemetryUpDownCounter`, `TelemetryHistogram`; `InstrumentOptions` (`description`, `unit`); `HistogramOptions.boundaries`; `TelemetryMetricDefinition` (kind + unit + attributes, `boundaries` only for histograms); `createTypedMetrics(metrics, schemas)`; `TypedTelemetryMetrics`.
- **Data flow:** `createTypedMetrics` flattens the schemas' `metrics` maps into one definition map (`:126-131`) and returns an object whose three factory methods look the definition up by name and pass it to the adapter — so the *adapter* receives the description/unit/boundaries, and the caller gets compile-time name/kind/attribute checking.
- **Non-obvious design decisions:** the metric-kind is part of the name's type — `metrics.counter("call.duration")` is a compile error, so a caller cannot record a duration into a counter (proved by `// @ts-expect-error` cases in `test/metrics.test.ts`); metric attributes reject `cardinality: "high"` at the type level; `MeasurementArguments` makes the attributes argument **optional only when no attribute is required**, and appends an optional `context` for histogram exemplars.
- **Edge cases & failure handling:** the metric helper performs **no runtime attribute validation** (README:236) — the type system is the only guard; instrument metadata is read and retained at runtime, unlike the span starter which retains nothing.
- **Surprising:** duplicate metric names across composed schemas are rejected at compile time (`:120-124`), mirroring the span-name rule — the same "one vocabulary" discipline as August Trading's single-source modules.

### `packages/telemetry/src/noop.ts`
- **Purpose:** the inert context — telemetry you can leave switched on.
- **Key abstractions:** `NOOP_TELEMETRY_CONTEXT` (typed as `TelemetrySpan`, matching the shared inert span); `NOOP_TELEMETRY_METRICS`; `NOOP_TELEMETRY_PROPAGATION`; the frozen noop instruments.
- **Data flow:** `startNoopSpan` simply awaits the callback with the shared inert span — nested spans return the *same* object, so identity checks pass.
- **Non-obvious design decisions:** every export is `Object.freeze`d, and the no-op "never inspects or retains names, attributes, events, or statuses" (README:259) — the name is not even read, so a no-op span cannot become a covert log.
- **Edge cases & failure handling:** a synchronous throw inside the callback becomes a rejected promise with the same value; an async rejection is preserved.
- **Surprising:** `NOOP_TELEMETRY_CONTEXT` is typed as `TelemetrySpan` rather than `TelemetryContext`, because it *is* the inert span and the contract makes a span a valid context (CHANGELOG 1.4.0).

### `packages/telemetry/src/render.ts`
- **Purpose:** plain-text rendering of stored spans — the "read the trace without a dashboard" path.
- **Key abstractions:** `renderTrace(spans: readonly StoredSpan[]): string` (`:10`).
- **Data flow:** spans are indexed by id → those whose parent is missing become roots → an explicit stack (not recursion) walks the tree → each line is `name key=value (durationms)[ error Name: message]`, events print as `· name attrs (+Nms)`, links print as `→ link trace <traceId> span <spanId>`.
- **Non-obvious design decisions:** the tree is defined by **parent relationships, not timestamp containment** (README:297) — a span whose parent is absent is a root, so traces merged from several stores still render; links are printed but **never followed** (a link cycle cannot hang the renderer — `test/render.test.ts` proves a mutual link renders fine); spans are **deduplicated by id** so a merge of two stores does not double-print.
- **Edge cases & failure handling:** the walk is iterative (a 2,000-deep tree is rendered without recursion, and the test proves the last line's indentation) — a deliberate choice against stack overflow on pathological traces.
- **Surprising:** attribute values are printed with `JSON.stringify` (so a string with a newline is escaped and readable) and the input array is never mutated.

### `packages/telemetry/src/testing/conformance.ts`
- **Purpose:** a runner-independent conformance suite any telemetry adapter must pass.
- **Key abstractions:** `createTelemetryAdapterConformance(factory)` (`:44`) returning `{group, name, run()}` cases; `TelemetryAdapterFixture` (a fresh context + a normalised snapshot reader + optional `propagation`/`metrics`).
- **Data flow:** a case acquires a fixture with `await using` (so disposal runs automatically), then exercises the contract: capability identity on roots/spans/extracted parents/inert spans; metric ordering and exemplars; input copying (mutating the caller's boundaries/description/attributes after the call must not change the record); link recording and the "links added after source settlement are ignored" rule; propagation through a JSON round trip, across *fresh adapters* (multiple hops) and the root fallback for absent/unknown carriers; the callback lifecycle (admitted **synchronously, exactly once**, result preserved, status `ok`); rejection identity for sync throws, async rejections and even `Promise.reject(undefined)`; last-explicit-status-wins; attribute merge semantics (later defined value wins, `undefined` ignored, events ordered); inertness after settlement; and nested/concurrent parentage including a deterministic `endSequence` ordering.
- **Non-obvious design decisions:** the suite tests **observable semantics**, not implementation: "It does not test malformed inputs or require suppression of adapter/backend failures" (README:341). The fixture's `getSpans()` may flush an asynchronous exporter first — the contract is about what is *eventually recorded*, not about when.
- **Edge cases & failure handling:** each case is independent and disposes its fixture; the multi-hop case creates two extra fixtures and disposes them too.
- **Surprising:** the conformance suite is written against `node:assert/strict` and lives in a *testing subpath*, so the runtime package stays runtime-neutral (README:341) — a nice boundary.

### `packages/telemetry/src/testing/types.ts`
- **Purpose:** the three types that describe a conformance fixture and a case.
- **Key abstractions:** `TelemetryAdapterFixture` (`AsyncDisposable`, `context`, optional `propagation`, optional `metrics`, optional `getMetrics()`, `getSpans()`); `TelemetryAdapterFixtureFactory`; `TelemetryAdapterConformanceCase` (`group`, `name`, `run()`).
- **Data flow:** a factory produces a fixture per case; the case's `run()` owns the fixture's lifetime.
- **Non-obvious design decisions:** the capabilities are **optional** on the fixture, so a tracing-only adapter passes the suite and simply skips the metrics/propagation groups (`if (!fixture.metrics) return;`).
- **Edge cases & failure handling:** `AsyncDisposable` means an adapter with resources cannot leak them even when a case fails mid-way.
- **Surprising:** the interface forces adapters to expose a *normalised* snapshot reader (`getSpans()`) — the conformance suite compares semantics through a normalisation layer rather than through the adapter's native objects, which is what makes it backend-independent.

### `packages/telemetry/src/testing/index.ts`
- **Purpose:** the testing subpath's public surface.
- **Key abstractions:** re-exports `createTelemetryAdapterConformance` and the three types.
- **Data flow:** `import { createTelemetryAdapterConformance } from "@earendil-works/pi-telemetry/testing"`.
- **Non-obvious design decisions:** it is a separate export path (`./testing` in `package.json`), so the conformance suite is never pulled into a production bundle.

- **Surprising:** a three-line barrel is the whole file — the minimal possible public surface.

## 2. Ideas worth stealing

1. **Fail-closed measurement: an incomplete experiment publishes nothing.** A control/treatment pair contributes to the headline only when *both* arms produced exactly one score; missing, duplicate, skipped, pending, unscored or errored arms become a `BlockedPair` with a reason, the eval set's pass rate is withheld entirely, and the CLI exits non-zero (`packages/evals/src/report.ts:249`, `:379`; `packages/evals/src/cli.ts:192`; rule stated in `packages/evals/README.md:103`). **UNIQUE (mechanism).** *Why it transfers:* August Trading has several "the agent says the plan is good" surfaces whose numbers are currently read as truth. The same rule — a partially-measured population yields "unavailable", not a percentage — applied to accuracy/pass-rate panels would remove an entire class of misleading dashboards.
2. **Missing is not zero.** Operational metrics carry `{availableRuns, total: null}` so an unmeasured metric can never be silently summed as zero (`packages/evals/src/report.ts:306`, pinned by `packages/evals/test/comparison.test.ts`). **UNIQUE.** *Why it transfers:* August Trading's performance/accuracy stats and outcome-engine counters are exactly where a missing sample quietly becomes a 0% loss rate.
3. **A protocol digest that names the exact experiment.** The whole protocol (model, image ids, cases, tasks) is hashed with sha256 and the digest is written into `protocol.json` *and* carried into the report (`packages/evals/src/cli.ts:163`, `:186`). **UNIQUE.** *Why it transfers:* August Trading's trade-log and backtest records could carry a "config + prompt + model" digest, so a "why did this backtest differ" question has an answer without keeping every config forever.
4. **Verify the variant that was actually sent, not the one you intended.** The harness asserts the *system prompt that reached the provider* matches the intended arm (rules section present; docs section present iff the arm says so) and fails closed when the markers are missing (`packages/evals/src/harness.ts:257`, `:494`). **UNIQUE.** *Why it transfers:* August Trading assembles prompts from many layers (`composePrompt` + the prompt registry); a test that asserts "the prompt this turn actually sent contained X" is the cheapest defence against a silently-emptied context.
5. **Alternating order to fight order bias.** The variant order flips on every repetition (`packages/evals/src/plan.ts:54`, pinned by `packages/evals/test/plan.test.ts`). **UNIQUE.** *Why it transfers:* any A/B in August Trading (two prompt framings, two provider orders, "plan-first" vs "chart-first") should alternate which side goes first, or the second side inherits a warm cache.
6. **The judge must be unreadable by the model under test.** The evaluator sources are chmod-root-only, the container drops to UID 65532, and the runner *probes* that the demoted user cannot read the judge or the fixtures (`packages/evals/docker/entrypoint.ts:73`, `:80`; `packages/evals/src/harness.ts:154`). **UNIQUE.** *Why it transfers:* if August Trading ever lets the model grade its own trade analysis, the grading rubric must be outside the model's reach — otherwise the measurement is part of the system under test.
7. **A conformance suite as a reusable contract for any adapter.** One runner-independent suite checks 15 observable behaviours (capability identity, synchronous single admission, result/rejection identity, status rules, attribute merging, event ordering, inertness after settlement, nested/concurrent parentage, links, propagation, metrics) and is executed by *any* backend (`packages/telemetry/src/testing/conformance.ts:44`). **UNIQUE.** *Why it transfers:* August Trading has several persistence paths (SQLite/Capacitor, IndexedDB web fallback, Preferences) with no shared behavioural contract; a conformance suite in the shape of this one would make "the web fallback behaves like native" a testable claim.
8. **Store/query separated from recording, and telemetry declared to be diagnostics, not state.** `TelemetryStore` (`findTraces`/`getTrace`/`findMetrics`) is a distinct interface from the recording contract (`packages/telemetry/src/index.ts:91`), and the README states plainly: do not persist a context or span; carriers are correlation only (`packages/telemetry/README.md:515`). **UNIQUE.** *Why it transfers:* the trade journal is *state*; a run's telemetry is *evidence*. Drawing that line in the schema stops an observability feature from quietly becoming a second source of truth.
9. **Callback-scoped spans with no `end()`.** The span ends when the callback settles; every post-settlement call is inert (`packages/telemetry/README.md:108`, pinned in `packages/telemetry/src/testing/conformance.ts`). **UNIQUE.** *Why it transfers:* August Trading's tool calls and pipeline stages each have a "when does this end?" bug class; making the scope the unit removes the bookkeeping.
10. **Low-cardinality is a compile-time rule for metrics, not a lint rule.** `cardinality: "high"` is a type error on a metric attribute (`packages/telemetry/src/metrics.ts`, README:236) and unknown attribute keys are rejected even when the value comes from a variable. **UNIQUE.** *Why it transfers:* August Trading's analytics are currently free-text; making the allowed attribute set a closed type at the boundary is how you keep a metrics table queryable.
11. **A "render as text" path that needs no dashboard.** `renderTrace` prints the span forest with attributes, durations, errors, event offsets and cross-trace links, iteratively (no recursion), dedup by id, and never follows a link (`packages/telemetry/src/render.ts:10`). **UNIQUE.** *Why it transfers:* a "show me the last 20 analyses and where their time went" plain-text view in the Settings/Health tab is a fraction of the work of a charting dashboard.
12. **Dedicated packages for measurement, kept out of the runtime.** `packages/evals` and `packages/telemetry` are separate packages; the telemetry package has **zero runtime dependencies**, ships its own no-op, and keeps its renderer and conformance suite on separate export paths. **CONVERGENT** (shape only: `deepseek-harness` ships `packages/telemetry` with an `otel` sub-package owning event/session logs and a transport; `hermes-agent` ships an `evals/` directory of one-concern probe scripts — those were read at directory level only). *Why it transfers:* August Trading's AGENTS.md already treats "canonical single-source modules" as a discipline; the same discipline applies to instrumentation — a measurement package that the app can depend on but that never depends on the app.

## 3. Trading-specific findings

- **Long-lived monitoring & scheduled work:** *not in this shard.* `packages/evals` runs one-shot experiments and `packages/telemetry` records in-process spans; nothing here schedules, retries or recovers a job. The nearest transferable property is the **write-as-you-go ledger**: the CLI rewrites `observations.jsonl` after every arm and the CLI exits non-zero on a blocked pair (`packages/evals/src/cli.ts:179-183`, `:192`) — a scheduled run in August Trading should leave the same kind of append-only, always-readable ledger.
- **Human-in-the-loop approval:** the closest thing in this shard is a **structured verdict tool that terminates the turn** — `submit_documentation_audit` takes a constrained verdict + explanation, is schema-constrained (`additionalProperties: false`, `constrainedSampling: strict:"prefer"`) and sets `terminate: true` so the agent cannot keep talking after submitting (`packages/evals/evals/documentation-audit.eval.ts:9`, `:27`). That is exactly the shape August Trading's skill-draft approval and trade-plan proposal gates need: one typed, terminating, machine-checkable submission per decision.
- **Post-mortem / reflection loops:** the eval report is a **reflection layer over its own history** — it compares outcomes arm-to-arm and raises named flags (`no-lift`, `negative-delta`, `control-saturated`, `treatment-saturated`, `flaky`) rather than a bare score, and it *withholds* the headline when any pair is incomplete (`packages/evals/src/report.ts:336`, `:379`). The "flaky" flag — the same case producing both a pass and a fail across repetitions — is the mechanism that stops a noisy outcome from being promoted to a rule. August Trading's learning loop has no equivalent of "one repetition cannot establish stability" (`packages/evals/README.md:80`).
- **Multi-agent:** *not in this shard.* There is no debate, no subagent, no multi-agent comparison here: each arm is a single agent in its own container, and the isolation is deliberate (one process, one fresh home/agent dir/workspace per case). The transferable insight is the negative one — **one agent per isolated arm**; a debate would confound the measurement the experiment is trying to make.
- **Structured logs the model can query:** this is the shard's strongest trading answer. `TelemetryStore` (`packages/telemetry/src/index.ts:91`) gives settled-trace discovery with attribute/name/error/time filters, opaque cursor pagination and metric queries, over a backend-neutral snapshot type — and the in-memory implementation keeps the raw store in a plain array (`packages/telemetry/src/memory.ts:368`), i.e. **no database required**. The trade-log equivalent for August Trading is the same shape: an append-only, settled-record store with attribute filters and a plain-text renderer, queryable without SQL.
- **Staying simple as features accumulate:** three deliberate omissions define this shard's simplicity: no exporter, no global current-span state and no backend dependency (`packages/telemetry/README.md:13`); no `AsyncLocalStorage` (`README:519`); and the eval package contributes **nothing** to the shipped agent — it is a separate workspace package that the app never imports. August Trading's equivalent discipline is already written into its AGENTS.md ("canonical single-source modules"); the transferable rule is that a *measurement* concern must not acquire a dependency on the thing it measures.

## 4. Non-obvious decisions and gotchas

1. **The control arm removes the docs from the *prompt* as well as from disk.** `without_docs` deletes the coding-agent's README/CHANGELOG/docs/examples from the image *and* strips the `\n<docs>\n…\n</docs>` section from the default system prompt (`packages/evals/src/harness.ts:494`). Missing the second half would leave the agent told to read documentation that no longer exists — a broken control that still "works".
2. **The documentation harness cannot even be constructed on a developer machine.** `createPiDocumentationEvalHarness` throws unless `PI_EVAL_CONTAINER === "1"` *and* a sandbox identity exists (`packages/evals/src/harness.ts:523-527`). The guarantee is enforced at construction, not at run time.
3. **Vitest's transform cache is a leak path, and it is closed explicitly.** `protectTransformedModules` chmods the Vite `ssr/` cache to 0600 *after* the modules are loaded, then the demoted process is re-tested against each of them (`packages/evals/src/harness.ts:130-180`). A judge that leaks through a loader cache is still a judge the model can read.
4. **The container asserts its own image layout before running anything.** `/repo` must contain exactly five entries, and every internal Pi dependency must be free of `docs/ examples/ src/ test/ tests/` and of any `readme*`/`changelog*` (`packages/evals/docker/entrypoint.ts:27-52`). The `with_docs` arm additionally asserts those files exist **and are non-empty** (`:57-64`).
5. **A zero score is data; a null score is `unscored`; an error is `errored`.** Four distinct outcomes, and only `scored` participates in the lift (`packages/evals/src/report.ts:34`, `:101`). The eval README makes the same point for the judge layer: "Use `judgeThreshold: null` for comparative scoring. A low score is data, not an infrastructure failure."
6. **`getSpans()` has no timestamps; `getTrace()` does.** The recorder's normalised snapshot carries `settled` and a deterministic `endSequence` instead of times; the store view carries wall-clock `startedMs/endedMs` and a **monotonic** duration (`packages/telemetry/src/memory.ts:339-361`, `packages/telemetry/test/store.test.ts`). Two views of the same record, on purpose.
7. **`findMetrics` on the in-memory adapter returns count-one rows, not aggregated counters.** Each raw measurement becomes its own row in a ten-second bucket (`packages/telemetry/src/memory.ts:408-430`), while the SQLite adapter elsewhere aggregates per series and interval (README:293). Two adapters with the same interface and different aggregation semantics — a real trap for anyone writing a query that assumes buckets.
8. **Propagation identifiers are opaque strings.** `extract` only checks that the required carrier keys hold strings; it does not validate any format, and an external scope is accepted as-is (`packages/telemetry/src/memory.ts:315-330`, pinned by `packages/telemetry/test/propagation.test.ts` "treats recognized carrier identifiers as opaque strings").
9. **A settled span can still be linked to and injected; a settled *source* silently ignores `addLink`.** Asymmetric by design, and pinned by two conformance cases (`packages/telemetry/src/testing/conformance.ts:127-157`).
10. **The credentials are removed from the host agent dir and from `process.env` before the model runs**, and restored afterwards (`packages/evals/src/harness.ts:322-334`, `:441-443`). The API key is available to the runtime through an in-memory store, not on disk.

## 5. Weak spots

1. **The experiment cannot be run cheaply.** Every documentation comparison requires a Docker daemon, two image builds (each running `npm ci` and a full build), and one container per arm per repetition (`packages/evals/src/docker.ts:41`, `packages/evals/src/cli.ts:170-184`). The only fast feedback is the trivial host smoke eval — there is no local "run this one case against two prompt variants" mode.
2. **The "no network for the agent" claim is only partial, and the repo says so.** The documentation eval exposes no shell and no web-search tool, but the provider traffic needs container network access, so Docker alone cannot prove that code the agent writes never uses the network (`packages/evals/README.md`, "Provider traffic still requires container network access"). A determined agent with `read`/`write` could still open a socket if the runtime allows it.
3. **The in-memory telemetry store is unbounded, process-local and not a snapshot across pages.** Storage grows without limit; pagination can shift as late spans settle or retention expires; `findMetrics` returns raw count-one rows that do not match the aggregating adapter's semantics (`packages/telemetry/README.md:285`, `:295`; `packages/telemetry/src/memory.ts:408`).
4. **The type-level schema machinery is heavy.** `packages/telemetry/src/index.ts` spends roughly 300 of its ~470 lines on conditional types for attribute inference, and it buys *compile-time* guarantees only — `createTypedSpanStarter` performs no runtime validation and retains nothing (`packages/telemetry/README.md:470`). That is a large complexity budget for optional instrumentation, and a team that does not use the typed starter gets none of it.
5. **The eval package is welded to pi-coding-agent internals.** `buildSystemPrompt`, `getAgentDir`, `createAgentSessionServices`, `getReadmePath`/`getDocsPath` are imported directly (`packages/evals/src/harness.ts:14-27`; `packages/evals/test/harness.test.ts:3`), so an upstream refactor of the prompt builder breaks the evals — including the marker-based docs stripping, which depends on the literal `\n<docs>\n` and `\n<cwd>\n` markers of the prompt format (`packages/evals/src/harness.ts:494`).
