## 2. Verification of the plan's three "junk" examples

All three verified against the source.

### 2.1 The "N/A pattern" skill

- `schemas/tradeAnalysis.ts:317-325` — `DEFAULT_MARKET_CONDITIONS` hard-codes `pattern: 'N/A'`, `candleBehavior: 'N/A'`, etc.
- `schemas/tradeAnalysis.ts:334` — `pattern: coerceToString(mc.pattern) || 'N/A'`. The schema fills in the literal string when the LLM omits the field.
- `utils/verdictSkillDraft.ts:19` — `const family = analysis.detectedPatternFamily || analysis.marketConditions?.pattern;` — and `pattern` is `'N/A'` by default. `if (!family) return null;` does **not** catch the `'N/A'` string.
- Result: a draft skill named like `Repeat BTC Long N/A` with `IF: BTC long setup showing the N/A pattern` and `THEN: take the long only while the N/A pattern holds`. The `if (!family)` guard is truthy for the string `'N/A'`.

**Fix surface (one shared helper, ~15 LOC):**

```ts
// utils/meaningfulLabel.ts
const JUNK = /^(n\/?a|none|null|undefined|unknown|—|-{1,3}|\.{1,3})$/i;
export const isMeaningfulLabel = (s?: string | null): boolean =>
    !!s && s.trim().length >= 3 && !JUNK.test(s.trim());
```

Use at every generation site:
- `verdictSkillDraft.ts:19` — `if (!isMeaningfulLabel(family)) return null;`
- `SkillMemoryService.buildSkillDescription` (line 884) — refuse to write a description that has no claim (so `Repeat: BTC Short Family A — learned from BTC Short Family A.` never lands).
- `MemoryFilesService.syncPatternMemoryUnlocked` — refuse to write a `pattern-memory.md` section whose family is junk.
- The `extractLessonFromPostMortem` regex (line 498) — also accept `**Lesson:** …` and `Lesson: …` on the same line; the current regex's `[\n]{10,}` greedy can swallow across paragraphs.

### 2.2 The "diary lesson = LOSS FORENSIC ANALYSIS header"

- `MemoryFilesService.ts:496-506` — `extractLessonFromPostMortem` regex-mines the first `Lesson:` / `Key takeaway:` line. When the post-mortem formats the lesson as a header (`**Lesson: 🩸 LOSS FORENSIC ANALYSIS…**\n\nThe actual lesson is…`), the regex returns the title because it's on the same line and ≥ 10 chars.
- `MemoryRetrievalService.ts:6-8` — explicit contract: "Diary is RAW STORAGE — never injected. It feeds doctrine rewrites and skill gates; the model sees its conclusions, not its journal."
- Net: the diary is **write-only from the prompt's perspective**. Doctrine distillation (`DoctrineConsolidationService.ts:63` — `closed.slice(-60)`) and skill worth-gate (via cluster trades, not diary) are the only readers.

**Two real fixes (small):**

1. Change `extractLessonFromPostMortem` to walk until it finds a non-header line. If the first match starts with `**` or `#` or has no sentence case, skip it and try the next.
2. Add a separate structured `trade.postMortem.lesson` field in the analysis schema. The post-mortem generator already produces structured markdown; the lesson should be a first-class field, not a regex-mined afterthought. This is the fix the plan's "Tier 1 — fix lesson capture" item points at.

**Don't** try to make the diary injectable — that breaks the design contract and bloats prompts. The diary's value is exactly that it's an offline corpus for the doctrine rewriter.

### 2.3 The "Ranging / Low-ADX Day Playbook"

- `MemoryFilesService.ts:52` — `market-conditions` is a default folder.
- `MemoryGraph.ts:258` — graph walk does include `market-conditions/` notes: `if (node.kind === 'note' && node.path?.startsWith('market-conditions/')) keep(node, 80, []);` — but with a baseline score of **80**.
- `MemoryGraph.ts:281-282` — the only way a note can be promoted past the baseline is if it has an `appliesWhen` overlap with the query. Market-conditions files have `hasDim` edges only, not `appliesWhen` — so they never reach the 500+ tier.
- `MemoryRetrievalService.ts:368-382` — `listRetrievedMemorySources` declares the kinds that ever get pushed into a prompt: `identity`, `skill`, `rules`, `similar`. **No `playbook` kind exists.** The `kindForHit` function on line 64-70 returns `'playbook'` as a fallback only — that branch is dead.
- `MemoryRetrievalService.ts:451-454` — the `similarTradesBlock` is the closest non-skill/non-doctrine block, and even that's verdict-stage only.

**The plan's claim is exactly right: market-conditions files are write-only at the prompt layer.** They're visible in the dashboard (`MemoryBrowser.tsx`), they show up in the graph (with a low score), but the model never reads them during analysis.

**Two ways to resolve this:**

1. **Delete the folder** if no consumer is real. The `market-conditions` defaults (`ranging-day.md`, `after-liquidity-sweep.md`) exist only as starter content. They were created for a "playbook" feature that the rest of the system never implemented.
2. **Make them real** by giving them the same `appliesWhen` graph edges that rules get. Then the baseline score of 80 + `appliesWhen` overlap lifts them into the prompt tier.

I'd recommend option 1 (delete) for any user who isn't already using them as personal notes — keep the folder, but stop seeding templates. Option 2 is real work and a feature in its own right.

## 3. The structural reason it doesn't get smarter

Verified each claim.

### 3.1 Sliding window

- `DoctrineConsolidationService.ts:28` — `DOCTRINE_WINDOW_TRADES = 60`. Doctrine is rebuilt from the **last 60 closed trades only**. The prompt never reflects what the user learned 200 trades ago.
- `DoctrineConsolidationService.ts:119` — `MAX_DOCTRINE_CHARS = 1800` is the injected size.
- `MemoryFilesService.ts:24` — `MAX_DIARY_ENTRIES = 50`. The diary is FIFO.
- The doctrine itself can carry forward beliefs — `DOCTRINE_MAX_REVISE_SHARE = 1/3` (line 30) — but only what the model chose to retain. There is no formal "settled belief" registry.

### 3.2 No cross-coin generalization

- `SkillMeta` is scoped `coin? + direction? + family? + regime?`. The same lesson on BTC and ETH becomes two skills. There is no `generalize()` pass that lifts 2+ matching skills into a coin-less family skill.
- `MemoryGraph.ts` has no `generalizesTo` edge.

### 3.3 Regime sparsity

- `useTradeLogging.ts:226-228` — `marketRegime` is only set when `message.analysis?.marketSnapshot?.regime?.regime` exists. Many analyses have no live hybrid snapshot at log time, so `marketRegime` is `undefined`. The whole `regime-conditional` machinery (applyNotebookSkillsToAnalysis with `regime` option, the strict-matcher's regime lane, the `applyEvidenceDecay` cross-regime halving) runs on missing inputs for those trades.
- There's no `regimeLedger` per coin — the harness cannot say "BTC has spent 58% of the last 90 days ranging." That's a real signal gap.

### 3.4 No base-rate calibration

- `AlgorithmicMemoryService.ts:58-101` computes per-family W/L but `familyPerformance` is **never read by any prompt path** (the field exists on `GlobalMemory` but `getMemoryFilesContext` doesn't surface it). It surfaces in the dashboard only.
- There is no per-(family × direction × regime) base rate with confidence intervals. A user can't see "your breakout trades win 31% over 18 samples — your High conviction on breakouts is miscalibrated by ~25 points."

### 3.5 Evidence-gate missing on candidate avoid

- `SkillMemoryService.ts:1466-1473` — a `candidate` (status) avoid skill that strictly matches caps High/Medium → Low with **no check on `wins + losses`**. A 0-evidence candidate that was created from a single clustered trade (worth-gate path with `MIN_CLUSTER_FOR_SKILL = 3`) can size the user down before any of those trades actually close.
- Compare to the prompt-side injection at `MemoryRetrievalService.ts` which does rank by `evidenceFreshnessFactor(m)` (120-day decay) but doesn't gate by sample size either.

### 3.6 No global token budget + dedup

- `MemoryRetrievalService.getMemoryFilesContext` (line 403+) — pushes blocks into one 900/400/600-char budget but **does not dedup across blocks**. The same coin can appear in `matchedSkillBlock`, `uncoveredMistakeLine`, and `similarTradesBlock` independently.

## 5. New direction — what you asked for

### 5.1 Remove the chat version

The chat surface is `MessageItem.tsx` + `ChatArea.tsx` + `ChatInput.tsx` + the entire `components/chat/` tree. The debate UI is layered on top of chat messages. Concretely:

- Keep `MessageItem.tsx` for `analysis`-bearing messages (the analysis bubble, the debate stage, the verdict).
- Delete or hide the `text`/`role` chat path. No free-form user text → no LLM chat reply. The user input is only the trading-setup form (chart + coin + direction + intent). One input, one action: **"Analyze this setup."**
- Side effect: removes `isAccuracyMode`, `isLensMode`, the `accuracySubMode` paths (the "normal mode"), `runAccuracyMode`, the `autoCapture` flow, the `MessageRole` enum's `user/assistant/system` distinction (becomes `analysis | debate | verdict`), the chat-style streaming UI, the `Message.text` field, the `MessageItem.thinking` and `MessageItem.byline` paths.
- This is a **large deletion** but mechanical: search-and-replace at the message-shape level, then remove UI surfaces. ~30 files affected.

What stays: the analysis pipeline (`useAnalysisPipeline`), the debate pipeline (`conductRealDebate`), the verdict, the post-mortem, the journal, the skills grid, the memory browser, the learning dashboard, the price-watch stack, the autopilot.

### 5.2 Remove the normal mode

"Normal mode" = `accuracySubMode === 'original'` and the free-form text path. The `AccuracyModeModal` in `App.tsx:3094`, the `accuracySubMode` setting, the `customInstructions.accuracyOriginal / accuracyPure` paths — all the dual-mode branching where the harness behaves differently based on a toggle.

Replace with a single mode: **lens mode**. Every analysis is a debate between 3-4 lens seats, with the moderator synthesizing. The user picks which lenses (Macro, Technical, Risk, plus an optional Contrarian slot) — the harness decides everything else.

What stays from "normal mode": the user can pick providers per lens via the existing `AnalystLensSettings`. What goes: the `accuracyOriginal` text path, the `accuracyPure` direct-call path, the modal, the toggle.

### 5.3 Improve lens mode — "the model itself, no personality"

Right now, `LENS_SWING_PROMPTS[AnalystRole.MACRO_VOLATILITY]` is a 200+ line persona ("You are a macro analyst with 15 years of experience…"). This is theater. The model is the same LLM. A persona prefix doesn't change what the model knows — it just makes the output more verbose and more committed to a position (which is the opposite of what the debate wants).

The fix: **drop the persona, keep the role scope.** Each lens becomes a 1-paragraph job description, not a character sketch:

```
MACRO:  Focus on higher timeframes (4H, Daily), volatility regimes, ATR, liquidity
        zones, and macro trend. Cite a specific timeframe + level per claim.
TECHNICAL:  Focus on chart structure: patterns, SMC, order blocks, EMAs, RSI, MACD,
            momentum. Cite a specific pattern + bar index per claim.
RISK:  Focus on R:R, stop placement, entry timing, and failure scenarios. For
       every setup, give the strongest case AGAINST taking it before defending it.
```

A few lines, not a character. The model already knows what an LTF/LTF context is — saying "you are a 15-year veteran" doesn't add information, it just inflates the response.

### 5.4 Strict rule: every agent verifies its data before predicting

Add a **mandatory pre-prediction gate** to every lens. Before a lens writes its prediction, it must answer three questions in the prompt:

1. **What is the specific data point?** (e.g., "BTC 4H close below $94,200, RSI 38, MACD bearish cross at 14:00 UTC on day 3 of the move")
2. **What is the source?** (the chart bar, the hybrid snapshot, the desk-tool lookup)
3. **What is the falsification?** (the single observation that, if it occurred, would invalidate the prediction)

A prediction without those three lines is invalid. This kills the most common AI failure mode in trading: confident opinion without anchoring to a verifiable observation.

Implementation: add a `buildLensPreflightBlock(setup, hybridData)` to `AnalystLensService` and inject it at the top of every lens prompt. The preflight block is the same for every seat — only the seat's *response* differs.

### 5.5 Each agent gets its own memory field and role

Right now, all lenses share the same `matchedSkillBlock` injection. The Macro lens sees the same skills as the Risk lens. That's wrong — Macro cares about regime skills, Risk cares about avoid skills, Technical cares about pattern skills.

Add a `lensScope` field to `SkillMeta`:

```ts
type LensScope = 'macro' | 'technical' | 'risk' | 'all';
```

At enforcement time, `applyNotebookSkillsToAnalysis` filters `rankedMatchedSkills` to only those where `(m.lensScope ?? 'all') === 'all' || m.lensScope === activeLens`. The default is `'all'` so legacy skills still inject.

The deeper version: each lens has a *separate* `AttributedInsight` store. The Macro lens writes "regime changed from trending to ranging" insights; the Technical lens writes "this setup has 2 prior false breakouts in 30 days" insights; the Risk lens writes "your stop is below the 4H liquidity sweep, expect a wick" insights. They never share, and the dashboard can show "what has the Macro lens learned that the others haven't?"

That's a real implementation project. The cheap version is `lensScope` on the skill — single field, two-line filter, immediate effect.

### 5.6 Tighten how each agent learns

The current loop is:

```
trade closes → applySkillEvidence (SkillMemoryService) → evidence file updated
post-mortem runs → if-then regex mined → candidate skill created
worth-gate runs every N trades → LLM judges cluster → create/merge/skip
every M minutes → doctrine rewrites
```

That's the right shape, but the verbs are blurred. Each lens should have a clear learning path:

- **Macro lens** learns *regime transitions*: "BTC was trending, is now ranging, day 4 of the transition." Stored in a new `services/learning/regimeLedger.ts` (one line per coin × day). The lens never sees the trade log; it sees its own regime ledger.
- **Technical lens** learns *pattern frequencies*: "BTC long breakouts have a 38% false-break rate over the last 60 days." Computed from `findRelevantTrades` and stored in `services/learning/patternStats.ts`.
- **Risk lens** learns *what fails*: "BTC long setups with R:R < 1.5 lose 67% of the time." Computed from closed trades and stored in `services/learning/riskStats.ts`.

Each lens's memory is *its own* file, not a shared notebook. The doctrine slot unifies them at the top, but the per-lens memory is scoped.

### 5.7 Minimal UI

The reference you pasted is **zcode-style**: one column, transcript shows what happened, no panels or tabs visible by default. Your current UI has:

- Side panel (chat list)
- Top header
- Composer (with attach, Team, send, Templates, suggestions)
- Right docked panels: analysis progress, debate side panel, jobs drawer, settings, accuracy modal
- A bottom toast area
- An inline approval modal
- A replacement offer card
- A byline under each settled bubble

A minimal version: **single column, no right panels by default, one composer, transcript that streams**. Everything is a one-line `[expand]` for a temporary view.

A specific design that I'll spell out in §7 below.

## 11. The single architectural change

Most of the items above compose into **one structural shift**: the learning loop stops being a *global notebook with per-skill attribution* and becomes *per-lens notebooks with a shared doctrine layer.*

```
TODAY (after ROUND-40):
   All trades → SkillMemoryService → skills/<coin>_<dir>_<family>.md
                                       │
                                       ▼
                  MemoryRetrievalService injects ranked slice
                  into ALL lens prompts (filtered by audience only)

NEW SHAPE:
   All trades → per-lens ledger:
                    Macro:    regimeLedger.md  (per-coin regime history)
                    Technical: patternStats.md  (per-(family×dir×regime) base rates)
                    Risk:      riskStats.md     (per-(family×dir×regime) loss causes)
                                       │
                                       ▼
                  doctrine.md (unified, settled-beliefs protected)
                                       │
                                       ▼
                  MemoryRetrievalService injects:
                    - doctrine slot (always)
                    - Macro lens sees: regimeLedger + matching skill
                    - Technical lens sees: patternStats + matching skill
                    - Risk lens sees: riskStats + matching skill
                                       │
                                       ▼
                  lens prompt reads ITS memory first, not the shared skill
```

Each lens's memory is **only that lens's**. The doctrine is the only shared file. The matching skills (the cross-coin / cross-pattern IF/THEN procedures) are still shared, but they only fire when the lens's own memory surfaces a relevant setup.

This is the change that makes the agents feel like they each have their own field and role. The other items — strict preflight, single column UI, lensScope, base rates — are all *enablers* of this shift.

**Round 44 (preflight + lens scope):** the preflight gate, `lensScope` on skills, prompt surgery. ~3 days. Pairs with the §11 changes.

**Round 45 (compounding memory):** settled-beliefs registry, cross-coin generalization, weekly rollup, sequential-eval promotion. ~1 week. This is the round where the harness starts to actually learn.

**Round 46 (falsification refinement):** veto → injection telemetry, cross-regime stamp, underperformer → roster selection. ~3 days. Closes the loop on decisions → next-decision bias.

After Round 46, the harness will:
- Refuse to write junk skills (Round 41).
- Show one column, one input, one verdict (Round 42).
- Each lens has its own memory field (Round 43).
- Each lens verifies its data before predicting (Round 44).
- Memory compounds (Round 45).
- Decisions bias the next decision correctly (Round 46).

That's a 4-week plan. The plan you pasted is the first 3 days (Tier 1). The full direction is the 4 weeks.
